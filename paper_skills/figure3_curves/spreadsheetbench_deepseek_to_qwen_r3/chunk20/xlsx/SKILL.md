## Core Workflow


After gathering enough information to understand the task (sheet structure, data patterns, target ranges), immediately transition to writing the output file. Do not continue exploration beyond what is needed to inform the write phase. Always produce a concrete output file at the required path.

- **MANDATORY FIRST ACTION**: After reading the task instruction, your immediate next step MUST be to inspect the input workbook

- **FORMULA-STRING ZERO-TOLERANCE**: The #1 grading failure is writing formula strings (e.g., `'=SUM(H2:L2)'`) to cells. The grader reads with `data_only=True` — formula strings appear as `None`. ALWAYS compute results in Python and write literal values (numbers, strings, booleans). The ONLY exception is when the task explicitly says "store the formula text" or "the grader will inspect the formula string." Before saving, scan the answer range: `if isinstance(cell.value, str) and cell.value.startswith('='): cell.value = None  # recompute`. After saving, reload with `data_only=True` and confirm answer cells contain plain values, not `None`. (print sheet names, dimensions, and sample data). You must then write and execute a solution script within the next 2 turns. Never end a turn without either inspecting or writing — idle turns that neither inspect nor produce output are prohibited. If you have inspected and understood the task, write the solution script NOW.

- **Use the exact `OUTPUT_PATH` constant from the task specification** — never retype or reconstruct it by hand. Store it in a script variable at the top of your solution and reference only that variable. If a file-not-found error occurs, print `os.listdir('.')` and compare the directory contents against the exact path string before re-running.

- Always reuse the input workbook as the basis for the output file. Load it with `openpyxl.load_workbook(input_path)`, locate the target sheet (or create it if absent), modify only the required cells/ranges, and save to the output path. Never create a new workbook from scratch (`Workbook()`) unless the task explicitly requires a blank file — doing so discards other sheets, formatting, and metadata present in the original. After saving, verify that other sheets remain intact by printing `wb.sheetnames`.



- After any inspection that confirms the task logic, your next action must be a single script that loads the workbook, applies all required changes, and saves to the exact output path. Do not split inspection and writing into separate turn sequences that risk never reaching the save step. Before declaring TASK_COMPLETE, confirm that `os.path.exists(output_path)` returns True.

- **Script delivery**: Write the entire solution script in one shot using a heredoc: `cat <<'EOF' > script.py` followed by the full script content, then `EOF` and execute with `&& python script.py` in the same shell command. Never build scripts incrementally with multiple `echo` appends across separate turns — this fragments the workflow and multiplies parsing failures. One file, one turn.


- **Checkpoint Rule (2-turn limit)**: You have exactly 2 turns to complete inspection. Turn 1: inspect the workbook (print sheet names, dimensions, all data). Turn 2: write and execute the solution script. If you reach a third turn without having written any output, STOP — you are stuck in an inspection loop. Immediately write the solution script using the heredoc pattern, execute it, and verify the output file exists with `ls -la <output_path>`. Never declare TASK_COMPLETE without a verified output file on disk.


- **Manipulation tasks (deletions, insertions, formatting)**: Before writing any manipulation code, inspect the workbook: print sheet names, dimensions, and sample data from the target area (headers, first few data rows). After saving, reload the output and verify the change was applied correctly (e.g., zero remaining matches for a deletion criterion), print sample output from the answer range, and confirm unaffected data is preserved. Do not skip inspection or verification — silent failures (misaligned columns, wrong sheet, over-deletion) are undetectable without these checks.


- **Three-phase solution pattern**: (1) Extract all input values/metadata into Python lists or dictionaries before any row iteration, (2) iterate over target rows applying the logic with the pre-extracted data, (3) reload the saved output file and print the full answer range to verify correctness. This separation prevents logic errors and makes verification straightforward.

- **Save-before-completion gate**: Before declaring TASK_COMPLETE, confirm that `wb.save(output_path)` has been called AND `os.path.exists(output_path)` returns True. If the output file does not exist on disk, you are NOT done — write and execute the save script immediately. Never end a task with only inspection output; a concrete output file at the required path is mandatory.

- **Output path consistency**: Extract the `output_path` from the task prompt once, store it in a variable at the top of your script, and use that same variable for `wb.save()` and all verification loads. Never use a different path or hardcoded string for verification — load from the exact same variable to confirm the file was written correctly.

- **FRESH WORKBOOK PROHIBITION (NON-NEGOTIABLE)**: NEVER call `openpyxl.Workbook()` or `pd.ExcelWriter()` unless the task explicitly says "create a new blank file" or "start from scratch." Always load the input with `openpyxl.load_workbook(input_path)`, modify in place, and save to `output_path`. Creating a new workbook discards all other sheets, formatting, macros, data-validation rules, and metadata. After saving, print `wb.sheetnames` and confirm ALL original sheets are present — if any are missing or a default "Sheet" appears, you created a fresh workbook; reload the input and redo the operation. This rule is repeated across sections because it is the #2 cause of grading failures after formula strings.

- **Path-error recovery**: If a `cd` or file-access command fails with "No such file or directory," do NOT search the filesystem (`find`, `ls` in parent directories). Instead, immediately re-read the `working_directory` or `OUTPUT_PATH` from the task prompt and reconstruct the path character by character. A single typo is the most common cause; filesystem searches waste turns and rarely succeed.


- **Force-write escalation**: If you reach Turn 3 without having written a solution script, you have violated the 2-turn checkpoint. Immediately write the heredoc script using ALL inspection data gathered so far — do not inspect further, do not ask clarifying questions. The script must load the workbook, apply the best logic you have, save to OUTPUT_PATH, and verify the file exists. Incomplete output is better than no output.


- **PRE-MODIFICATION SHEET AUDIT**: Before modifying any workbook, print `wb.sheetnames` and inspect the full contents of EVERY sheet, especially any sheet named "Output," "After," "Expected," or mentioned in the task. Never assume the workbook is empty or that only one sheet exists. Base all subsequent actions on what you actually observe.

- **Single-script, single-pass execution**: Write one self-contained Python script that reads the input, performs all required logic, and saves to the output path. Execute it immediately via the heredoc pattern. Never split work across multiple scripts, intermediate files, or manual shell transformations — a single cohesive code block is faster and less error-prone. This pattern has been proven to produce complete solutions without wasted turns or unnecessary complexity.
## Inspection


- Print the **entire** dataset (all rows, all columns) at the start of every task before designing any logic. This reveals headers, data types, grouping dimensions, non-contiguous layouts, and edge cases that affect the solution. Print the name, dimensions, and ALL cell values for every sheet in the workbook before writing any code. Do not skip sheets even if they appear empty or irrelevant. If an output sheet already contains data or formatting, treat it as a template—decide explicitly what to preserve versus overwrite.

- Before any transformation, inspect ALL sheets in the workbook, especially sheets named "After," "Expected," or "Target." If such a sheet exists, treat it as a worked example defining the intended output. Load and print the contents of any example sheet. Reconcile your understanding of the task against what that sheet actually shows before writing code.
- Dump the **entire** target data range in one pass before deciding on a write strategy. Sampling only the first/last N rows hides repeating sub-headers, blank separators, and duplicate patterns that affect the transformation logic.
- Before modifying any cell, inspect its current state using `print()` or direct attribute access. Check value, fill, font, alignment, and number_format of at least one cell per target column. Example: `print(f'Cell {cell.coordinate}: value={cell.value!r}, fill.start_color={cell.fill.start_color.rgb!r}')`

- **RGB type pitfall**: `cell.fill.start_color.rgb` (or `.fgColor.rgb`) may return an `RGB` typed object, not a plain string. Before using `in`, `len()`, or any string operation on a fill color, cast it: `rgb_str = str(cell.fill.start_color.rgb)`. Then use `rgb_str` for all comparisons. A one-liner type check (`print(type(cell.fill.start_color.rgb))`) before writing color logic prevents `TypeError: argument of type 'RGB' is not iterable`.

- Before writing to a column identified by letter (e.g., BN), confirm its numeric index. Read the header row and search for the column letter, or use `openpyxl.utils.get_column_letter()` to map indices. Never assume a column letter maps to a small index — letters like BN correspond to high indices (e.g., 66). Print the mapping for all target columns before writing.
- When grouping or aggregating, inspect ALL columns that partition the data (e.g., employee numbers, regions, categories) not just the obvious one (e.g., week). Use a tuple of all partitioning columns as the grouping key. After building grouped structures, print the keys alongside their aggregated values to verify correct segmentation.
- After dumping the data, use the detected dimensions (`ws.max_row`, `ws.max_column`) or `ws.iter_rows()` with no arguments to define iteration ranges. Never hardcode cell ranges (e.g., `A1:A4`) based on assumptions or partial snippets — always derive ranges from actual workbook inspection.
- After loading the workbook, print the coordinate, `repr(value)`, type name, and `number_format` for every cell in the target range. Example: `for row in ws.iter_rows(min_row=1, max_row=ws.max_row, max_col=ws.max_column): for cell in row: print(f'{cell.coordinate}: {repr(cell.value)} ({type(cell.value).__name__}), format={cell.number_format}')` This reveals mixed data types (e.g., datetime objects vs. ISO strings) that would otherwise cause incorrect transformations.

- Read exact sheet names from `wb.sheetnames` before accessing any sheet. Never rely on sheet names from the task instruction — they may differ in capitalization, spacing, or spelling. Use the names exactly as returned by `wb.sheetnames`.
  **DO NOT** access a sheet by a name from the task instruction without first printing `wb.sheetnames` and using the exact name found there. Task instructions frequently misname sheets (e.g., 'Import Data' vs. actual 'Imported Data'). Always print the list, then use the matching name.
- Before modifying a target cell, inspect its full context: (a) the cell's current formula/value and `number_format`; (b) all cells referenced in its formula, including edge cases (e.g., the upper bound of a MAX range); (c) any cells affecting conditional logic (e.g., the IF condition). Use multiple exploration passes if needed. After changes, verify the number_format is preserved and surrounding cells are undisturbed.

- Print cell values, fonts, and fills together in one pass before any modifications. Example: `for row in ws.iter_rows(min_row=1, max_row=ws.max_row, max_col=ws.max_column): for cell in row: print(f'{cell.coordinate}: value={cell.value!r}, font={cell.font.name!r}, fill={cell.fill.start_color.rgb!r}')` This reveals header styling, existing formatting, and data layout in a single inspection step.

- After dumping all input data, explicitly confirm the data patterns, gaps, and example values match your understanding of the task before writing any code. If an example output sheet exists, reconcile your logic against it at this stage.

- After printing the header row, explicitly print the column letter and its numeric index for every target column. Example: `for col_idx, header in enumerate(headers, 1): print(f'Col {get_column_letter(col_idx)} (idx {col_idx}): {header}')` This prevents misidentifying column positions when task instructions reference letters like Q, BN, or AZ.

- Print merged cell ranges using `ws.merged_cells.ranges` before any modifications. Merged cells affect how data is read and written — values exist only in the top-left cell of each merged range.

- When an example sheet (e.g., "After," "Expected") exists, identify output cells by structural clues—non-empty values in adjacent columns, not fill color alone. Dump every column in the used range, not just the primary value column. Fill color is unreliable across openpyxl versions; adjacent-column data is deterministic.

- Never trust external data previews (e.g., `spreadsheet_content` hints) as the full truth — they may show only a subset of rows or columns. Always inspect the actual workbook with openpyxl to determine the real structure, headers, and column mappings before writing any transformation logic. After printing all sheets, confirm you've inspected every sheet in `wb.sheetnames` and explicitly reconcile your code's assumptions against observed dimensions (max_row, max_column) before writing any solution logic. This one-pass full inspection prevents assumptions about data layout, header positions, or value formats that would require costly rework later.

- When checking cell content against a target value (e.g., searching for 'X', a number, or a string), load the workbook twice: once normally (`data_only=False`) to see stored formulas, and once with `data_only=True` to see evaluated results. Use the evaluated value from the `data_only` load for matching. Print both the stored formula and the evaluated value for any cell where they differ. Example: `wb_data = openpyxl.load_workbook(path, data_only=True); ws_data = wb_data[sheet_name]; print(f'Stored: {repr(ws.cell(r,c).value)}, Evaluated: {repr(ws_data.cell(r,c).value)}')`

- When the task references criteria cells (e.g., filter values in specific cells like I2, J2), print their exact values, types, and number_formats before designing any filter logic. Also dump the full target write area (headers and all rows) to confirm whether it is empty or contains existing data. After this step, state aloud: the criteria types (string/datetime/number) and whether the target range is populated.

- Complete the full-range inspection (all rows, all columns, all sheets) BEFORE writing any output cells. Map out data blocks, headers, existing values, and empty target cells from this inspection before choosing a computation approach.

- Before writing any lookup or matching logic, state in plain English exactly what value you expect in at least one specific output cell (e.g., G2) and why. If the task says "corresponding ID" or "matching value," confirm whether the match searches across ALL rows (lookup table pattern) or only within the SAME row (self-check pattern). Print the parameter values you will search for and the full column you will search within. If no clear example exists, manually test your interpretation against 2-3 rows before coding.

- When a sheet named "Desired Results," "Expected," "After," or similar exists, treat it as the **authoritative ground-truth target** — not a vague hint. Your output must match it cell-by-cell. Before writing any code, print every cell in that sheet with coordinates and `repr(value)`. After producing your output, load both sheets and compare programmatically (see Verification).

- Before writing formulas that reference lookup tables, inspect BOTH the lookup column and the reference column using `repr()` to see whitespace, special characters, and exact data types. Print a few sample values from each side to confirm the mismatch (e.g., trailing spaces in one column but not the other). Then design the fix that addresses the actual mismatch — do not apply hints literally without verifying the resulting formula is syntactically valid.


- After completing the full inspection pass (all sheets, all rows, all columns), explicitly log your findings in plain English before writing any code: list the fixed columns, variable columns, lookup mappings, data types, and any discrepancies between task instructions and actual file contents. This checkpoint ensures your transformation logic is grounded in observed reality, not assumptions.

- When dumping all rows, explicitly note the boundary between data rows and empty/non-data rows (e.g., the first row where all key columns are None). Use this boundary to set iteration limits so downstream logic processes only the intended source rows, not trailing empty rows or secondary tables below the data block.

- When a task requires filling or modifying a column, confirm the exact row range that needs changes (e.g., rows 2–154) by printing `max_row` and spot-checking both the first and last few rows with both `data_only=False` (formulas) and `data_only=True` (cached values). Only proceed to writing after this range is confirmed.

- Before any substring search or row-deletion logic, print the header row (if present), all data rows, sheet name, and dimensions. This ensures the exact row positions for matches are visible and verifiable before writing manipulation code. After printing, confirm the target substring appears at the expected row(s) before proceeding.

- When printing cell values with `repr()` and `type()`, explicitly note whether boolean-like values are Python `bool` (`True`/`False`) or strings (`'True'`/`'False'`/`'none'`). This distinction directly affects condition logic: `cell.value is False` vs `cell.value == 'False'`. Print a summary of unique types found in each column before writing any conditional code.

- **Before any file operation, confirm the exact path**: print `os.path.exists(spreadsheet_path)` using the path from the task specification verbatim. If False, print `os.listdir('.')` and compare against the exact path string before retrying. Never retype, guess, or search for alternative file locations — use the provided path exactly.

- When printing cell values during initial inspection, always include coordinates: `print(f'{cell.coordinate}: {repr(cell.value)}')`. This confirms column positions and data layout match the task description before any manipulation code is written. The coordinate-value pairing is the fastest way to catch column misalignment errors.

- When printing all rows and columns, explicitly note any duplicate entries, repeated header rows, or non-contiguous data blocks. List all unique values in lookup/helper columns to confirm the data domain before designing filter or grouping logic. This prevents surprises from unexpected duplicates or sparse key columns.

- **Full-range diagnostic with constraint detection**: After dumping all data, print a diagnostic covering every row in the target range — input values, existing output values, and computed match/lookup results — before writing any transformation code. This reveals edge cases (typos, mixed types, blanks) across the entire dataset, not just the first N rows. Also explicitly scan for rows beyond the main data block that contain constraints, thresholds, or metadata (e.g., min/max values, capacity limits, target totals). Print these rows with their row numbers and values, and label them as constraints. Use this diagnostic as your baseline for later verification.


- **Pre-code confirmation checkpoint**: After printing all non-empty cells across all sheets, explicitly confirm you have identified: (1) the full data range (first and last row/column), (2) all parameter/criteria cells and their exact values, (3) all header rows, and (4) the target output positions. Only then proceed to write solution code. This checkpoint prevents coding against incomplete understanding of the workbook layout.

- **Inspection depth heuristic**: For sheets with ≤50 rows, print every cell value. For larger sheets, print at least the first 20 rows and last 5 rows to confirm data boundaries, lookup table positions, and existing formula structures. This broader initial sample catches multi-region layouts (e.g., a lookup table in rows 2–8 followed by data starting at row 12) that narrower samples miss.

- **Multi-sheet task rule**: When the task instruction mentions multiple sheets, a "second worksheet," or an attached example, you MUST print the full contents of EVERY sheet before writing any code. Do not rely on the instruction text alone to infer the expected transformation — the second sheet often contains the authoritative expected output. After printing all sheets, explicitly state which sheet defines the expected outcome and reconcile your planned logic against it.

- **Print ALL rows, never sample**: Use `ws.max_row` to print every row of every sheet. Do NOT limit inspection to the first N rows (e.g., `[:5]`) — data beyond the sample may be critical for the answer. Also cross-check the `spreadsheet_content` field from the task prompt; it often reveals rows or sheets your openpyxl inspection might miss. After printing all rows, confirm the count matches `ws.max_row` before writing any code.

- **Dual-load inspection for multi-region sheets**: When the workbook contains summary rows, data blocks, or non-contiguous regions, load the workbook twice: once normally to see formulas, and once with `data_only=True` to see computed values. Print all rows and columns from both loads. Explicitly identify each region's boundaries (e.g., summary rows 1-5, data rows 12-22) and the relationships between them before writing any output code. This dual-load, full-print pattern catches computed-value discrepancies and multi-region layouts that single-load inspection misses.

- When the task involves fixing or modifying formulas, print the full contents of every relevant sheet before touching any cell. Identify the lookup axes (row headers, column headers), key cell values, and range boundaries. Compare working vs. broken formulas side by side to understand the structural difference before coding a fix.

- Before any row-deletion logic, print every cell value in the target column(s) row-by-row (e.g., `for r in range(1, ws.max_row+1): print(f'Row {r}: {repr(ws.cell(r, col).value)}')`). This reveals blank regions, data boundaries, and the exact rows that will be affected. Confirm the first and last data rows and all blank gaps from the printed output before designing the deletion approach.

- **Proven habit: full-structure inspection before any action.** Load the workbook, print every non-empty cell with coordinates and `type(cell.value).__name__`, and confirm you understand data ranges, header positions, criteria lists, and pre-existing formulas before choosing an approach or writing output. This single habit has repeatedly prevented incorrect assumptions and rework.


- **Pre-lookup column mapping checkpoint**: Before building any lookup dictionary or composite key, print the header row with column letters and indices for EVERY sheet involved. Then print a sample of 3-5 actual key values from each sheet side-by-side to confirm the columns align. Example: `for r in range(2, min(6, ws.max_row+1)): print(f'Sheet1 key: {ws1.cell(r, col1).value!r}, Sheet2 key: {ws2.cell(r, col2).value!r}')`. If the keys don't match in format or content, stop and remap columns before writing any lookup code.

- **Trace filtered/matched rows during execution**: When applying filtering or matching logic, print each row that passes the criteria as it is processed (e.g., `print(f'Row {r}: {value} matched')`). This provides real-time traceability and confirms the filtering logic is producing the expected subset before writing output. This habit has been proven to catch misinterpretations of task criteria early.

- **Proven habit: dual-sheet header inspection first.** When the workbook contains multiple sheets, print the headers and first few rows of EVERY sheet before choosing an approach. This reveals column mappings, data layout differences, and expected-output patterns that single-sheet inspection misses. This pattern has consistently produced correct lookup logic and prevented misaligned transformations.
## Writing Output


- Before writing to any answer range, print all non-empty cells in that range with `repr(cell.value)`. If cells already contain data, verify them against the task logic. Preserve existing correct values and only fill in missing or incorrect cells. Do not blindly clear the answer range unless the task explicitly requires regenerating all values from scratch.
- **CRITICAL: Write computed literal values, never formula strings.** Unless the task explicitly says "store the formula text" or "the grader will inspect the formula string," compute results in Python and write the numeric/string values directly to cells. Formula strings (e.g., `'=C2-D2'`, `'=SUMIF(...)'`, `'=OFFSET(...)'`) are NOT evaluated when the grader reads with `data_only=True` — cells will appear as `None`. This is the #1 cause of grading failures. When a task says "write a formula that does X" or "fix the formula in cell Y," it is describing the logic you must implement in Python — compute the result and write the literal value. Example: `ws.cell(row=r, column=5).value = sum_c - sum_d` NOT `ws.cell(row=r, column=5).value = f'=C{r}-D{r}'`. After writing, verify by loading with `data_only=True` and confirming answer cells contain numbers/strings, not `None` and not strings starting with `=`. **This rule overrides all other guidance about formulas — if you are ever tempted to write a formula string, stop and compute the value in Python instead.**


- **"I need a formula" interpretation trap**: When the task says "I need a formula for an Excel sheet that assigns a score of 6, 3, 2, or 0..." or similar phrasing, interpret this as a request for the resulting computed VALUES in the answer range, NOT for the formula text itself. Compute the scores in Python and write the numeric results directly. Do NOT write formula strings and then verify them by printing the formula text — that confirms nothing about the actual cell values. After writing, load with `data_only=True` and confirm cells contain the expected numbers (6, 3, 2, 0), not formula strings and not None. This interpretation applies to ALL task phrasings that mention formulas, functions, or calculations — unless the task explicitly says "store the formula text" or "the grader will inspect the formula string," always write computed literal values.

- **Round values to match declared number_format precision before writing.** After determining the number_format string for a cell (e.g., `'0.00000000000'` for 11 decimals), round the computed value to the same number of decimal places: `round(value, N)` where N is the count of `0` characters after the decimal point in the format string. Write the rounded result, not the raw floating-point value. Do not rely on the format string to truncate at display time — the stored value must match the declared precision exactly. After saving, verify that `round(cell.value, N) == cell.value` for every graded cell.




- When replacing or regenerating content in a target sheet, clear existing data in the target ranges first before writing new values. Use the answer-range dimensions as guidance for how many rows to clear and fill. After writing, check cells immediately beyond each table's data rows for stray values that the clearing step should have removed.
- When clearing backgrounds or formatting, use UNCONDITIONAL reset: `cell.fill = PatternFill(fill_type=None)` for every cell in the range. Do NOT gate clearing on existing fill attributes (e.g., `if cell.fill.start_color.rgb`). Apply clearing inside the same loop that writes new values, not in a separate pass.

- When copying rows from a source sheet, preserve ALL style properties from the source cell: font, fill, border, alignment, number_format, and protection. **NEVER assign a source cell's style proxy objects directly** (e.g., `target_cell.font = source_cell.font`) — this causes `TypeError: unhashable type: 'StyleProxy'`. Instead, extract individual properties and create fresh style objects: `target_cell.number_format = source_cell.number_format`; for alignment, construct `openpyxl.styles.Alignment(horizontal=source_cell.alignment.horizontal, vertical=source_cell.alignment.vertical)`; for font, extract name/size/bold/italic individually. Only modify number_format for columns that explicitly need different display formatting. After writing, spot-check that unmodified columns match the source formatting exactly.
- Before writing computed results to any answer range, explicitly clear every cell in that range (set to None or empty string). This prevents stale values from prior edits or template defaults from contaminating the output. After writing, scan the entire answer range to confirm only intended rows contain non-None values.
- When implementing conditional logic with multiple rules, decompose each sub-condition into a well-named boolean variable, then apply rules in priority order using if-elif. This makes the logic directly traceable to task instructions and prevents tangled nested conditions.

- When a task asks why a formula does not return a value or describes a displayed-value discrepancy, compute the result in Python and write the literal value — do NOT write a formula string. Load with `data_only=True` to read cached values, compute the intended result, and write it. After writing, confirm `cell.value` is a number/string, not a formula, unless the task explicitly requires formula correction.

- When copying or transforming cell values (e.g., pulling datetimes from one column to another), iterate over rows, check that the source cell value is not None, compute the target value in Python, and assign it directly: `if source_cell.value is not None: target_cell.value = source_cell.value`. This pattern ensures answer ranges contain actual data values (datetime, int, float) rather than formula strings.

- After inspecting the input workbook and confirming `ws.max_row`, use that value to parameterize all row iteration (e.g., `for row in range(2, ws.max_row + 1)`). Never hardcode row counts based on assumptions or partial previews. If the task specifies a fixed answer range, reconcile it against the observed `max_row` before writing — if they differ, use the observed dimensions and document the discrepancy in a comment.

- When writing cells that may contain mixed types (strings, numbers, blanks), always use openpyxl direct cell assignment (`cell.value = value_or_None`), never pandas `to_excel()` which can reinterpret dtypes and produce `NaN` instead of blank cells. Write `None` for empty/no-match cells to produce genuinely blank cells in the output.


- **Formula trap — one rule to remember**: ANY formula string written to a cell will appear as `None` when the grader reads with `data_only=True`. "Fix the formula," "write a formula," and similar phrasing all mean: compute the result in Python and write the literal value. Verify with `data_only=True` load — every answer cell must contain a number/string, not `None` and not a string starting with `=`.

- **Match the exact `answer_position` from the task specification.** Before writing, print the `answer_position` (e.g., `G1:I1000`) and confirm how many columns and rows the grader expects. Write ONLY those columns — do not add extra computed columns (like totals or intermediate values) inside or adjacent to the answer range unless the task explicitly includes them. After writing, read back the exact answer range and confirm the column count matches.

- **Before saving, scan answer cells for formula strings**: `if isinstance(cell.value, str) and cell.value.startswith('='): cell.value = None  # or recompute`. Formula strings written via openpyxl are NOT evaluated — they appear as `None` when the grader reads with `data_only=True`. Always compute results in Python and write numeric/string values directly. After writing, load with `data_only=True` and confirm answer cells contain numbers/strings, not `None`.

- **Type-cast after string cleaning**: When cleaning numeric strings (e.g., removing commas, currency symbols, or whitespace with `re.sub`), convert the cleaned result to `float` or `int` before assigning to `cell.value`. Example: `cleaned = re.sub(r'[^\d.]', '', str(cell.value)); cell.value = float(cleaned) if cleaned else None`. After saving, load with `data_only=True` and print `type(cell.value).__name__` for every cell in the answer range \u2014 if any value is `str` when it should be numeric, re-process and re-save.
- When extracting substrings from structured text (e.g., a value between a prefix and a delimiter), use a targeted regex with a capturing group: `re.search(r'Prefix-([^,]+)', cell_value)`. Apply `.strip()` to the captured group before writing to the target cell. After writing, print both the source text and the extracted result for every row to verify correctness.

- **"Fix the formula" / "Modify the formula" trap**: When the task says "fix the formula in cell X" or "update the formula to handle Y," it is describing the transformation logic you must implement in Python — it is NOT asking you to store formula text in the cell. ## Common Pitfalls


- When filling letter suffixes for URNs (e.g., '5a', '5b', '5f'): parse existing lettered values to set the letter counter correctly. For a pure numeric URN like '5', reset the counter to 0 (next blank gets 'a'). For an already-lettered URN like '5f', extract the letter index (f=6) and set the counter to that index so the next blank continues with 'g'. Do NOT reset the counter to 0 when encountering a lettered URN. After writing, verify that within each numeric URN group, letter suffixes increase strictly (a,b,c,...) with no gaps or repeats.

- When computing balances from columns named "DEDUCTIONS" or "ADDITIONS", pause to map the natural sign direction: a deduction reduces what is owed (makes balance more positive), an addition increases what is owed (makes balance more negative). Write a comment in your script showing the formula mapping (e.g., `new_balance = previous - deductions + additions`) before assigning to cells. Hand-check one row with a non-zero value to confirm the sign, then after writing load with `data_only=True` and print the answer range to verify.

- If openpyxl.load_workbook raises a TypeError about styles (fills, fonts, borders), unzip the xlsx, remove or comment out the offending elements in xl/styles.xml, re-zip, and reload. Do not abandon the file or switch libraries. After fixing, verify the output file exists with `ls -la <output_path>`.

- When deleting or inserting multiple rows, collect row indices first, sort in descending order (highest to lowest), then process in that order. Example for deletions: `for r in sorted(rows_to_delete, reverse=True): ws.delete_rows(r, 1)`. Example for insertions: `for r in range(max_row, min_row - 1, -1): ws.insert_rows(r)`. This prevents index shifting from corrupting subsequent operations.

- The same reverse-order rule applies to column deletions: `for col in sorted(cols_to_delete, reverse=True): ws.delete_cols(col, 1)`. Deleting columns left-to-right shifts indices, causing later deletions to target wrong columns.

- When a task says "look for value X in the cells above/below row Y," decide on a scan direction before writing any code and document it in a comment. Prefer scanning from the column header downward, taking the FIRST match that satisfies the condition, unless the instruction explicitly says "closest" or "nearest." After writing the result, verify the answer cell contains a data value (not a formula string) and spot-check the scanned column to confirm the correct match was selected.

- When the task describes a row range (e.g., "rows 14-83") but the graded answer range starts earlier (e.g., E9:M83), inspect the extra rows (9-13) to determine if they need data, clearing, or should remain as-is. After the operation, print the entire answer range to confirm no unintended gaps.

- When deleting rows based on a cell value (e.g., "to be processed"), inspect the actual values first.
Always guard against `None` cell values before calling any string method: `if cell.value is not None and 'target' in str(cell.value).lower():`. Never call `.lower()`, `.strip()`, or `in` directly on `cell.value` without the None check — this causes `AttributeError` on empty cells. This guard is mandatory for all search-and-delete or search-and-modify operations. If they are full-string status codes, use exact string comparison (`str(cell.value).strip().lower() == "to be processed"`), not substring search (`in`). Substring matching risks deleting rows that merely contain the phrase (e.g., "to be processed later"). After deletion, print the deleted row count and spot-check a few remaining rows to confirm no partial matches were wrongly targeted.

- After row deletions, compare `ws.max_row` against the answer-range row bound from the task specification. If the answer range expects rows down to row 9 but `max_row` is now 8, ensure the graded range is still fully populated (e.g., verify row 9 still contains expected content or adjust output). Print the exact cells in the answer range and confirm none are unexpectedly empty.

- When a task instruction describes an operation on rows where a column's values satisfy a condition (e.g., "delete rows where the values in column D sum up to zero"), determine whether the check is per-row or aggregate BEFORE writing code. If the instruction mentions a threshold applied to individual values or describes deleting "rows where" a condition holds, interpret it as a per-row check: each row is evaluated independently against the condition (e.g., `abs(row_value) < threshold`). Do NOT compute a sum across all rows and apply a single aggregate decision. After writing your logic, re-read the instruction and state aloud the condition that determines deletion for a single row; if your code uses a different condition, revise it before running.

- When writing formulas into cells (only when the task explicitly requires formulas), verify the syntax is valid for the spreadsheet engine. Never apply functions like TRIM to a multi-column range reference — `VLOOKUP(F2,TRIM(Sheet3!$A$2:$D$300),2,FALSE)` is invalid because TRIM cannot operate on a range. Instead, trim only the lookup value: `VLOOKUP(TRIM(F2),Sheet3!$A$2:$D$300,2,FALSE)`. After writing any formula, re-open the output file and print the VALUES (not formula strings) of all cells in the answer range — if any cell's `.value` is `None` or an error string, the formula is malformed and must be corrected before saving.


- **Never hard-code column names or ranges copied from inspection output.** Extract headers dynamically from the first row of the data sheet using positional slicing (e.g., `fixed_cols = headers[:4]`; `variable_cols = headers[4:]`). Hard-coded lists fail silently when the sheet structure changes. After extraction, print the derived lists to confirm they match intent, but always build them from the actual sheet data. See also: Inspection rule on deriving ranges from workbook inspection.

- **Never use `pd.ExcelWriter` or `df.to_excel()` to produce the output file.** These create a fresh workbook, discarding all original sheets, formatting, and metadata. Always load the input workbook with `openpyxl.load_workbook()`, modify it in place, and save to the output path. The only exception is when the task explicitly requires a blank new file. This applies even when pandas is convenient for aggregation — do the computation in pandas if needed, but write results back into the openpyxl workbook cell by cell.

- When each answer row corresponds to a key value (e.g., a fiscal year in column H) and the source data is split into multiple blocks (e.g., per-OEM sections), your formula MUST filter by that key across the ENTIRE data range — not just the first block. Before writing, inspect the answer row's key cell, confirm the full data range spans all blocks, and include a conditional match on the key column. After writing, trace one formula to verify it selects rows from every block matching that key, not a single contiguous chunk. Also, before writing any aggregate formula (SUM, SUMPRODUCT, AVERAGE), inspect the sheet for existing precomputed subtotal or denominator columns (e.g., SUMIFS totals). If a column already holds the exact aggregate you need across all data groups, reference it directly — do not recompute from a partial range.

- **Use built-in openpyxl column/row insertion and deletion instead of manual cell-shift loops.** When moving or rearranging columns or rows, always prefer `ws.insert_cols()`, `ws.delete_cols()`, or `ws.move_range()` over manual cell-by-cell copying. Manual loops cause StyleProxy errors, deepcopy recursion, and incorrect data placement. When the instruction says "delete rows," physically remove the rows with `ws.delete_rows(row)`, never just clear cell contents (`cell.value = None`) — clearing leaves blank rows that change the answer range dimensions. After any column insertion or deletion, verify the maximum column count and header positions by printing a fresh scan of row 1, then confirm the answer range holds expected data values. After row deletions, verify `ws.max_row` reflects the expected row count and no unintended blank rows remain in the answer range.

- **Save backup of source data before destructive rearrangements.** Before any operation that shifts, moves, or overwrites cells, extract all data you will need later into a Python list or dict — including values, number formats, fonts, fills, borders, and alignments. Then perform the destructive operations (insert, delete, shift), and only afterward write the saved data back to its new location. Checklist: (1) loop through the source column's rows and store a dict per row with value and style properties; (2) perform all openpyxl insert/delete calls; (3) iterate the saved list to write data into the new location; (4) verify the target answer range and any dependent columns (e.g., totals) contain data values, not None.

- Before writing any solution, list all conditions from the instruction and confirm your code handles every one. Check for multiple criteria joined by "and," "or," or "both." After implementing, re-read the instruction and verify each clause has a corresponding code path. Missing a condition (e.g., deleting blank rows AND rows with values in a range) is a common silent failure.

- **Dynamic column search before manipulation**: When task instructions indicate column positions may vary (e.g., "column changes daily"), never hardcode column letters or indices. (1) Print the full header row to confirm all column labels and positions. (2) Loop to find the target label and store its column index. (3) Verify the found index before any destructive operation (move, insert, delete). (4) Raise a descriptive error if the label is not found — never silently proceed with a wrong column. This pattern is proven successful for tasks with variable column layouts.


- **Sorting with multiple directives**: When the task says "group/sort by X, then sort by Y," preserve the X-based grouping and apply Y only within each group. Never re-sort the entire dataset by Y globally — that destroys the primary partition. Before writing, state aloud: "Group 1 contains these rows sorted by Y; Group 2 contains these rows sorted by Y." If a reference/expected sheet exists, reconcile your grouping logic against it before coding.

- **Never hardcode row indices or ranges based on inspection output** for dynamic conditions (blank rows, rows matching a pattern, rows to delete).
