## Writing Output

The grader reads with `data_only=True`; formula strings return `None`. This rule overrides ALL other guidance — when in doubt, compute and write the value. After writing, reload with `data_only=True` and verify `isinstance(cell.value, (int, float, str))` for every answer cell — never a formula string or None. If any cell is None or a formula string, recompute and rewrite immediately.


Write computed values directly — never write formula strings (e.g., `=VLOOKUP(...)`, `=SUMPRODUCT(...)`, `=SUMIFS(...)`) unless the task explicitly asks for the formula itself to be graded. The grader evaluates cell results, not underlying code. Even if existing cells contain formulas, write computed numeric values into your answer range.

Before writing computed results to any output range, explicitly clear every cell in that range (set to None) from the minimum to maximum row/column. This prevents stale values from prior edits or template defaults from contaminating the final result.

After writing, read back with `data_only=True` to confirm cells hold numbers (int/float), not `None` or formula strings. ## Common Pitfalls


- **#1 FAILURE: Writing formulas instead of computed values**: openpyxl does NOT evaluate formulas. Any cell containing a formula string (e.g., `=IF(...)`, `=VLOOKUP(...)`, `=SUMPRODUCT(...)`) will read back as `None` when the grader opens the file with `data_only=True`. ALWAYS compute results in Python and write the final data value (int, float, str). This rule applies even when the task says "apply a formula," "create a formula," "fix the formula," "use SUMPRODUCT/SUMIFS," or "what would the formula be" — the grader reads the answer range's displayed values, not the formula code. Only write formula text if the task explicitly says "the answer cell should contain a formula" or "store the formula itself." When in doubt, compute and write the value. After writing, reload with `data_only=True` and verify EVERY answer cell holds a data type (int/float/str), never a formula string or None. This is the single most common cause of grader failures. **If you must write formula text, ensure row-dependent references increment correctly per row — never write the same literal formula string with a fixed row reference across multiple output rows.**
- **Skipping workbook inspection**: Failing to inspect pre-filled cells, headers, or data shape leads to wrong assumptions. Always dump all cells with coordinates first. Dump the FULL column range you intend to process — not just a sample — to catch edge cases (headers, blank runs, pre-existing values) that partial inspection would miss.
- **Hardcoding ranges or criteria**: DO NOT hardcode row ranges, column letters, or lookup ranges (e.g., `$F$10:$F$11`). Always derive ranges from `ws.max_row`/`ws.max_column` after inspection. For criteria lists, scan the column from header to last non-empty cell and collect all values programmatically. After reading, print collected criteria to confirm completeness.
- **Piecemeal script building / splitting work across multiple scripts**: Write the complete solution in one self-contained Python script that reads, processes, and saves in a single execution. Use the heredoc pattern: `cat <<'EOF' > script.py ... EOF && python script.py`. Never build scripts with multiple `echo` appends across separate turns, split work across intermediate file writes, or use manual shell transformations — one programmatic pass is faster, less error-prone, and consistently produces correct output.
- **Manual cell shifting**: Do NOT iterate cells to shift data. This causes StyleProxy errors, deepcopy recursion, and misaligned data. Always use `ws.insert_cols()` / `ws.delete_cols()` / `ws.move_range()` instead.
- **Overwriting source data**: Before inserting, deleting, or moving columns/rows, save all affected cell data (values + formatting) into a list/dict. Perform structural changes first, then write saved data to new locations. After any rearrangement, print a scan of the header row and target range to confirm correct positioning.
- **Creating new workbooks instead of modifying in-place**: TOP-CAUSE FAILURE. Always load with `openpyxl.load_workbook(input_path)` and modify in-place. Creating `openpyxl.Workbook()` discards sheets, formatting, and metadata. Only create new if the task explicitly says "create a new file." After saving, print `wb.sheetnames` to confirm the sheet list matches the input.
- **Mirroring existing formula patterns (OFFSET, INDIRECT, etc.)**: Seeing formulas in input cells does NOT mean you should write formulas in output. Compute referenced values in Python and write the resulting numbers. The grader reads with `data_only=True`; formula strings return `None`.
- **Hardcoding data or ranges from task previews**: Never copy values from `spreadsheet_content` into your script as hardcoded literals, and never hardcode cell ranges (e.g., `ws['A1:A4']`) based on the preview snippet. Always read input data dynamically from the workbook with openpyxl and derive ranges from `ws.max_row`/`ws.max_column` after full inspection. The preview may be abbreviated; the actual workbook is authoritative.
- **Leaving old data in target ranges**: When replacing content, clear existing data in target ranges before writing new values. After writing, verify no leftover data remains outside the expected data range. Use surgical clears — limit `iter_rows` to exact `min_col`/`max_col` to avoid destroying data outside the target area.
- **Blindly clearing answer ranges before inspection**: Never clear an entire answer range without first reading and inspecting every cell in it. Some cells may already contain correct values that the task expects you to preserve or verify. Print all non-empty cells in the answer range before any modification. Only clear cells that need to be overwritten — preserve pre-existing data that matches the task logic. After writing, confirm preserved cells still hold their original values.
- **Grouping by insufficient keys**: When aggregating or flagging, include ALL columns that segment the population (e.g., employee ID + week, not just week) as a tuple key. After grouping, print keys with results to verify no entities were conflated.
- **Conditional clearing of formatting**: When resetting backgrounds, apply unconditional reset (`cell.fill = PatternFill(fill_type=None)`) to every cell in the range. Do NOT gate on checks like `if cell.fill.start_color.rgb` — this leaves unexpected formats intact.
- **String methods on None cells**: Always guard against None: `if cell.value is not None and 'target' in str(cell.value).lower():`. This prevents AttributeError crashes.
- **Writing string representations of numbers**: After cleaning/transforming numeric data, explicitly convert to `float()` or `int()` before assigning to `cell.value`. Verify with `isinstance(cell.value, (int, float))` after writing.
- **String-only sort keys for mixed letter-number codes**: Parse numeric component into integer for comparison (e.g., `(letter, int(num))` tuple key). Pure string sort puts 'D 14' before 'D 6'.
- **Multi-directive sort destroying earlier grouping**: First directive defines primary partition; subsequent directives apply WITHIN each group — not globally. State groups explicitly before sorting and spot-check group boundaries after.
- **Overwriting structural rows (headers, subtotals, category labels)**: Before writing, inspect with `data_only=True` to distinguish data rows from structural rows. Only write computed values into data rows — preserve existing formulas, labels, and blanks on structural rows.
- **Deleting or inserting rows/columns in wrong order**: Always process deletions AND insertions in descending reverse order (`reversed(sorted(rows_to_delete))` or `for row in range(max_row, min_row-1, -1)`) to prevent index shifts. Print confirmation for each deleted/inserted item.
- **Row count after structural changes**: Verify the answer range still contains the expected number of rows. Print count before and after.
- **Ambiguous search direction in column lookups**: When told to "look for value X above/below row R," scan from column header (row 1) downward, taking the FIRST match. Only scan upward if the instruction says "closest" or "nearest." Document the chosen direction in a comment.
- **Preserving sort order**: Do not sort IDs or rows unless the task explicitly requires it. Preserve exact source order.
- **Assuming success on one sheet**: Always verify other sheets were not accidentally modified.
- **openpyxl style-parsing crashes (TypeError)**: Unzip the xlsx, fix malformed elements in `xl/styles.xml`, re-zip, and retry loading.
- **Inspection-only completion**: Never end a turn after only inspecting. The output file must be written and verified before TASK_COMPLETE.
- **Fixed references when filling across rows**: When computing values for a range of rows, always read each target row's own input cells — never use a fixed row reference (e.g., `B2`, `C2`) for every output row. In a loop, index the current row and read its column values (e.g., `ws.cell(row=row, column=2).value`). If writing formula strings (only when explicitly required), adjust row numbers in each reference (`B{row}`, not `B2`). Spot-check a few output cells against their corresponding input rows to confirm row-relative correctness.
- **Resetting letter counters on already-lettered values**: When filling letter suffixes (e.g., '5a', '5b', '5c') for blank cells based on a preceding numeric base, do NOT reset the letter counter to 0 when encountering an already-lettered value like '5f'.
