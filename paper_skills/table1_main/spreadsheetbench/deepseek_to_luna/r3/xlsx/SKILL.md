## Critical Rules (MUST follow)


- **MANDATORY pre-code full-sheet inspection — print cell values AND types for ALL relevant sheets**: Before writing any solution code, execute a read-only script that prints every sheet's name, dimensions (`max_row`, `max_column`), and ALL rows up to `min(ws.max_row, 50)` with cell coordinates, values (use `repr()`), and types. Print `ws.merged_cells.ranges` for every sheet you plan to modify. Use `data_only=True` when loading for decision-making to see computed values, not formula text. This is a hard gate; skip it only if the task explicitly does not require an output file. See the full Inspection checklist below for the complete mandatory procedure.

- **NEVER WRITE ANY FORMULA INTO ANY ANSWER CELL — NO EXCEPTIONS**: The grader reads cell *values*, not formula text. Every formula — `=SUM()`, `=IF()`, `=VLOOKUP()`, `=A1`, `=Sheet2!B3`, `=SUMPRODUCT()`, `=INDEX/MATCH` — produces `None` when read back by openpyxl. Compute every result in Python and write the literal number, string, or None. If you write a formula, the grader sees an empty cell. This rule has zero exceptions. After saving, reload with `data_only=True` and print every answer cell. If any cell is `None` or starts with `=`, recompute in Python and re-save.
- **Skip styling unless the task explicitly requires it**: If the task says formatting is "for explanation purposes only" or does not mention specific formatting requirements, do not write any code that copies or sets cell styles, fonts, fills, borders, or column widths. Style-copying code (e.g., `src._style.copy()`) often causes `AttributeError` and wastes turns. Write only the data values.


- **GATE — Save, reload, and print FULL answer-range values before TASK_COMPLETE**: After every script that modifies the workbook, save with `wb.save(output_path)`, then immediately reload the file with `openpyxl.load_workbook(output_path)`, iterate over the EXACT answer range (every row, every column — not just a sample), and print every cell's coordinate, value, and type. File existence alone (`ls`, `os.path.exists`) is NOT sufficient — you must confirm the answer-range content is correct by visually inspecting the printed output. Also print `os.path.getsize(output_path)` and verify the file size is greater than 0 bytes. A zero-byte file indicates a failed save. If the file is missing, zero bytes, or values are wrong, retry — never call TASK_COMPLETE without this printed verification. This is unconditional; skip it only if the task explicitly does not require an output file.

- **NEVER write formula expressions into output cells.** Compute all values in Python and write literal numbers, strings, or None. Formulas (e.g., `=SUMIF(...)`, `=IF(...)`, `=VLOOKUP(...)`, `=COUNTA(...)`) will NOT evaluate — openpyxl does not recalculate, so the grader sees None. After saving, reload with `data_only=True` and verify every cell in the answer range has a concrete value (int, float, str), not None and not a formula string. Print each cell's value and type to confirm: `print(f'{cell.coordinate}: value={cell.value}, type={type(cell.value).__name__}')`.
- If the workbook contains a sheet named "After" (or any sheet that appears to be a target/example output), inspect it BEFORE writing your solution. Match its exact format: whitespace, header treatment, cell placement. Use it as a functional specification.
- **Treat the "After" sheet as an answer key**: If the "After" sheet contains values (e.g., a single cell with a number, or a column marking special rows), derive your output directly from those values rather than computing independently. The "After" sheet shows the expected answer pattern — use it to identify which rows to process and what value to write. Never substitute a mathematically-derived result when the workbook already contains the answer.
- **Inspect before writing formulas**: Load the workbook and print the actual cell values and types for relevant rows/columns before writing any formula. Do not assume column contents from task descriptions or previews. Check for variations like prefixes, suffixes, or whitespace that could break exact-match conditions.
- **Save and verify the output file**: Include `wb.save(output_path)` in every modifying script, then verify with `print(os.path.exists(output_path))` in the same script. This is a hard gate — see GATE rule above.
- **Clear ALL columns before repopulation**: When writing new data to an existing sheet, clear every column that might hold legacy data from row 2 to `ws.max_row`. Do NOT guess a column range—iterate ALL columns in the output region (including separator/empty columns). Set each cell to `None` AND apply `PatternFill(fill_type=None)` to remove background color. After clearing, spot-check cells in each target region (especially near the bottom of old data) to confirm no leftover strings, numbers, or fill remain. When the output includes a computed column (e.g., a total column), include it in the clearing range. Do not assume it is already empty.
- **Clear target rows when merging into a single sheet**: When consolidating data into one sheet (e.g., a 'combined' sheet), clear all rows from 1 to `ws.max_row` (or the expected max) before writing. This prevents stale rows from previous runs from contaminating the merged output. Verify by reading back the sheet dimensions and first few rows after writing.
- After writing output, reload the workbook and verify cleared columns have no fill (print fill properties to confirm).

- **Use the exact output path from the task instruction**: Extract `output_path` verbatim from the task and pass it to `wb.save(output_path)`. Never construct a different path, rename, or use a relative path. After saving, confirm the file exists at that exact path with `print(os.path.exists(output_path))` and `ls -l <output_path>`.

- **Produce output, not explanations or code**: When the instruction asks "how can I create a VBA code that does X" or "how to modify code to achieve Y," produce the RESULTING spreadsheet at `output_path` — not the VBA, Python, or pseudo-code. The grader reads cell values, so the deliverable is the transformed workbook. Only generate code-as-output if the task explicitly requests a code file. After saving, reload and print the answer range to confirm cells hold data values (int, float, str), not code strings or formula text.

- **Do not trust pre-existing partial output**: When the output sheet already contains some values (e.g., first few rows filled), do NOT assume those values are correct or should be preserved. Treat the task instruction as the sole specification for the complete output. Clear the entire answer range and repopulate all rows from scratch based on your computed logic. After writing, verify every cell in the answer range matches your computation — not just the cells that were originally empty.

- **Delete rows bottom-to-top**: When deleting multiple rows, always iterate in reverse order — highest index first (e.g., `for r in sorted(rows_to_delete, reverse=True)` or `range(ws.max_row, 0, -1)`). This prevents index shifts from corrupting subsequent deletions. The same principle applies to column deletions: process rightmost to leftmost (`reversed(sorted(cols_to_delete))`).

- **NEVER call TASK_COMPLETE without first reloading the saved file and printing the FULL exact graded answer range.** After `wb.save()`, immediately reload with `openpyxl.load_workbook(output_path)`, iterate over every row and column in the exact answer range, and print every cell's coordinate, value, and type. Confirm results match expectations by visually scanning the printed output. This is non-negotiable — no exceptions for simple tasks, no reliance on file existence alone, no printing only the first few rows.
- **Accept empty output when logic dictates**: If your computed logic correctly results in no data rows (e.g., all rows deleted, no rows meet criteria), write only the header row (if present) and save. Do not fabricate data or second-guess a correct empty result. Verify the output matches your logic, not an assumption that output must contain data.

- **Interpret ambiguous tasks as data-manipulation problems, not formula-design problems**: When a task describes searching, filtering, or conditional lookups across a column without explicitly requesting a formula, use a Python script with openpyxl to iterate over rows, perform the logic programmatically, and write literal results. - **Complete substantive fixes before cosmetic formatting**: When the task instruction lists multiple required changes (e.g., "resolve this VLOOKUP error, then change formatting to text and left align"), treat them as an ordered sequence. Finish every data transformation, formula fix, and value correction BEFORE applying any formatting (fonts, alignment, number_format, fills). After reading the instruction, list each required change explicitly in a comment. Before writing, verify that cells expected to contain computed results hold actual values — not #N/A errors or blank cells — unless the instruction explicitly says to leave errors in place. After saving, confirm the substantive fix succeeded before moving to formatting.

NEVER redirect output to a different pre-existing sheet — the grader reads ONLY the sheet named in answer_position. After saving, reload and print `wb.sheetnames` to confirm the target sheet exists, then print every cell in the exact answer range on that sheet. If the data landed on the wrong sheet, fix it before TASK_COMPLETE.

- **Execute a read-only inspection before any code**: Before writing any solution, run a script that prints the active sheet's name, dimensions, and the first 10-20 rows of all columns. Confirm the actual data matches the task description. Then inspect the initial state of the output region (e.g., print its cells) to ensure you are overwriting correctly.

- **Base formula ranges on discovered data bounds, not assumptions**: Before writing any formula that references a column range (e.g., `$B$3:$B$40`), print `ws.max_row` and `ws.max_column` to discover the actual data extent. Check `type(original_value)` or attempt `float(cleaned_string)` — write the numeric type, not a string. Inspect any pre-existing example values in the sheet to confirm your output format matches.

- **Cross-sheet lookups must be computed in Python, never via INDIRECT formulas**: When a task requires pulling data from multiple sheets (e.g., looking up a student's age from their named sheet), iterate over `wb.sheetnames` in Python, build a lookup dictionary, and write literal values. Always identify and print the exact range the instruction labels as the actual data before computing. If the instruction mentions both a sample and an actual range, use the actual range. If ANY cell in the data_only=True pass returns `None`, `0`, or an unexpected type, the formula did not evaluate correctly — inspect the referenced source cells to diagnose why, then fall back to Python-computed literal values. Never assume syntactically correct formulas produce the intended numeric output. This applies to ALL formulas, including SUMPRODUCT, INDEX-MATCH, and simple cell references.
## Common Pitfalls


- **Alphanumeric sorting**: When sorting codes like "D 14" that mix letters and numbers, never use plain string sorting (e.g., `.casefold()`). Split each entry into its alphabetic prefix and the numeric part, convert the number to int or float, then sort by `(prefix, numeric_value)`. After writing, spot-check entries sharing a prefix to confirm numbers increase correctly (e.g., "D 6" before "D 14").
- **Assuming error values are strings**: Excel error values like `#N/A`, `#VALUE!` are not the string "error". Use `ISERROR()` or `ISNA()` for error detection, never string equality.
- **Declaring completion without producing output**: The output file must be saved and its existence verified before calling the task complete.

- **Misreading multi-criteria condition hierarchies**: When an instruction lists several conditions (e.g., "if A AND B, then if C write X else Y"), do not assume A is a prerequisite for all writes. Inspect the data for rows where partial conditions match, determine which condition gates the write, and code only that gate. Test edge cases where the first condition is false but later conditions are true before finalizing logic.


- **Writing formulas instead of computed values**: If you accidentally write formulas, reopen the workbook, replace all formula cells in the answer range with their computed static values, and save again. Then reload with `data_only=True` and confirm every cell has a concrete value.
- **Filling sequential blanks from suffixed labels**: When filling blanks with incrementing suffixes (e.g., '6a','6b','6c'), never use the literal string of the adjacent cell as the base—that cell may already contain a suffix, causing accumulation ('6a'→'6aa'→'6aaa'). Instead, inspect the full column first. Extract the numeric core from every non-blank cell using a regex like `^(\d+)([a-z]*)$`. Maintain a separate suffix counter per numeric base; reset it only when a pure number (no suffix) is encountered. Generate each suffix by converting an integer counter to a letter sequence (a, b, …, z, aa, ab, …), never by appending to the previous cell's suffix. After writing, print the first ~20 and last ~10 rows of the filled column and visually confirm suffixes restart at 'a' for each new base and increment sequentially.

- **Context-dependent 'blank row' interpretation**: When a task says "delete blank rows" without qualification, inspect the instruction's focus to determine which column(s) define blankness. If the task discusses only column A, a row is blank when column A is empty/None — other columns may contain data. After applying deletion logic, verify the answer range: if the task says "delete blank rows above X," confirm no rows above X remain that should have been removed per your interpretation.

- **Ambiguous 'above'/'below' scanning direction**: When a task says "find X in cells above row Y," the scanning direction is ambiguous — it could mean the nearest row to Y (scanning upward) or the first row from the top (scanning downward). Before coding, decide which interpretation the spec intends. If the phrasing does not say "closest" or "nearest," default to top-down scanning (matching natural data-header order). After finding the source row, print both `row` and `value` to self-verify before writing output.
- **Row insertion/deletion ordering**: When inserting or deleting rows that affect other pending row targets, always process bottom-to-top as described in Critical Rules. Before each insertion, print the current row number and confirm the target cell still holds the expected value. When testing cell emptiness, check for both `None` and empty string (`''`), since formula outputs can produce either. After deletion, reload and verify the remaining rows against expectations.

- **Row-height preservation on copy**: When copying cells from source rows to destination rows, copy row dimensions explicitly: `ws.row_dimensions[dest_row].height = ws.row_dimensions[src_row].height`. Never use self-assignment (`ws.row_dimensions[r].height = ws.row_dimensions[r].height`), which does nothing. After writing, reload and print the height of at least one middle output row alongside its source row to confirm they match.

- **Duplicate detection and sorting with mixed date formats**: When extracting rows where a key column value appears more than once, use `collections.Counter` on that column to identify duplicates, then filter the source rows. For sorting by date when values may be datetime objects or strings, build a key function that tries `datetime.strptime` with known formats as a fallback (e.g., `%Y-%m-%d`). This pattern reliably handles mixed-type date columns.

- **Column deletion scope**: When a task doesn't specify a single sheet, iterate over all worksheets (`for ws in wb.worksheets`) to apply the same treatment everywhere. Use the reverse-order deletion pattern from Critical Rules.

- **Lookup key mismatch**: Before constructing any lookup (VLOOKUP, INDEX/MATCH, or programmatic equivalent), print the lookup value and a sample of the target column values side-by-side. Confirm they share the same type and granularity (e.g., both are full dates, both are strings, both are numbers). If they differ (e.g., date vs month, string vs integer), transform the lookup value or the table values before writing the formula. This prevents silent lookup failures where no match is found.

- **Cross‑sheet value replacement by key, not row position**: When transferring values from a reference sheet to target sheets (e.g., replacing prices from ITEMS into SHEET1/SHEET2), never assume rows align by position. Build a lookup dictionary keyed by the shared identifier column (e.g., column A). Iterate over target rows, match the identifier, and write the corresponding value. After writing, verify by printing old and new values for each row to confirm correct key‑based matches.

- **Fixing formulas by writing formulas**: When the task asks to "correct" or "fix" a formula (e.g., "correct my IF formula in E2"), do NOT write a corrected formula. Instead, load the workbook with `data_only=True` to get cached values of all dependent cells, compute the correct result in Python, and write the literal value to the answer cell. The grader reads the cell's value, not its formula. After saving, reload and confirm the cell contains a concrete number, not a formula string.

- **Assuming non-empty cells should be preserved when filling/replacing values**: When a task instructs you to fill a column with computed values based on a condition (e.g., "fill column D with invoice numbers for matching rows"), write the new value to every row that meets the condition, regardless of whether the cell is currently empty or contains a previous value. Do not add a guard that only writes to blank cells unless the instruction explicitly says "only fill empty cells" or "skip cells that already have data". Before writing, inspect the target column to understand its current content, but do not use that to decide whether to overwrite. After writing, reload the file and print the target column's values to confirm they are the new values, not the originals.

- **Misinterpreting 'sort only column X'**: When an instruction says 'sort only column X' or 'sort column X lowest to highest,' apply that sort as the ordering rule for every row in the output — even within groups. Treat it as a secondary sort key on column X. After writing, verify that within each group of identical values, column X is strictly ascending.

- **Using copy-and-clear instead of delete_rows for row removal**: When the task requires removing rows and shifting remaining rows upward, use `ws.delete_rows()` — do NOT implement a manual copy-non-blank-rows-to-new-positions-and-clear-trailing-rows loop. The copy-and-clear approach leaves stale blank rows at the bottom of the sheet that the grader detects. After calling `delete_rows()`, reload the saved workbook and confirm `ws.max_row` has decreased and no trailing blank rows remain in the answer range.

- **Recompute dependent columns after row reordering**: When reordering rows (sort, insert, delete), do not copy only primary data columns. Any column that contains computed values, formulas, or derived data must be recomputed for the new row order. After reordering, iterate over all output columns and verify no cell is `None` that should hold a value — a common failure is leaving formula-dependent columns blank after a sort.

- **Bulk operations overwriting header/metadata rows**: When zeroing or filling a column, never apply the operation to all rows indiscriminately (e.g., `for r in range(1, ws.max_row+1)`). Identify data rows explicitly — exclude header rows, label rows, blank separators, and constraint-metadata rows (e.g., rows containing 'min', 'max', or similar labels). Only modify the data rows. After writing, scan the output workbook and confirm that any row whose original content was a string label still retains that string, not a numeric value.
- **Skipping zero-valued cells during addition**: When processing constraints or balances, reserve the "do not modify zero cells" guard ONLY for operations that reduce a cell value (subtraction, selling, deduction). For operations that increase a cell value (addition, purchase, replenishment), a cell starting at zero is still eligible to receive additions up to its maximum. Before finalizing any conditional skip, test against the edge case: "if this value is zero and the operation is addition, should it really be excluded?" After writing output, for each row where a residual was non-zero and the operation direction matches the skip, confirm all unit columns — including those starting at zero — were considered as potential targets.

- **Chaining in-place sorts on mutable lists**: When performing a multi-level sort, never apply two consecutive `list.sort()` calls on the same mutable collection (e.g., sort by column B, then sort by column A). The second sort rearranges elements already grouped by the first level and can silently duplicate or drop rows. Instead, extract sort keys into an auxiliary list of `(key1, key2, ..., row_data)` tuples and sort once with a compound key. After writing, confirm the number of output rows equals the number of input rows and that no duplicate full-row tuples exist in the answer range.

- **Multi-criteria row matching with array formulas**: When a single lookup column is insufficient to uniquely identify a row (e.g., matching both region AND expense name), use `MATCH(1, (range1=criteria1)*(range2=criteria2), 0)` with array multiplication. Anchor the INDEX array and both MATCH ranges with absolute references where needed for copying across cells. This pattern is reliable when the task explicitly requires formula-based lookups and the workbook context supports it.


- **Lookup-value-to-position mapping**: When a task says "column X contains the number N, then this result should reflect in cell Y," it means find the *position* (1st, 2nd, 3rd, 4th) where the lookup value appears in the reference row, not concatenate all reference values. Produce a single numeric rank per row. Before coding, inspect one concrete example row from both sheets to confirm the expected mapping. After writing, verify answer cells contain individual numbers, not delimited strings.
- **Composite-key uniqueness check**: Before building any lookup dictionary, print all distinct combinations of the proposed key columns and verify uniqueness. If a key like (meet, race) appears on multiple dates, add the date (or other discriminating column) to the composite key to guarantee a one-to-one match. Print the full set of keys and confirm the count equals the number of unique source rows before using the dictionary for lookups.

- **Replacing error values without diagnosing the formula**: When a cell shows #REF!, #N/A, or another error, do NOT immediately overwrite it with a literal value. First load the workbook with `data_only=False`, print the full formula that produced the error, and identify the root cause (wrong range, missing sheet, circular reference, column index out of bounds). Fix the logic — not just the output — so the solution generalizes. After writing, verify the cell contains a computed data value, not a hardcoded guess.
- **Sign-preservation in proportional scoring across positive and negative ranges**: When mapping values to scores linearly (e.g., min→-5, max→+5), derive the sign directly from the original value: `score = value * (target_max / abs(source_extremum))`. Never introduce a separate negative constant that flips the sign. After writing, print each value alongside its score and confirm positive inputs produce positive scores and negative inputs produce negative scores — especially at the specified extrema.
