- **ABSOLUTE RULE: Never write formula strings into answer cells.** Compute results in Python and write plain values (numbers, strings, booleans). Formula strings cause grader to read `None`. The ONLY exceptions: (a) task instruction explicitly says "write the formula itself," or (b) weighted/conditional aggregates across dynamic ranges (see below). Even for exceptions, after saving, reload with `data_only=True` and print every answer cell to confirm non-None, non-formula-string values. If ANY cell fails, rewrite with computed Python values and re-verify. Simple comparisons (RIGHT, LEFT, LEN, IF) are NEVER formula exceptions — always compute them in Python. **SUMIF, SUMIFS, COUNTIF, COUNTIFS, AVERAGEIF are NEVER formula exceptions.** These are simple conditional aggregations easily computed in Python. Always iterate rows, check conditions, and write the numeric result. Writing these as formula strings produces None on reload.

If that sheet does not exist in the workbook, create it with `wb.create_sheet()`. Never write output to the source data sheet unless `answer_position` explicitly names it.
- **Pre-save formula check (MANDATORY):** Before every `wb.save()`, iterate the answer range and assert no cell value is a string starting with `=`. Replace any formula string with its computed value immediately.
- **Aggregate formula exception (STRICTLY LIMITED)**: ONLY write an actual formula when the task instruction explicitly says "write the formula itself" AND the computation involves weighted averages or conditional aggregates across dynamic ranges. In ALL other cases — including SUMPRODUCT, SUMIF, or any calculation that can be performed in Python — compute the result in Python and write the numeric value. If you do write a formula under this exception, confirm all referenced ranges align in size and start/end rows before writing. After saving, reload with `data_only=True`. If ANY answer cell returns None after reload, replace the formula with its computed Python value and re-save. **SUMPRODUCT anti-pattern**: Writing `'=SUMPRODUCT(...)'` as a string into a cell will always produce None on reload. Compute the sum-product in Python (iterate matching rows, accumulate products) and write the final number.

### Row Insertions and Deletions
### Row and Column Insertions and Deletions
When inserting or deleting rows that affect other pending row targets, always sort target row numbers in descending order and process bottom-to-top. This ensures each operation only shifts rows below the insertion point, preserving higher-numbered target row indices.
- Use `for r in range(max_row, min_row-1, -1)` to traverse in reverse.
- Access cell values via `ws.cell(r, c).value`.
- Check for both `None` and empty string `""` to handle blank cells and formula outputs.
- Delete or insert the row only after all relevant cells in that row are checked.

When deleting columns, always process from right to left (highest column index first) to avoid index shifts.

- **Use `ws.delete_rows()` for row removal**: When the task requires removing rows and shifting remaining rows upward, always use `ws.delete_rows(row_idx, count)` rather than a manual copy-and-clear loop. Copy-and-clear leaves stale empty rows at the tail that increase `max_row` and produce `None` values in the answer range. After deletion, verify `ws.max_row` decreased by the expected count and no trailing blank rows remain in the answer range.

- **Recompute formula-dependent columns after reordering**: When rows are reordered or sorted, any column whose original values came from formulas referencing other cells in the same row must be explicitly recomputed after the reorder. For each output row, re-apply the formula's logic using the new row positions: read the referenced cells at their new locations, compute the result, and write it. Do not assume copied values will be correct — formula references shift with the row. After writing, print every cell in such columns and confirm none are `None` unless the computation genuinely yields it.

- **Verify after bottom-up deletion**: After processing deletions in reverse order, confirm the remaining rows are correctly positioned by checking that a known data row (e.g., a specific header or content row) appears at the expected index. This catches index-shift bugs even when the reverse-order pattern is used.

Source cells may carry inconsistent or hidden formatting. After writing, reload and print each cell's `.number_format` alongside its value to confirm uniform formatting across the entire output range. (Reinforced by repeated success.)

## Common Pitfalls


- Assuming sheet names (e.g., `'Sheet1'`) without inspecting the workbook first.
- Declaring completion without reloading and verifying the saved output against the answer range.
- **Hardcoding ranges** (`min_row=1, max_row=4`): Fails when data layout differs from expectations. Always inspect dimensions first and iterate dynamically.
- **Skipping output verification**: Saving a file and declaring completion without re-reading it risks undetected failures (wrong sheet, formulas instead of values, no actual changes).

- **Replacing values by row position across sheets**: When copying or updating values from one sheet to another, never assume rows align perfectly. Build a lookup dictionary from the reference sheet keyed by an explicit identifier column (e.g., column A), then iterate target rows and match by that key. Print old and new values for each matched row to confirm correct key-based replacement.
- **Filling sequential labels from adjacent cells**: When generating incremental labels (e.g., '6a','6b','6c') to fill blanks based on neighboring non-blank cells, never use the literal string of the adjacent cell as the base—especially if that cell already contains a suffixed label. This causes suffix accumulation ('6a'→'6aa'→'6aaa'). Instead, extract the numeric core from every non-blank cell (regex `^(\d+)([a-z]*)$`), maintain a running suffix index per numeric base, and reset the index only when a pure number appears. Generate suffixes by converting an integer counter to Excel-style column letters, not by re-appending the last suffix.

- **Writing formulas instead of computed values**: The most common and severe failure. Agents write complex Excel formulas as strings into answer cells, save, and declare completion without verifying. The grader then reads `None` for every cell. Always compute results in Python, write values (not formulas), and reload the saved file to confirm non-None, non-formula-string output.
- **Writing formulas that depend on volatile array formulas**: When source columns contain array formulas that return `""` for non-matching rows, downstream formulas referencing those cells will also produce empty results. Inspect with `data_only=True` first to identify which rows actually contain values, then write computed results only into those rows.

- **Mixing reading and writing in the same loop**: Writing to the target sheet before all source data is read can cause interference or incorrect values. Always separate phases: first read all source cells into a list, dict, or list of tuples, then iterate the target range and populate from that structure. Print the full extracted structure and confirm its length and values before opening the workbook for writing.


- **Sorting alphanumeric codes as plain strings**: When column values mix letters and numbers (e.g., "D 14", "D 6"), plain string sorting orders "D 14" before "D 6". Always split each entry into its alphabetic prefix and numeric part, convert the number to int/float, and sort by a tuple of `(prefix, numeric_value)`. After sorting, spot-check entries sharing a prefix to confirm numbers ascend correctly (e.g., "D 6" before "D 14").
- **Writing formulas without tracing lookup failures**: When a formula returns wrong or empty results, inspect every cell it references (lookup keys, lookup arrays, return arrays) by printing their actual values with `data_only=True`. Verify the lookup key exists in the lookup array and that the return array has a value at the matched position. Replace formulas with computed values only after confirming the lookup logic is correct.
- **Detecting duplicates and sorting by mixed-type dates**: When asked to find rows with duplicate values in a column and sort them, use `collections.Counter` on that column to identify values with count > 1. Filter rows matching those duplicates. For sorting by date when cells may contain datetime objects or strings, build a key function that tries `datetime.strptime` with known formats (e.g., `'%Y-%m-%d'`, `'%d/%m/%Y'`) and falls back to the raw value. Print the parsed dates before sorting to confirm correctness.

- **Recalculating values that already exist in the spreadsheet**: Before computing a denominator, subtotal, or intermediate result, scan the sheet for cells that already contain that exact value (e.g., sums in adjacent columns, precomputed totals). If a precomputed cell exists, reference it directly instead of duplicating the calculation. This avoids range-mismatch inconsistencies and redundant work.
- **Ignoring explicit sort instructions**: When the instruction specifies a column must be sorted (e.g., 'column H sorted lowest to highest'), apply that sort as a secondary sort key within every group, even if the instruction also says 'do not sort within the group.' The explicit sort requirement is the final ordering rule. After writing, verify that within each group of identical values in the first output column, the sorted column's values are strictly ascending.
- **Misparsing multi-condition rules as strict prerequisites**: When a task describes multiple conditions (e.g., 'if BL=LAG and BG matches X or Y, then check AY to decide the value'), do not assume the first condition is a prerequisite for all writes. Inspect the data for rows where conditions partially match (e.g., BG matches but BL≠LAG) and determine whether the instruction intends to operate on those rows too. Before coding, print rows that satisfy each condition subset and state your interpretation explicitly. Test your logic against pre-filled example rows or expected-result columns before writing the full answer range.
- **Ambiguous search direction ('above'/'below')**: When a spec says "look for X in the cells above/below row Y," do not assume a scanning direction. If the phrasing does not explicitly say "closest" or "nearest," default to top-down scanning within the referenced region (e.g., `range(1, first_match_row)` for "above"). Print both the found row number and cell value before using it, so you can self-verify the interpretation matches intent.

- **Clearing cells incompletely**: When the instruction requires a cell or column to be "empty without background colour," setting `cell.value = None` alone is insufficient — the original fill formatting persists. Always also apply `PatternFill(fill_type=None)` to remove background color. After saving, reload and print each affected cell's `.fill` property to confirm no fill remains.
- When deletion criteria involve a threshold on absolute values, both per-row checks (`abs(value) < threshold`) and aggregate sum checks (`sum(abs(v) for v in values) < threshold`) are valid approaches. Choose whichever matches the task instruction's wording, and verify the resulting row count matches expectations before deleting.

- **Leaving cleaned values as strings**: When using `re.sub` or string operations to clean cell values (e.g., stripping currency symbols, whitespace), always convert the cleaned result back to a numeric type if the original was numeric or the cleaned string represents a number. Use `float(cleaned)` or `int(cleaned)` before writing. After writing, verify with `type(cell.value).__name__` on a sample of output cells to confirm they are `float` or `int`, not `str`.

- **Copying row dimensions incorrectly**: When preserving source row heights during a copy operation, `ws.row_dimensions[r].height = ws.row_dimensions[r].height` is a self-assignment that does nothing. Always copy from the source row to the destination row: `ws.row_dimensions[dest_row].height = ws.row_dimensions[src_row].height`. After saving, reload and print the height of at least one middle output row alongside its source row to confirm they match.
- **Trusting openpyxl's inferred types for criteria and source columns**: openpyxl may display a cell as `datetime.datetime` even when the underlying stored value is a string. Before writing any filter or comparison, print the exact type and repr of the criteria cells and at least five scattered values from the column being compared: `print(type(ws['I2'].value), repr(ws['I2'].value))`. Handle both `str` and `datetime` cases explicitly (parse strings with a known format like `strptime`). This avoids type-mismatch crashes or silent filtering failures.
- **Interpreting 'blank row' too literally**: When a task says "delete blank rows," read the full instruction to identify which column(s) define blankness in context (often a single key column like A). Do not require every cell in the row to be None. After applying your deletion logic, reload the saved workbook and confirm no rows remain that should have been removed according to your context-aware interpretation.
- **Trusting truncated task-instruction summaries**: The `spreadsheet_content` preview in the task prompt is often truncated and incomplete — it may hide rows, columns, or entire sheets. Always load the live workbook with openpyxl and print every sheet's full contents (all rows, all columns) before writing any logic. If answer-range values seem inconsistent with the preview (e.g., IDs not seen in any preview row), pause and re-inspect the source data. Never assume the preview shows all rows or correct data types.
- **Losing numeric sign in proportional mappings**: When mapping values across both positive and negative ranges (e.g., -5 to +5), derive the sign directly from the original value — do not introduce a separate negative constant that flips signs. For a formula like `score = value * target_max / abs(extreme)`, use the raw `value` (preserving its sign) multiplied by the positive target magnitude. After writing, verify sign consistency by printing each input value alongside its output score and confirming negative inputs produce negative outputs.
- **Splitting text at character-type boundaries**: When a task requires splitting a string at the first letter, digit, or other character class, use `re.search(r'[a-zA-Z]', val)` to locate the split position. This generalizes to any pattern where a substring must be extracted based on character type transitions.
- **Bulk-operating across all rows without distinguishing data from metadata**: When zeroing, clearing, or overwriting a column, never apply the operation to every row blindly (e.g., `for r in range(1, max_row+1)`). First identify which rows are data rows versus header, label, or constraint-metadata rows. Restrict the operation to data rows only. After writing, verify that any row whose original content was a string label still retains that string, not a numeric value — scan the output and confirm non-data rows are unchanged unless the instruction explicitly requires modifying them.
- **Skipping zero-valued cells during addition operations**: A guard like `if value == 0: continue` is correct only for operations that reduce a cell (subtraction, deduction, selling). For operations that increase a cell (addition, replenishment, purchase), a zero-valued cell is a valid target and should not be skipped. Before finalizing any conditional skip, test the edge case: "if this value is zero and the operation increases it, should it really be excluded?" After writing output, for rows where a residual was distributed, confirm that all eligible unit columns — including those starting at zero — were considered as targets when the operation would increase their value.
- **Misinterpreting 'modify code' requests as code-generation tasks**: When the instruction asks how to modify existing VBA or script code to achieve a sheet-level transformation (e.g., 'How can I modify my VBA code to delete blank rows?'), interpret this as a request to perform the transformation directly on the spreadsheet and save the result to the output path. Only generate code text if the instruction explicitly asks for the code itself, not the modified spreadsheet.

- **Writing cross-sheet reference formulas**: When the answer range needs values derived from other sheets (e.g., student ages from individually named sheets), never write INDIRECT, VLOOKUP, or other reference formulas that depend on sheet-name construction. These produce None when read back. Instead, iterate all relevant sheets in Python, extract the needed values into a dict keyed by sheet name or identifier, then write the computed static values into the answer range. After saving, reload with `data_only=True` and confirm every answer cell contains a number or string, not None.
- **Skipping sheets referenced in data cells**: When a column contains values that match other sheet names (e.g., student names in column A that correspond to sheet tabs), inspect every sheet in `wb.sheetnames` before writing any output — not just the active sheet. Print the full contents of each referenced sheet to confirm the data you need exists and to catch edge cases (e.g., extra students, missing sheets).
- **Assuming cell content type without inspection**: When a condition references a column that might contain error values (e.g., checking if a cell equals "error"), always print the actual cell values first with `data_only=True`. Excel error types (`#N/A`, `#VALUE!`, `#REF!`, etc.) are not strings — they are `openpyxl` error objects. Use `cell.value` and check `isinstance(cell.value, openpyxl.cell.cell.TYPE_ERROR)` or inspect the string representation. For formula-based condition checks, use `ISERROR()` or `ISNA()` rather than string equality. After writing, print the answer range to confirm non-None computed values, not empty results from mismatched conditions.
- **Defaulting to formulas for lookup/search tasks**: When the instruction describes finding matching rows, searching a column for substrings, or looking up values based on conditions, solve it with a Python script that iterates over the data—not with VLOOKUP, XLOOKUP, or INDEX-MATCH formulas. Use `casefold()` or `.lower()` for case-insensitive text matching. Only write formulas when the instruction explicitly requires them or when the task involves weighted aggregates across dynamic ranges (per the aggregate formula exception above).

- **Assuming traversal order when a reference sheet exists**: When a reference/expected-result sheet is provided, never assume row-major or any default scan order. Print the reference sheet's full contents and deduce the exact ordering pattern (row-by-row, column-by-column, grouped by source column, etc.) before writing your algorithm. Reconstruct the reference values exactly in code as a self-check before writing output.

- **Conditional overwrite guards that preserve old data**: When a task describes filling, replacing, or updating values in a column, write the new values unconditionally to every row matching the criteria. Do not add guards like `if cell.value in (None, '')` unless the instruction explicitly says "only fill empty cells" or "skip cells that already have data." After writing, reload and confirm the output cells hold the new expected values, not the originals.

- **Leaving computed columns as None after row reordering**: When reordering or sorting rows, columns that originally contained formulas (e.g., conditional lookups within the same row) become stale or `None` if only static values are copied. After any row reorder, identify all columns with formula logic, recompute their values using the new row positions, and write the results. Print the answer range afterward to confirm no formula-dependent column contains `None` unexpectedly.

- **Removing all blank rows without analyzing structure**: Blank rows may serve as intentional separators between data blocks. Before filtering out rows where all values are None/empty, inspect the full sheet to identify the layout pattern. If the input has separator rows between logical groups, preserve a single empty row between those groups in your output. After writing, confirm that sections separated in the input remain separated in the output.
