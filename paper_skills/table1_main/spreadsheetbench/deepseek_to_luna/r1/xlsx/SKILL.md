## Critical Rules (MUST follow)


- Parse `answer_position` to extract the EXACT sheet name and cell range. Write output ONLY to that sheet.
- **Save to the exact `output_path` — no temp files, no renames.**
- **Save-then-reload gate (MANDATORY):** After every `wb.save()`, immediately reload the workbook from the exact output path with `data_only=True` and print every cell in the answer range. This single-step save-then-verify pattern is proven grader-safe: write once to the exact path, run `ls -la <output_path>` to confirm the file exists on disk, then reload and print cell values. File existence alone (`ls`) is NOT verification — you must see the actual cell values from the saved file before TASK_COMPLETE. This gate is non-negotiable and must appear in your output. Extract the `output_path` from the task instruction and pass it verbatim to `wb.save(output_path)` in a single write operation. Never save to a temporary location and then move or rename the file. After saving, immediately verify the file exists with `ls -la <output_path>` and reload it with openpyxl to confirm contents. This single-step save-then-verify pattern is proven grader-safe.
- **Target sheet existence check:** Before writing any output, check `wb.sheetnames` for the sheet named in `answer_position`. If it does not exist, create it with `wb.create_sheet('ExactSheetName')`. Never default to modifying the source data sheet — the grader reads ONLY the sheet specified in `answer_position`.
- When a spec says "look for X in the cells above row Y," scan **top‑down** (from row 1 toward Y) unless the spec explicitly says "closest," "nearest," or "immediately above." Print both the row number and cell value after finding the match so you can self‑verify before writing.
- After saving the output workbook, open it fresh with openpyxl, read the exact answer cell(s) the grader will check, and print `cell.value` and `type(cell.value)` before calling TASK_COMPLETE. Never rely on in‑memory values from the write pass.
- **Write computed values, never Excel formulas**, unless the task explicitly says "provide the Excel formula." Compute the result in Python (e.g., `round(value, 2)`) and write the number/string directly to the cell. The grader reads with `data_only=True` and will see `None` for any uncalculated formula. This includes volatile functions like INDIRECT, OFFSET, and TODAY — they will NOT evaluate and will appear as `None`. Always compute the final value in Python and write it as a static number or string.
- **ABSOLUTE PROHIBITION — formula strings:** NEVER write code like `cell.value = '=SUMPRODUCT(...)'` or `cell.value = f'=VLOOKUP(...)'`. These are STRINGS, not computed values. The grader WILL see `None`. Instead, compute the result in Python (loop, sum, filter, etc.) and write the final number: `cell.value = int(round(computed_total))`. After saving, reload with `data_only=True` and verify `isinstance(cell.value, (int, float))` is True — if you see a string starting with `=`, you wrote a formula, not a value. This is the #1 cause of grader-visible failures.
- **SUMIF/SUMIFS/SUMPRODUCT trap:** These functions will NEVER evaluate in openpyxl. If you find yourself typing `'=SUMIF('`, `'=SUMIFS('`, or `'=SUMPRODUCT('`, STOP — you are about to write a formula string. Compute the conditional sum/product in Python using a loop with an `if` condition, then write the numeric result. After saving, reload and verify the cell holds an `int` or `float`, not `None` and not a string starting with `=`.
- **Pre-write data inspection (formula safety check):** Before writing ANY formula or value into an answer range, load the workbook with `data_only=True` and print the exact answer-range cells. If ANY cell in the range currently contains a formula (visible as `None` or a string starting with `=` in the formula-version workbook), do NOT write new formulas that depend on those cells — they will cascade to `None`. Instead, compute ALL needed values in Python and write them as static numbers/strings. This is the #1 cause of grader-visible `None` failures.

- Read the task instruction as an ordered sequence of required deliverables. Complete every substantive manipulation (formula fixes, data transformations, value corrections) before applying any formatting changes. After reading the instruction, list each required change explicitly, then verify your output addresses every item before TASK_COMPLETE.
- **Dual-load inspection for error diagnosis:** Before fixing ANY cell that shows an error or unexpected result, load the workbook twice: `wb = openpyxl.load_workbook(path)` (formulas) and `wb_data = openpyxl.load_workbook(path, data_only=True)` (cached values). For the target cell and its precedents, print BOTH `formula=...` (from the formula load) and `cached_value=...` (from the data_only load) side by side. Diagnose WHY the formula fails (out-of-range index, circular reference, missing sheet) before writing any fix. Fix the underlying logic using the actual spreadsheet data — never hardcode a replacement value that merely matches the expected answer without understanding the computation.
- When calling tools (especially bash commands), pass ONLY the required parameters. For bash, provide exactly `command` and no other keys — extra keys like `description` cause tool‑parse errors and waste turns.

- **Broken formula replacement:** When you encounter a cell containing a formula that produces an error or incorrect result, do NOT leave a corrected formula in its place (unless the task explicitly asks for formulas). Instead, compute the intended value from the actual data (using cached/visible values from `data_only=True` load), then write that computed literal value into the cell. After writing, confirm the cell holds a concrete Python type (int, float, str), not a formula string.

- **Result, not code:** When a task says "create/code/macro/formula that does X" or "display the count/result in cell Y," compute the RESULT in Python and write the plain data value (number, string) to the target cell. Never place source code, VBA, or formulas in comments, separate sheets, or the cell itself unless the task explicitly says "provide the code" or "provide the Excel formula." After writing, verify `cell.value` is a plain data type (int, float, str), not a formula string or comment.
- **Actual data range, not sample range:** Before computing, inspect the EXACT data range named in the task instruction (e.g., "actual worksheet data range L26:SHA26"), not just the sample range shown in the task preview (e.g., A1:M1). Print values at the specified range coordinates and confirm you're operating on the range the grader will read. Sample ranges in previews may differ from the real data.

- **Dynamic array function trap:** Functions like UNIQUE, FILTER, SORT, SORTBY, SEQUENCE, and RANDARRAY will NEVER evaluate in openpyxl. If your Python logic would produce a formula string containing any of these function names, STOP — you are about to write a formula, not a value. Compute the result entirely in Python (use `set()` for unique, list comprehensions for filter, `sorted()` for sort) and write the final list/array as static values into the target cells. After writing, scan the answer range for any cell whose `.value` is a string starting with `=` — if found, rewrite immediately.
- **File existence gate (MANDATORY):** After ANY save/write operation, immediately verify the output file exists with `ls -la <output_path>` or `test -f <output_path>`. If the file is missing, retry the save — never proceed to verification or TASK_COMPLETE without a confirmed file on disk. This check must happen before any reload-for-verification step.

- **SUM/aggregation anti-pattern:** Never write `cell.value = f'=SUM(H{rr}:L{rr})'` or similar aggregation formula strings. The grader reads with `data_only=True` and will see `None`. Instead, compute the sum in Python: `cell.value = sum(ws.cell(row=rr, column=c).value for c in range(h_col, l_col+1))`. This applies to ALL aggregation functions (SUM, AVERAGE, COUNT, MIN, MAX, etc.) — compute them in Python and write the numeric result.

- **Source-data-first commitment:** Before writing ANY code that modifies the workbook, print the first 5 and last 5 values of EVERY source column referenced by the task. Then state: "Source data inspected. I will compute ALL results in Python and write static values (int/float/str/datetime). I will NOT write formula strings." This declaration must appear in your output before any write operation. Skipping this step is a proven failure pattern — agents who write formulas blind produce ungradable None outputs.
- **Aggregate inspection gate:** Before computing ANY sum, count, average, or other aggregation across rows, execute a separate inspection step that prints EVERY row of EVERY relevant sheet using `iter_rows` with `max_row` (not just the first N rows). Verbally confirm all data rows are visible and no values are unexpectedly None or non-numeric. Only then proceed to compute aggregates. This prevents missing rows, header offsets, and trailing empty rows from corrupting results.
- **Aggregate formula trap:** When computing sums, counts, averages, or other aggregates for answer cells, never write formula strings like `=SUM(C2:C4)`. The grader reads with `data_only=True` and will see `None`. Instead, compute the aggregate in Python (e.g., `sum(ws.cell(row=r, column=c).value for r in range(start, end+1))`) and write the numeric result directly. After saving, reload with `data_only=True` and verify every answer cell holds a concrete number (int or float), not None and not a formula string.
- **Inclusive range bounds:** When `answer_position` specifies a range like `E2:E154`, write to ALL rows from the start row through the end row inclusive (e.g., `range(2, 155)` in Python). Confirm the row count matches `end_row - start_row + 1` before saving.

- **Interpretation default — data manipulation, not formula design:** When a task describes searching, filtering, conditional lookups, or text matching across columns, default to a Python script with openpyxl that iterates rows and computes results programmatically. Only design Excel formulas if the task explicitly says "provide the Excel formula" or "write a formula." This script-based approach is proven reliable for ambiguous tasks and avoids formula-string failures.

- **Before/After pattern gate:** When the workbook contains a sheet named "After", "Expected", "Desired Results", or similar, inspect it BEFORE writing any output. Treat it as a functional spec: match whitespace, header treatment, and value placement exactly. After writing, reload the output workbook, print the answer range AND the reference sheet side-by-side, and confirm every cell matches before TASK_COMPLETE.
- **Pre-write structure inspection + row count gate:** Before writing any transformation logic, load the workbook and print: (a) all sheet names, (b) dimensions of the target sheet, (c) header row values for every column, and (d) a COUNT of rows that will be affected by your planned operation. State the count explicitly: "I expect to modify N rows." Do NOT proceed to write code until this inspection output is printed and the count is confirmed.
- **Post-save row recount gate:** After saving, reload the output workbook and iterate through all data rows to count how many actually contain the expected result. Print: "Verified: M out of N expected rows updated." If M ≠ N (the count from the pre-write inspection), halt, diagnose the discrepancy, and re-run — do NOT declare TASK_COMPLETE until the counts match.

- **Header-row preservation in answer ranges:** When the answer range starts at row 2 (e.g., H2:L4), the grader expects data values starting at row 2 — NOT column headers. Inspect row 1 before writing: if headers already exist there, leave them untouched and write data starting at row 2. Only write headers into the answer range if the task explicitly asks for them. After writing, reload and verify row 2 contains actual data values (dates, numbers, strings), not header text.

- **'Formula' wording trap:** When a task says "I need a formula that..." or "create a formula to..." but specifies an `answer_position` with cell ranges, the grader expects the COMPUTED RESULT (number/string), not the formula text. Only write formula strings if the task explicitly says "provide the Excel formula" or "write the formula itself." When in doubt, inspect any example values already present in the answer range — if they are plain numbers/strings, write computed values. After writing, reload with `data_only=True` and verify every answer cell holds a concrete value (int/float/str), not `None` and not a string starting with `=`.

## Inspection


- **Proven first action:** Before writing ANY code, load the workbook and print every sheet's name, dimensions, and ALL cell values (all rows, all columns) for every sheet. This single step is the most reliable way to understand column layout, data types, and pre-existing output-sheet content. Do NOT skip this — agents who inspect fully avoid column-mapping errors and silent overwrites.

- Load the workbook and print every sheet's name, dimensions, and ALL non-empty cell values with their row and column coordinates. Use `enumerate(ws.iter_rows(min_row=1, max_row=ws.max_row, max_col=ws.max_column, values_only=False), start=1)` and print each cell's coordinate and value. For very large sheets (>200 rows), print at minimum the header row and all rows in every data region referenced by the task. Never rely on truncated task‑description previews. Confirm the data matches expectations and note exact range boundaries before writing logic.
- Before modifying any workbook, load it twice: `wb = openpyxl.load_workbook(path)` and `wb_data = openpyxl.load_workbook(path, data_only=True)`. For the header row and target range, print every cell's `value`, `number_format`, `font`, `fill`, `border`, `alignment`, and any formula string. Confirm whether target cells contain formulas or constant values — do not overwrite formulas with values unless the task explicitly requires it.
- After inspecting headers and sample rows, form an explicit hypothesis: "What does this workbook already compute, and what is missing?" Print columns adjacent to the answer range and check for pre-existing formulas or partial computations. Compare what the sheet already contains against what the task asks you to produce. Your script must add only what is needed and must not duplicate or contradict existing structure.
- When searching a column for a value "above" a marker row, default to scanning from row 1 downward. Only scan upward from the marker if the spec says "closest" or "nearest." Print the found row and value for confirmation.
- When column positions may vary, scan the header row dynamically with a loop to find the target label. Validate the found column is not None before proceeding, and use `openpyxl.utils.get_column_letter` for logging or final checks.
- Before writing results, inspect any pre‑filled cells in the answer range. Use them to infer intended edge‑case behavior (e.g., False vs None for missing matches). Copy original answer‑range values before overwriting, then after writing loop through and compare each cell to its original; halt or correct if the pattern breaks.

- Before writing formulas that reference data ranges, always check `max_row` and `max_column` on the data sheet and use those exact bounds in every range reference (e.g., `$B$3:$B${max_row}`). Never hardcode a row bound from a partial printout.

- If the workbook contains a sheet that appears to show expected output (e.g., labeled with sort order or example results), read its full contents before acting. After producing output, compare a few key rows from your answer range against the corresponding rows in that expected sheet to verify ordering, values, and row count match. This catches ordering errors, duplications, and data loss before submission.
- Before writing conditional logic (IF, filtering, lookups), print the actual values and types of the target column cells you'll match against. Check for variants: prefixes, suffixes, whitespace, or case differences that would break an exact-match comparison. Design your matching logic to handle observed variants (substring containment, `.strip()`, `.lower()`, etc.). After writing, print the final values in the answer range to confirm all expected rows were updated.
- When operating on data tables, build a column-name-to-index map by scanning row 1: `col_map = {str(ws.cell(1, c).value).strip().lower(): c for c in range(1, ws.max_column + 1)}`. Normalize header strings (strip, lower) for robust matching. Raise a clear error if a required header is missing before proceeding.
- After extracting data into Python structures (lists, sets, dicts), print them alongside their source coordinates. Confirm the extracted values match the spreadsheet's actual content before using them in computations.
- Print `ws.max_row` and `ws.max_column` for every sheet, then iterate through all rows with `enumerate(ws.iter_rows(...), start=1)` so row coordinates are explicit. This prevents off-by-one errors when mapping data positions to output ranges.

- **Before ANY modification script:** Print at minimum the first 20 rows of every relevant sheet using `for row in ws.iter_rows(max_row=min(ws.max_row, 20), values_only=False): print([c.value for c in row])`. Confirm header positions, empty rows, and target value locations. Never assume the layout matches a truncated task-description preview or pre‑provided spreadsheet summary — summaries may misrepresent cell types, formats, or values (e.g., showing all values as strings when some are native datetime objects). Always inspect the actual workbook's cell values, types, and `number_format` in the target range before writing any solution. Only proceed to write modification code after this checkpoint is complete and the output confirms your assumptions.
- When printing sample rows, include column letters alongside values (e.g., `A: value, B: value`) to make header-to-column mapping explicit during inspection. This reduces errors when later referencing columns by letter in formulas or output ranges.

- **Expected-output sheets as answer keys:** If the workbook contains a sheet whose name or content suggests it shows expected output (e.g., "After", "Expected", "Manual Result", or a sorted/transformed version of the data), treat it as a partial answer key. Read its ENTIRE contents — every row and every column — before writing any code. Do NOT compute answers from first principles; instead, deduce the transformation rules (ordering, grouping, filtering, formulas) from the reference layout and reconstruct the output exactly.

- When source data is irregularly spaced or contains example output values, print ALL non-empty cells in the relevant columns (or a full row-by-row dump) to discover the exact pattern before mapping source rows to destination rows. ## Common Pitfalls


- **Lookup mismatch:** Before writing a lookup formula, print the lookup value and a few candidate match values from the target column side by side. Verify they share the same type and grain (e.g., both are strings, integers, or dates with identical components). If a direct match would fail, transform the lookup value or table values (extract month, trim spaces, cast types) before constructing the formula.
- Writing to a pre-existing sheet instead of the sheet named in `answer_position`. Always create or clear the exact sheet requested.
- Declaring TASK_COMPLETE without reading back the output file. Always verify first.

- **TASK_COMPLETE after `ls` only:** Do NOT declare TASK_COMPLETE after only confirming the file exists on disk (e.g., `ls -l`). You MUST reload the workbook with openpyxl, print every answer cell's value and type, and confirm correctness before calling TASK_COMPLETE. File existence \u2260 correct output.
- DO NOT delete or modify rows based on assumptions from a truncated preview. Always inspect the full dataset first.

- **Redundant recalculation:** Before computing a denominator or intermediate value, scan nearby cells for precomputed equivalents (sums, counts, totals). If the exact value already exists in a cell, reference that cell directly instead of duplicating the calculation with SUMIF/SUMIFS.

- **Weighted averages with conditions:** When a task requires a weighted average (weight column present) filtered by a condition column, use `SUMPRODUCT((condition_range=condition)*weight_range*value_range)/SUMPRODUCT((condition_range=condition)*weight_range)`. Confirm all three ranges align in size and start/end rows before writing the formula.

- **Multi-level sort corruption:** Never chain two in-place sorts on the same mutable list to achieve multi-level sorting. The second sort rearranges elements already grouped by the first level, causing duplicates and dropped rows. Instead, extract row data into tuples keyed by all sort columns (e.g., `(key1, key2, row_data)`) and sort once with a compound key. After writing, confirm the number of output data rows equals the number of input data rows and that no duplicate full-row tuples exist in the output range.
- **Bulk operations on wrong rows:** Before zeroing, clearing, or transforming a column, identify which rows are data rows versus header/metadata/label rows. Apply bulk operations ONLY to data rows. After writing, verify that non-data rows (headers, labels, blank separators) still contain their original values — scan for any string label that was overwritten with a numeric value.
- **Skipping zero cells during addition:** When adding/replenishing values, do NOT skip cells just because they currently contain zero. Zero cells are valid targets for addition. Only skip zero cells for subtraction/deduction operations. Before finalizing a conditional skip, ask: "If this cell is zero and the operation increases its value, should it be excluded?"
- **Sheet name mismatch:** Always print `wb.sheetnames` and use the exact string (including case) when accessing sheets. Never assume capitalization — `'Imported Data'` and `'imported Data'` are different keys.
- **Unnecessary normalization:** Before writing matching logic (e.g., `in`, `==`), inspect a sample of the actual data values to confirm exact casing, whitespace, and punctuation. Match against the literal keyword using the casing observed in the data unless the task explicitly requires case-insensitivity. Avoid blanket `.lower()` or `.strip()` calls that weren't requested and weren't validated against the data — they can inadvertently change matching semantics.
- **Column deletion index shift:** When deleting multiple columns, process them in reverse order (highest index first) to prevent index shifting. Use `reversed(sorted(cols_to_delete))` or iterate from `ws.max_column` downward.
- **Row insertion/deletion index shift:** When inserting or deleting multiple rows, always process in reverse order (highest row number first). For deletion: `for row in sorted(rows_to_delete, reverse=True): ws.delete_rows(row)`. For insertion: collect target rows, sort descending, then insert — this ensures each operation only shifts rows below the insertion point, leaving higher-numbered targets at their original positions. Before each operation, print the current row number and confirm the target cell still holds the expected value. The same principle applies when iterating with `range(ws.max_row, start_row-1, -1)` — always go highest to lowest.

- **Conditional overwrite guards:** When a task says to fill, replace, or update values in a column, write the new values unconditionally to every matching row. Do NOT add guards like `if cell.value in (None, '')` unless the task explicitly says "only fill empty cells" or "skip cells that already have data." After writing, read back the output cells to confirm they hold the new values, not the originals.

- **Rank/position lookup misinterpretation:** When a task says to find where a value appears among a set of reference columns and return its position (1st, 2nd, 3rd, 4th), produce a single numeric rank — NOT a comma-separated concatenation of all reference values. Before writing code, inspect one concrete example row from both the source and reference data to confirm the expected output format. If any duplication exists, include additional discriminating columns (such as date) in the composite key to guarantee a one-to-one match for every output row. Handle both `str` and `datetime` cases explicitly — parse strings with a known format using `strptime`. Never assume a cell's Python type matches its displayed format.
