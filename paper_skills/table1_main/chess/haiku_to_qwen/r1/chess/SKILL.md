## When NOT to Analyze: Fast Paths and Stopping Rules

Rules in this section license SKIPPING work: when a single cheap check
settles the position, when further verification cannot change the
decision, and when a line of analysis should be abandoned. Every entry
must name (a) the exact trigger that makes the shortcut safe and
(b) the condition under which the shortcut must NOT be taken. A rule
without both parts does not belong here.


- **Trigger:** a candidate move in the legal-moves list is already annotated with a check/mate symbol (+/#). **Shortcut:** treat that annotation as ground truth for the move's immediate effect — do not re-derive check/mate status via manual board reconstruction or repeated FEN re-parsing. **Do NOT skip when:** the annotation is absent, or when what's actually in question is a downstream consequence (e.g., whether the opponent has any legal reply) — verify that separately via tool output.

**Flagged mate shortcut:** If the legal-move list marks a move "#" (checkmate), make exactly ONE confirming tool call — `<safety>` or `<simulate>` on that exact move — and commit immediately with `<action>` once it reports no legal opponent reply. Writing "I will run safety(...)" or "let's use safety to confirm" does NOT count as this call — naming the tool without an actual tool tag appearing that same turn is zero tool calls, and committing `<action>` afterward on manual reasoning alone is the exact failure this rule exists to prevent. A mate-flagged move always outranks a non-mate alternative (e.g. a material-winning capture) — do not weigh it against them by piece value; only compare it against another move if that move is ALSO flagged "#", in which case either suffices. Do NOT manually trace diagonals, king-escape squares, or attacker/defender counts in prose to verify a flagged mate: that free-text re-derivation is the recurring failure mode (repeated self-doubt, incomplete enumeration followed by committing on faith anyway), and trusting the "#" label with zero tool calls is equally wrong. Do NOT call `<hanging>`, `<threats>`, `<board>`, or `<line>` in addition, and do NOT keep evaluating other candidates once the one tool call confirms mate. Exception: if the mate-marked move's own legality is ambiguous (e.g. pin or check status unclear from the list), verify that specific ambiguity with a tool before committing. Runtime tripwire: the instant you catch yourself re-parsing the same FEN/board a second time in one turn ("wait, let me recheck..."), OR repeating self-confirmation phrases like "Done. Proceed. Output matches." without a new tool call in between, stop — that loop is the known failure signature — and issue the confirming tool call immediately instead of continuing to narrate agreement with yourself.

**Once verified, one pass is final — do not re-audit for reassurance.** After a single pass has checked every standard failure mode for the claim (for mate: no legal block, no legal capture of the checking piece, no legal king escape), do not repeat that same check again under labels like "final check", "just to be sure", or "self-correction" — this restates identical facts and produces zero new information. If an urge to re-verify remains, it must point at a genuinely different failure mode you have not yet checked (a missed defender, a discovered check, a zwischenzug) — otherwise commit with `<action>` immediately.

Proven pattern worth keeping: alongside the one confirming tool call, a single quick manual pass naming the king's escape squares, capture options, and block options and why each fails (e.g. "e1/e2/g1 controlled, g2 blocked, capture still leaves check") is fine and not the banned behavior — the banned behavior is repeating that same derivation a second or third time in the same turn. When checking escape squares by hand, trace ALL of the checking piece's lines from its destination square (every rank/file/diagonal it now commands), not just the single line running to the king — a queen delivering check from a corner also rakes the rank and diagonal, covering escape squares a king-line-only check misses; missing this caused a real failure where a student wrongly doubted a correct "#" flag and burned a full turn re-deriving instead of calling a tool. Also: the king's own square never blocks the checking piece's line — a square beyond the king along the same rank/file/diagonal as the check is still attacked once the king would step there, since the king itself isn't a blocker for its own attacker. If your manual read says an escape square "looks unattacked" but contradicts a "#" flag, suspect this exact x-ray error first, and settle it with one `<board>`/`<safety>` call rather than re-deriving the same line a second time. Runtime tripwire: the instant you catch yourself re-parsing the same FEN/board a second time in one turn, or writing reassurance phrases like "wait, let me recheck," "just to be absolutely sure," or "double-checking, everything checks out" — stop, that loop is the known failure signature — and issue the confirming tool call immediately instead of a third manual pass. Recognizing a mate from the legal-move list annotation is a valid starting point, but it still requires the one confirming tool call before `<action>`; it does not license extra manual verification passes in its place.

- **Trigger:** your own square-by-square board reconstruction from the FEN contradicts a move that appears in the legal-moves list (e.g., you conclude a piece's path is blocked, but the list shows that move as legal, or marks it #/+). **Shortcut:** do not resolve the conflict by declaring "trust the list" (or "trust my own reading") in prose and moving on — call `<board>` or `<simulate>` with that exact move and let the tool's returned position settle which reading was wrong, then proceed from that observation. **Do NOT skip when:** your reconstruction and the list already agree — no extra tool call is needed in that case.

- **Trigger:** a capture in the legal-move list (e.g. "Rxc3", "Bxc3") looks geometrically impossible for the piece you believe occupies the source square. **Shortcut:** in 1-2 sentences, check whether it's simply a capture of an enemy piece that just moved onto that square (your mental model of "what's there" is stale, not the move list) — the "x" always means capturing whatever now stands on the destination, regardless of what stood there earlier. If that one check doesn't resolve it, call `<hanging>` or `<safety>` on the square immediately. **Do NOT skip when:** this is your second manual re-derivation of the same FEN in one turn — that is the failure signature (a real case burned an entire turn re-deriving the board dozens of times over an ordinary recapture and never called a tool); stop narrating and call a tool instead.
## Finding the Move: Motifs and Candidates



Before generating candidates, ground the search in the position's concrete features rather than a scattershot legal-move scan. In one sentence: (1) name the structural features for both sides — exposed king, passed pawns/majorities, active or vulnerable pieces, material imbalance; (2) classify the position as tactical melee, quiet, or endgame from king safety and piece activity; and (3) name the single concrete tactical driver (e.g. an advanced passed pawn, an exposed king, a hanging piece). In a tactical melee, treat any check or capture that plausibly strips the enemy king's shelter or interacts with the named driver as the primary candidate to verify first, not a fallback after quiet consolidating moves. Confirm the chosen move appears in the legal-move list and directly addresses the exposed king or hanging piece identified.


Before generating candidates, parse the FEN/board exactly once, rank by rank, cross-checking every piece against the printed board diagram and material line
 — and parse it fresh from the CURRENT turn's board every turn; never recall or re-derive piece placement from an earlier turn's FEN/board from memory, even one you parsed correctly minutes ago. Cross-turn memory drift (e.g. recalling a pawn as a bishop from an old FEN string) is a distinct failure from same-turn re-parsing — the once-per-turn rule means once per CURRENT position, always freshly read, never once-per-game-from-memory. — treat the diagram and any stated material total as ground truth, trusting them over hand-counting FEN characters on any disagreement, and flag the discrepancy before proceeding. Write the derived piece list once, correctly, on this first pass — do not reason forward from a guessed or half-checked placement while planning to "verify later"; a wrong first read (e.g. misplacing a king by a rank) that goes uncorrected can silently propagate into the final move. If a legality or protection argument seems to fail later, re-verify the square-by-square parse for that specific piece against the board printout, or call `<threats>`/`<hanging>` for a verified read, before concluding a move is illegal or unprotected.
 As part of this same first pass, cross-check the derived piece list against the legal-move list itself — e.g., confirm a capture you're about to consider actually appears there — so candidate generation starts from a verified position, not an assumed one.
 Also cross-check any perceived threat against your own king this same way: if you believe your king (or a key piece) is in check or under attack, but that attack is not reflected in the position's forcing context (e.g. it isn't a check per the board/legal-move list, or `<threats>` doesn't list it), treat this mismatch as a strong signal you misplaced a piece while parsing the FEN — stop and re-verify the FEN rank-by-rank, or call `<threats>`/`<board>` directly, rather than reasoning forward from the unconfirmed threat. Do this parse ONCE per turn: if you catch yourself re-reading the FEN "just to check" again in the same turn, or re-deriving piece placement rank-by-rank in a later turn, stop — the printed board/legal-move list is already correct — and spend the remaining effort on structural features and candidate verification instead. This also means not re-running full material arithmetic from scratch after every hypothetical capture line you consider in prose — trust the material line given with the observation once, and let simulate/board tools report updated material for any line you actually verify; repeatedly recomputing material totals by hand after each imagined sequence is the same failure as re-parsing the FEN and burns the same budget. **Trigger:** if you state two different contents for the same square within one turn (e.g. relocating a queen, inventing a pawn that isn't there), that is the failure signature — stop immediately, reread the original board diagram/material line once, and proceed; do not restart the derivation from scratch a second or third time.

Call a tool that reports your own side's en-prise pieces and the opponent's top forcing replies (`<threats>`, `<hanging>`, or equivalent) once, early in the turn, before generating candidates — do this even when the position looks quiet.


**Check what the opponent's last move just hung, first.** Before broader candidate generation, look at the piece the opponent's last move just moved or captured with (e.g. "Last move: Bxc5") and count attackers vs. defenders on that square from the legal-move/capture list. A check or capture landing on that square with zero defenders is a top-priority candidate — verify and commit to it rather than spending further turns re-parsing the FEN or re-deriving board state from scratch. Also tally material balance for both sides at this same point; this baseline catches candidates that leave a piece en prise and flags FEN-misreading early. If the tool flags one of your own pieces as en prise and you can't immediately name the attacker from memory, treat that as a signal your mental board is wrong: re-derive piece placement from the FEN/printed board before proceeding, rather than dismissing the result.

**Order matters: defense scan before offense scan.** Before hunting for your own attacking ideas (sacrifices, pawn breaks, tactical shots), first list every one of your own pieces and state for each whether an enemy piece currently attacks it and whether it is defended. This is a distinct pass from scanning for your attacking chances — a piece hanging to the opponent overrides speculative attacking plans and must be addressed (moved, defended, or outweighed by a bigger threat) before any sacrifice or breakthrough idea is seriously considered. Skipping straight to "what can I attack with" while an own piece sits en prise is a recurring failure mode.

Also check specifically whether the opponent's last move created a new threat against one of your own pieces (especially the queen) — a newly opened diagonal/file/discovered attack often isn't caught by a generic hanging-piece scan alone. If such a threat exists, narrow candidates to moves that move/defend the threatened piece or create a bigger counter-threat, rather than defaulting to a quiet developing move. **Proven check:** call `<threats>` (or read the "forcing replies" field on a `<safety>` result) and ask explicitly — does it list a capture of my queen/rook? If so, that overrides any slower improving-move plan; your candidate must capture, block, or move the attacked piece before anything else is considered.

If the side to move is in check (or the legal-move list is restricted to king moves/blocks/captures of the checking piece), first filter candidates to only those that actually resolve the check, verifying each eliminates it, before evaluating any of them for tactical or positional merit. Among the surviving replies, do not stop at "this escapes check" — compare each for material and hanging pieces: a king move that dodges check can still leave a piece en prise, while capturing the checking piece may both resolve check and win material. Prefer the capturing reply when it recaptures the checking piece and no tool flags it as unsafe.

Otherwise, scan the full legal-move list and classify each move as check / capture / threat-creating (including moves that attack a piece the opponent just left en prise) / other, making this classification visible in the reasoning trail before using `<action>`.

**Ordering failure to avoid:** never analyze one candidate fully in prose, verify it, then repeat that cycle for the next candidate — this wastes turns and lets a false premise (e.g. wrongly assuming a move gives check) go unchecked through pages of analysis before a tool corrects it. The instant you have 2+ plausible checks/captures/threats from the legal-move list, submit them together in ONE `<safety>` call (e.g. `<safety>Re4+, c2, Rxd4</safety>`) before writing extended prose on any single one, then spend reasoning only on the survivors.
 Do this even when one or two other moves (a big capture, a passed-pawn push) visually jump out first — a salient-looking capture does not excuse skipping the forcing-move pass; write out every move ending in "+" or containing "x" from the printed list as its own short line before analyzing any candidate in depth. Treat every check, capture, and en-prise-attacking move as a mandatory first candidate and evaluate it — at least the top one via `<board>`/`<safety>`/`<simulate>` — explicitly ruling it out on threat-generation grounds (never vague preference or positional bias) before settling on a quieter move. Concretely: first list every move in the legal-move list ending in "+" or "x" (plus any move attacking an en-prise piece) as the initial candidate pool, and only broaden to quiet moves once none of those forcing candidates survives a tool check. Once you state that a move is best, emit exactly one `<action>` tag for it in that same turn — do not keep hedging or re-justifying a conclusion you've already reached.


When material is down or the opponent king looks constrained, list every check and capture from the legal-move list first and evaluate them as a group before any quiet move — verify your first few candidates in the trace are drawn from that checks/captures subset, not king or pawn moves. When the enemy king has few escape squares and the legal-move list contains multiple checking moves, explicitly list all of them before picking one — do not settle on the first check found or default to a quiet move; in sharp positions with an exposed king, the checking-move pool is the right first place to search, not an afterthought to a positional plan. Runtime check: before generating candidates in any position where the enemy king has reduced pawn cover or few escape squares, explicitly ask "which legal moves are checks or captures near the enemy king?" and make your first tool call (`<threats>`/`<safety>` on that shortlist) target one of those, not a quiet developing move. Proven pattern: enumerate the FULL set of checking moves from the legal-move list first (not just the first one found), since a small forced-reply set across multiple checks is itself a signal of a converting sequence — then verify the most promising one with a tool. Building that shortlist by manual scan (e.g. spotting Qf6+/Qg5+/Rg8+ by eye) is correct and worth keeping — but the shortlist alone is not a decision: it is only complete once `<simulate>` or `<line>` has verified the strongest candidate actually holds up, not merely assumed from the mental image.


If several turns pass without finding a forcing win, re-scan the CURRENT legal-move list for checks and captures again — do not keep working from a candidate pool built on an earlier turn's scan, and do not let the pool silently shrink to only the captures already considered. A check or forcing rook/queen lift sitting in the legal-move list every turn but never evaluated is a hard error, not a matter of taste.

Runtime check: before ranking candidates, tag every legal move that is a check or a capture and treat that tagged subset as your primary candidate pool — this filter is correct even in sprawling positions with many legal moves; the recurring gap is not identifying the pool but failing to verify each member with a tool before ranking.

If a check or capture appears to "lose material" to an immediate recapture, do not discard it from that single-ply snapshot alone: run `<line>` on the check-then-recapture sequence to see the position two plies deeper before rejecting it. A check that looks like it hands over a queen can still be the start of a forced mate once the recapture itself is forced — the forcing-reply tools exist precisely to catch this, and static one-ply judgment misses it. Do not stop at "this trades evenly" either: after `<simulate>`/`<line>` shows the forced reply, ask whether the resulting position creates a NEW tactic (fork, skewer, second check, newly undefended piece) — a check that looks like a plain trade at ply 1 can set up a winning shot at ply 2.


On the opening move of a puzzle, keep freeform analysis compact: name the position's structural theme and the one or two candidate forcing moves it suggests in a few sentences, then verify the strongest candidate with a tool call — do not hand-calculate multi-move mating nets or deep capture sequences before any tool call. Check: if a hand-calculated line goes deeper than 2-3 plies before touching a tool, stop and switch to `<simulate>`/`<line>` — deep manual calculation on the first move is also where illegal-move and wrong-diagonal errors creep in.


When `<hanging>`/`<threats>` output shows an undefended piece on BOTH sides (mutual hanging pieces, e.g. both queens exposed), treat that mutual exposure as the position's central tactical feature and generate candidates around capturing/defending it first, before considering other motifs.


**Confirmed habit — keep doing this:** starting every turn with one `<hanging>` call before any candidate generation is a proven, low-cost first action that catches en-prise pieces on both sides early — retain it even in quiet-looking positions. Treat an empty "your side en prise" result as a green light: proceed straight to attacking-candidate generation instead of re-checking defense. Pair this list with the printed material count as your baseline: for any capture candidate, recompute the exact point swing (attacker value minus defender value) against that baseline before deciding it's a genuine gain, rather than judging it qualitatively as "wins material."


**Proven opening sequence:** at the very start of a turn, call `<hanging>` once for an objective inventory of loose pieces on both sides, then call `<safety>` in a single batched call listing every candidate check/capture together (e.g. `<safety>Qxh2+, Qc6+, Qd5+</safety>`) and read the attacker/defender counts directly from that one call rather than hand-deriving them per-candidate. If you catch yourself manually judging a piece as "hanging"/"defended" through repeated self-doubt ("wait, is it really hanging?"), that is the trigger to run `<hanging>` instead — its list overrides your own read on conflict. Whenever a hanging-piece capture found this way competes with any check in the legal-move list, don't default to the capture: batch both into the same `<safety>` call and pick only after comparing attacker/defender counts and forcing-reply fields (a check with zero forcing replies can beat a capture that merely trades evenly).

If a move you are considering does not appear verbatim in the legal-moves list, discard it immediately and do not analyze it further. Before trusting any hand-calculated capture/recapture sequence more than one ply deep, call `<simulate>` instead of manually re-deriving defenders and redoing material arithmetic — a sequence you re-derive twice with two different conclusions is the exact failure signature this replaces. **Runtime check on the scan itself:** count how many distinct candidates you consider in prose before the first tool call confirming a concrete gain; past 2-3, the scan has become unstructured trial-and-error — stop, re-order the legal-move list into checks/captures/threats, and tool-verify the top of that list instead of continuing to freehand through quiet moves.

Runtime check tied to the candidate itself: once you settle on a leading candidate, confirm the squares its own piece and target occupy in your derived piece list match the same squares in the printed board diagram before verifying it further — this catches the transcription errors that free-text FEN parsing otherwise misses.


For any pawn one move from promotion, test each promotion choice against the enemy king's rank/file/diagonal before ruling it non-forcing — a promoted piece can deliver a long-range check via a newly opened line even when the move doesn't look like a capture or a direct advance toward the king. Verify with `<safety>` on the promotion move (e.g. `<safety>g1=Q+</safety>`) rather than hand-tracing the diagonal.

**Proven fast candidate-find:** when scanning the legal-move list, immediately flag any check, or any capture where the target has fewer defenders than attackers, as the first candidate to verify with a tool before probing quiet moves. For each flagged candidate, also state in one line the concrete follow-up it creates — what recapture becomes available, or what discovery it opens (e.g. a check that clears a file/diagonal onto an undefended piece) — before discarding or keeping it; a discovered-attack idea is often only visible once you ask what the moving piece uncovers.


**After any forcing move that moves the enemy king (or its defender), re-check for newly hanging pieces.** A king or defender dragged off its square can leave another piece undefended that was safe before. After committing mentally to a check/capture, ask "did this specific move undefend anything by moving the king/defender away?" and confirm with `<hanging>` in the resulting position — do not rely on the pre-move `<hanging>` read, and do not get absorbed hunting for deep mating nets while skipping this one-ply follow-up check.


**Fork/double-attack priority:** when scanning the legal-move list, specifically flag any check or capture that geometrically lands next to or attacks TWO enemy pieces at once (a fork) — this outranks a capture/check that merely trades evenly or loses material, so test it with `<safety>`/`<threats>` before spending a tool call on a lesser candidate (e.g. a knight-for-pawn trade) that was only tried out of uncertainty. Once such a fork is identified from the move list, do not hand-derive which squares/pieces it attacks or whether the destination is defended by counting diagonals/knight-geometry in prose — call `<threats>` or `<safety>` on that exact move immediately and read the attacker/defender/forking-target fields directly; reserve manual geometry reasoning for candidates no tool has yet answered.

**Confirmed habit:** when the enemy king is exposed — few defenders, open lines, or a weakened diagonal/file near it (e.g. a fianchetto pawn pushed or traded off) — the checks/captures scan above is validated as the correct first step. Before moving to verification, confirm in one line that at least one shortlisted candidate targets the opponent's least-defended piece, the king itself, or opens a line toward it; do not let material-grabbing captures elsewhere on the board crowd out this shortlist.
## Verifying the Move: Tool Ritual


Treat the printed legal-move list as ground truth: if a move appears there, don't question whether it's "really" legal — investigate its effect with a tool instead of re-deriving the board by hand.


**Immediate-tool-on-sight for forcing candidates:** the moment a check, capture, or mate-looking move appears on the legal-move list, call `<safety>`/`<simulate>` on it as your very first action — do not spend sentences or turns hand-calculating multi-move sequences, blocking pieces, or diagonals first. Re-deriving the same block/defender logic more than once before the first tool call of the turn is the exact failure signature (talking yourself into and out of the same conclusion repeatedly); when manual tracking disagrees with a tool's attacker/defender/en-prise count, the tool is right. Use free-text reasoning only to pick which candidate to test next, never to compute consequences a tool already verifies.


**Call a tool before any manual attacked/defended-square derivation, not after.** Before writing even one sentence like "does X attack square Y" or tracing a diagonal/file by hand, make your first tool call of the turn (`<threats>` or `<hanging>`) to get a verified read of what's attacked and hanging. Manual square arithmetic is only for interpreting or extending a tool's output, never a substitute for calling it — if several lines pass with no tool call yet, stop and call one now.


**Tool call comes before manual reasoning, not after.** As soon as you have 2-3 real candidates, call `<safety>` on all of them in one batched call BEFORE writing out square-control arithmetic, stalemate-trap worries, or attacker/defender counts in prose. Runtime check: if you catch yourself counting "does X attack square Y" in prose for more than one candidate without having called a tool yet, stop mid-reasoning and issue the `<safety>` call now.

Before asserting that a move gives check, is legal, or forces a specific reply, call `<safety>` on that exact candidate and quote its "gives check" / "forcing replies" fields directly — never assert these from mental visualization.
 This applies to every move in a self-generated multi-move line, not just the first: if you extend a hand-traced sequence ("...Rxe4 c2 Re2 b3 Rxc2...") past a claim you have not yet tool-checked, stop at that claim and verify it before adding the next move — a single tool check on move one does not license unverified extensions on moves two through five. Runtime check: if your reasoning contains a claim like "this is check" or "X is forced" that is not a verbatim quote from a tool's output field, stop and issue that tool call before continuing.

When unsure whether a candidate gives check or is even legal, do not walk diagonals/files from the FEN to settle it — call `<safety>` on it (or attempt it) and read the result directly: a legality error or a "gives check: no" answers the question outright. Trust that verdict and immediately move to the next candidate; do not re-derive the board a second time to double-check a tool's answer.

**Overloaded-defender trigger:** if multiple candidate targets are all defended by the same single piece, do not hand-count attackers/defenders for each target in prose — call `<hanging>` or `<safety>` on your top 1-2 candidates and let that output settle which target is actually winnable. Re-deriving the same defender count more than once for the same square is the failure signature — stop and call the tool instead. For any candidate whose payoff depends on a forced 3+ ply exchange sequence, run `<simulate>` on it rather than hand-tracing the captures and totaling material yourself. Never re-derive piece placement, square colors, diagonals, or attacker/defender reachability by hand in prose — this is the recurring source of self-contradictory conclusions (e.g. computing "king cannot reach d3" once and "king can reach d3" later from the same position). Confirm any doubted square, any line running more than one ply deep, or any "defended/undefended" claim with `<board>`, `<safety>`, or `<simulate>`; reserve free-text reasoning for strategic comparison, not for re-verifying geometry the tools already check.

Before committing any capture or check justified by an "undefended/safe square" claim, that claim must come from `<safety>`/`<hanging>`/`<threats>` output, not from eyeballing the board — manual defender-counting is a self-verification method with no external check and is exactly where miscounts (missed pin, missed defender) slip through undetected. Runtime check: if your final move's justification cites who attacks/defends a square and that fact was derived only in prose, stop and call the relevant tool on this exact move before `<action>`.

Run `<safety>` on every candidate check or capture before investing budget in deeper analysis. If it flags your own piece as en prise with no offsetting factor, or shows a favorable capture/forcing reply for the opponent on the destination square, discard that candidate immediately and move to the next one — no further hand-calculation needed to confirm a clear en-prise result. Do not proceed to `<simulate>` on a candidate that fails this screen. For a candidate that passes, run `<simulate>` and commit only once tool output — not mental calculation alone — supports the move, and only if that output came from a tool call made in the CURRENT position; discard and re-run if it is from an earlier turn or a prior version of the position.

**Banking a capture:** before treating any capture as won material, read both the destination-square attacker/defender count AND the explicit "en prise after the move"/"forcing replies" fields from that exact move's `<safety>`/`<simulate>` call — a mental read of "looks undefended" is not sufficient confirmation on its own. Read the "your pieces en prise after the move" field for the WHOLE board, not just the piece you moved or captured with: a quiet-looking "natural" capture that leaves some OTHER piece hanging elsewhere (e.g. an undefended knight left loose earlier in the game) is exactly what this field catches and hand-calculation misses — treat any piece listed there as a hard veto on that candidate unless outweighed by a bigger gain.

Never hand-calculate capture sequences or material counts in prose for more than one line. If hand-calculating a line produces contradictory material counts more than once, STOP: discard the hand-calculation and re-verify the simplest forcing candidate with a tool call instead of continuing free-text arithmetic. Before committing to any capture whose soundness depends on whether the target square or a piece is defended, call `<safety>` or `<simulate>` on that exact move rather than re-deriving defenders from the FEN by hand. Runtime check: if you re-derive which piece defends a square more than once in the same puzzle, or your own tracked piece locations disagree between turns, stop and get the tool's answer instead of a third manual pass. Repeated self-doubt about square control ('wait, is that really defended?') is itself the trigger to call `<safety>`/`<board>` — do not resolve the doubt by decoding the same FEN rank a second or third time, and do not fall back on trusting a +/# annotation as substitute evidence for a square-safety question the tool can answer directly. Before committing to a forcing move (check, capture, threat), verify at least one concrete opponent reply with `<line>` or `<board>` — do not commit by elimination alone ("everything else loses material, so this must work"). If line-verification errors out or budget is low, state explicitly that the follow-up is unverified rather than asserting confidence.


**Gate before committing:** if a candidate looks like an immediate win (mate, big capture, forced sequence), do not resolve it via internal monologue or hand-derived FEN/board tracing, even briefly — call `<safety>`, `<simulate>`, or `<board>` on that exact move and base the decision on its returned verdict. Self-check before emitting `<action>`: was the immediately preceding step a tool call on this same move whose output you read and referenced? If not, call the tool first — do not commit on self-derived reasoning alone, no matter how confident. Merely mentioning or intending to call a tool does not count — if the turn ends without an actual tool-result observation for that exact move in the current position, do not emit `<action>`; if budget is running low, spend the remaining turn making that one call rather than finishing a mental derivation.


**Say-it-do-it / narrated-intent trap:** a draft sentence like "let's use `<safety>` to check," "let me verify with `<simulate>`," or "I will call the tool" is a commitment, not a substitute for one. Scan your draft before sending: any sentence naming a tool you "will" call must be followed, that same turn, by the actual tool tag with real move arguments and a read result — never let a stated or narrated intention to verify replace the verification itself. **Watch specifically for the self-reversal variant:** proposing a tool call and then talking yourself out of it with confidence language ("Actually, I'm very confident it's mate... no need to overcomplicate") is the same failure wearing different words — if you catch yourself dismissing your own stated plan to verify, that dismissal is the trigger to make the call, not skip it. A tool's structured output (e.g. `<board>`'s explicit "your side en prise: [...]" field) catches silent miscounts — a missed defender, a misread attacked square — that a purely self-authored prose mate-check cannot, no matter how many times you repeat the same manual king-escape enumeration.

**Isolate the tool tag — do not bury it in prose.** When a turn's purpose is to call a tool, keep the reply minimal: a short lead-in (if any) plus the tag itself, never a large "(reasoning)... ## Comparing Candidates

When two or more candidates both look promising, gather the same
evidence for each (one <safety> block, one batched <simulate> against

sufficient-looking move.

**Proven breadth-first habit:** before narrowing to one candidate for tool-testing, name at least 2-3 distinct legal moves from the list (prioritizing checks, captures, pawn breaks) and state in one phrase what each threatens or risks. Runtime check: confirm your reasoning names ≥2 distinct candidates before you narrow to the one you test/commit — fixating on the first idea that looks plausible is a recurring miss even when that first idea turns out fine.

Gather the same concrete evidence for each (one <board> or <safety> call, one batched <simulate> against its testing replies) and choose by comparing that tool output, never by re-deriving outcomes longhand or committing the first sufficient-looking move. If any check is available in the legal-move list, include it in this shortlist alongside an apparently-winning capture even when the capture looks decisive — a single-candidate search is a recurring failure mode; compare at least two forcing options via one shared `<safety>` call before picking.

Before the final `<action>` on any capture or check, name at least one plausible alternative capture/check and state in one sentence why it's inferior (using tool-reported material/safety data, e.g. "wins a pawn only, vs. this move which wins an undefended piece") — do not commit to the first legal capture found without this comparison.


**Once-per-candidate cap:** before re-analyzing any candidate, check whether you already reached a verdict on it earlier in this turn — if so, do not restate or re-derive that analysis. Evaluate each distinct candidate at most once per turn (winning / refuted / unclear); looping back through already-rejected candidates is the known failure signature that ends in an arbitrary guess. Once every serious candidate has a verdict, commit to the best-verified one immediately.


In a simplified or endgame position where you already hold or are gaining a material edge, prefer a safety-verified free capture (e.g. an undefended pawn) over a more speculative maneuvering plan — run `<safety>` on that capture first to confirm the target is truly unguarded, then take it rather than searching for a fancier continuation.


This comparison discipline is not limited to checks/captures: in pawn-structure or breakthrough decisions with more than one plausible pawn-break candidate, explicitly name and compare at least two of them (e.g. one `<safety>` call per candidate) before committing — do not stop at the first push that "looks obviously right." Do not resolve the final comparison by hand-tracing multiple king-move branches in prose, especially once two mental lines start contradicting each other — that contradiction is the trigger to call `<simulate>`/`<board>` on the branch instead of re-deriving it a third time.

If the fresh call flags it as losing material or unsound, drop it and pick a different candidate from the current legal-move list — a plan formed before the opponent's actual reply is not verified for the position that now exists.


**No prefixed labels, no bare tool names, inside `<action>`:** do not wrap the final move in narrative scaffolding like "(final) PLAN: ..." before the tag — output the concluding sentence (if any), then the bare `<action>Move</action>` tag with nothing else on that line, containing a move copied verbatim from the legal-move list. A bare word like "safety" or a tool name inside `<action>`, or a move buried inside prose framing, can be read by the harness as containing no valid move — silently burning the turn even though a move was clearly intended.

**Never splice two tag names together.** After a rejected/malformed reply (e.g. a no-tag turn or a '(final)'-wrapped block), the fix is to resend ONE clean tag — never merge the action and a tool name into one broken tag like `<action>safety>Kxd5</action>`. Before sending, check the opening tag's content between `<` and `>`: it must be exactly one known tag name (`action`, `safety`, `simulate`, `board`, `threats`, `hanging`, or `line`) and nothing else — not two names concatenated, not a name plus a move. A prior parse failure is a formatting bug to fix with a single valid tag, not license to invent new tag syntax.

**Final recapture check (last step before `<action>`):** for the exact move you are about to commit, confirm which enemy pieces — including the king — could recapture or reply on the destination square, and whether that reply nets material for the opponent. Default to a `<safety>` call on the move itself for this check rather than manually enumerating every enemy piece/pawn's reach to the square in prose — manual enumeration can reach the right answer but is convincing-but-fallible and burns budget; reserve prose enumeration for cases where a tool call errored out. A move that passed earlier `<safety>` screening still needs this destination-square check as the final gate.

Before writing `<action>`, re-read your own most recent verdict on that exact move. If you previously labeled it inferior, drawn, or losing material, do NOT play it — either pick the candidate whose last verdict was positive, or call a tool to break the tie. Committing to a move your own analysis just rejected is a hard error. This applies even if the move still "feels" like the most forcing or logical option — a self-identified losing continuation (mental or tool-based) overrides any feeling of forcingness; drop the candidate and check the next-most-forcing legal move instead. Once a move is settled (including a confirmed mate), the very next output must be exactly one `<action>` tag for it — no restated reasoning, no hedging, nothing after the closing tag.

**Final self-contradiction scan (mandatory, zero-cost):** immediately before emitting `<action>`, re-read your own turn's text near the move string you're about to submit, and the last sentence of reasoning about it. If either contains "blunder," "loses," "hangs," "doesn't work," "doesn't win," "isn't actually check," "down material," "down a piece/pawn," or any similar admission that the line fails — do not submit that move anyway out of exhaustion or because it's "the most straightforward option." This applies even when your own prose already named the specific defender/recapture that causes the loss (e.g. "Bc3 is defended by Qc7, so this loses material") — a self-identified material loss is a stop signal, not a footnote; discard the candidate and pick the next one, or run one fresh `<safety>`/`<simulate>` call, instead of committing to a move your own immediately-preceding analysis just refuted.


**Resubmission after a parse/format failure is not a new turn to re-decide:** if the system reports no move was received (e.g. because trailing text like "(final)" or a "(final)" narrative block broke tag parsing), do not restart analysis from scratch and do not let the conclusion drift over subsequent turns. Re-issue `<action>MOVE</action>` for the SAME move you already verified, bare and alone, with nothing before or after the tag — a parse failure is a formatting bug, not evidence against the move. Only switch to a different move if a tool call made in the current position actually refutes the original one; never silently downgrade to a candidate your own prior analysis already called inferior, and never let two or more turns pass re-litigating already-settled candidates instead of just resending the tag.

**Legal-list confirmation before every `<action>`:** whenever a new position/legal-move list is printed after your move and the opponent's reply, re-read that actual list and confirm your intended continuation is present in it verbatim — including checking each king escape square or defender against the new board when the move is a check/mate — before committing. Do not assume a previously-calculated line still applies to the new list without this check.


**Do not abandon a self-verified winning line to re-litigate a side question.** If you have already worked out, with tool confirmation, that a forcing move (check/capture) followed by a specific opponent reply wins material or mates, lock that plan in — do not drift into re-debating an unrelated point (e.g. whether a different king move is also legal) and end up on a new, unverified candidate as a result. Each new candidate considered after a line is already priced needs its own fresh tool call, not a fresh hand-analysis of the whole board; if the priced line still holds, play it.
## Budget Discipline


- Do not spend reasoning turns re-verifying facts already given directly by the observation (e.g., a +/# suffix on a legal move, or a tool's stated result). Redirect that budget to confirming consequences the environment hasn't yet shown you.


- Do not repeatedly recount material or re-parse the FEN by hand between tool calls; trust the material/position line printed with each observation, verify it once, and route remaining doubt into a tool call instead of freehand recomputation.
- Run `<simulate>` on your top 1-2 candidates by the middle of your budget, not on the final call — reaching `<simulate>` only at the last available query leaves no room to compare an alternative if that simulation is inconclusive.
- Minimum-tool-call floor: never end a turn with `<action>` on a check, capture, or multi-piece tactical choice if zero tool calls were made this turn. If you notice you have reasoned entirely in prose and are about to commit, stop and make one targeted tool call on your top candidate before `<action>`.

- After 1-2 `<safety>` calls narrow to the most promising forcing candidate and immediately run `<line>` to walk that sequence to its terminal tool-reported status (checkmate, material change, or "no check") before the turn ends — never let a turn's final output be a bare tool call or tool name with no plan.
- Deciding a tool call is needed is not the same as making it: if your draft says "I will call `<safety>`", "let's use the safety tool", or similar, that same turn must contain the actual tool tag with real move arguments — never end a turn having only narrated the intention and then jump straight to `<action>` on unaided mental calculation. Before every `<action>` on a check/capture, count this turn's actual tool calls; if the count is zero and budget remains, that is a hard stop — issue one `<safety>`/`<simulate>` on the top candidate first.

- **Cross-turn tool-call floor:** if a full turn ends with zero tool calls (pure prose/manual FEN-parsing or arithmetic), the very next turn's first output must be an actual tool call before any further narration — do not let manual re-parsing or hand-calculated candidate lines span two or more turns with no tool tag issued. Re-parsing the same unchanged FEN/board in a second turn is itself the failure signature: treat the first turn's parse as final and spend every subsequent turn on tool-verified candidate checking.

- Minimum-tool-call floor: never end ANY turn with `<action>` if zero tool calls were made this turn — this applies to quiet pawn/piece moves too, not just checks/captures/multi-piece choices. If you notice you have reasoned entirely in prose and are about to commit, stop and make one targeted tool call (`<simulate>` or `<line>` on your top 1-2 candidates, checking the opponent's most testing reply) before `<action>`.
- **Do not commit from recalled pattern-memory.** A thought like "I recall this exact endgame pattern" or "this is the standard/book move here" is not verification — it is a guess dressed as recognition. If you catch yourself re-deriving the same board fact three or more times, or writing "I'm not sure"/"let me trust memory," treat that self-doubt as the trigger to call `<simulate>`/`<line>` on your top candidate rather than committing from recollection.
- **Hard commit threshold:** if you have made 3-4 tool calls on a single move-decision and still have not emitted `<action>`, stop opening new candidates. Commit immediately to the best tool-verified candidate found so far rather than pivoting to a newly-noticed move with no tool call refuting the one already priced as winning — ending the turn with only a tool call and no `<action>` is a hard failure.
- Running out of budget is never a reason to play a move you just judged as losing. If your own most recent reasoning or tool result on the candidate you're about to submit contains a losing verdict (terrible, loses, bad), do not submit it anyway with a rationalization like "most active option." Instead, scan every candidate already audited this turn and play whichever one's last tool result was neutral-or-better, rather than a fresh unverified move or one you yourself just refuted.


- **Per-turn structure check:** before ending any turn, confirm it contains exactly one tool tag or exactly one `<action>` tag — never zero of both. A turn consisting entirely of prose (manual FEN/board re-derivation, hand-traced variations, ASCII diagrams) with no tool call and no action tag is a hard failure, not a "thinking turn" — stop mid-reasoning and issue a tool call the moment you notice no tag has been emitted yet.


- **Do not re-type the same comparison across turns with no tag.** If a system reminder says a prior turn contained no tool tag and no move, the very next output must be a single tool tag or `<action>` tag with nothing else — restating or lightly rephrasing the same candidate analysis a second time without emitting a tag is a hard failure, not extra thinking room. Two consecutive turns of prose-only output on the same decision is itself the signal to stop narrating and commit to whichever candidate already has the best tool-verified result.
## Common Pitfalls


- Abandoning a verified strong capture/check for a self-calculated "improvement" that was never confirmed by a tool, especially after the hand-calculation already contradicted itself.
- Trusting long free-text geometry/arithmetic over a tool result or over a simple forcing move already identified and priced.

- Proven pattern (confirmed across multiple traces): once a final move is stated with supporting evidence, emit exactly one `<action>` tag immediately and stop — no restated conclusions, alternate lines, or hedging after it. Runtime check: the turn's last two outputs should be the concluding sentence, then the `<action>` tag — nothing between or after.


- Ending a turn with a tool call mislabeled or narrated as "(final)" instead of an actual `<action>` tag — a tool call, however confident-sounding, never substitutes for the required `<action>` tag; the turn is incomplete without it.
