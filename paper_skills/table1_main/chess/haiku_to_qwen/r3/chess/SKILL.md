## When NOT to Analyze: Fast Paths and Stopping Rules

Rules in this section license SKIPPING work: when a single cheap check
settles the position, when further verification cannot change the
decision, and when a line of analysis should be abandoned. Every entry
must name (a) the exact trigger that makes the shortcut safe and
(b) the condition under which the shortcut must NOT be taken. A rule
without both parts does not belong here.

- Trigger: the mating/tactical idea's supporting facts (king can't escape, no capture or block available) have already been stated once and confirmed. Shortcut: stop re-verifying and commit to the move. Do NOT take this shortcut if the first check was itself based on a hand-parsed FEN that hasn't been cross-checked against the printed board/legal-move list.
## Finding the Move: Motifs and Candidates


Before parsing the FEN, state in one sentence the position's dominant structural theme and the opponent's most exposed piece/king-safety issue (e.g., passed pawn vs. exposed king, back-rank weakness, pinned piece, overloaded piece) — then generate checks and captures that engage that theme first. This cheap framing step reliably narrows the legal-move list to the few moves worth calculating; verify every later candidate plausibly interacts with the named theme before choosing among them, and revisit the theme if none do.


Treat the printed board, FEN, and legal-move list as ground truth for piece placement and legality — do not hand-derive squares or legality from the raw FEN or from memory of an earlier turn.

Runtime check before writing any manual square/defender-counting paragraph: "have I already called a tool this turn that would answer this?" If a `<hanging>`/`<safety>` call already returned an answer (e.g. "en prise after the move"), use that result directly — do not re-derive the same defender/attacker fact by hand afterward as if the call hadn't happened; this exact pattern (call a tool, then ignore its output and keep hand-calculating) is a proven repeat failure.
 Parse the FEN/board into a piece list exactly once per turn; if a square needs rechecking, do it briefly, not by re-deriving the whole position again.

Runtime check while parsing the board: if you state two different pieces (or piece vs. empty) for the SAME square anywhere in your own reasoning (e.g. "e8 is a rook, wait, e8 is empty"), that contradiction is proof your board model is unreliable — stop narrating uncertainty, re-verify that square once with `<board>`/`<safety>`, and do not proceed to candidate generation until it is resolved. Do not resolve it by re-reading the FEN string again in the same error-prone way that produced the contradiction.


Never let a claimed memory of a "known puzzle" or "famous pattern" ("I recall the solution is X") override a candidate you have already priced out concretely from the CURRENT position. If a recalled pattern conflicts with a move you've already calculated to win material or force a good outcome, treat the recollection as unverified: run `<simulate>`/`<line>` on the recalled move before switching to it, and if you cannot verify it, keep the move you already confirmed wins. Before generating any candidates, parse the FEN rank-by-rank exactly once: for each rank string, write out the explicit 8-slot expansion (each digit = that many empty squares, e.g. "3q4" → "_ _ _ q _ _ _ _") before naming any piece's square, and cross-check each named piece against the printed board diagram — do this once up front, not piecemeal mid-analysis (agents that re-derive squares turn-by-turn drift, e.g. calling a piece's square differently in two consecutive paragraphs).
 Before naming any piece in analysis, cross-check its type/count against the "Material: white N - black N" field and the ASCII board; if a piece type isn't visible on the printed board or isn't in the material count, it does not exist — discard it immediately rather than building analysis on it. If a candidate or its geometry (e.g. a queen's path to the mating square) seems blocked, impossible, or inconsistent with the legal-move list, that is a signal your rank expansion has an indexing error — stop and re-expand that single rank character-by-character once; do not declare the FEN "typo'd" or default to blindly trusting the move list without resolving the contradiction, and do not keep debugging a possibly-illegal move in your head.
 Runtime check: if your reasoning contains "wait", "why is this legal", or re-lists board ranks more than once in a single turn without an intervening tool call, stop narrating and immediately call `<safety>`/`<hanging>` on the specific move in question — the printed board and legal-move list are ground truth, not a hypothesis to keep re-litigating. Do not reuse a stale material count or piece placement from an earlier turn either — if you re-derive the same square or material total more than once across the game and get a DIFFERENT answer each time, that divergence itself means your parsing is unreliable: stop hand-recomputing and pull an authoritative restatement from `<board>`/`<hanging>` instead of trying yet another manual pass.

Before pricing any capture by material gained, first scan the legal-move list for every check and every move landing adjacent to or on-line with the enemy king, and test the most king-proximal one with `<safety>` first — material comparisons are only relevant among candidates that survive this check-priority scan — this cheaply grounds analysis in a real tool result instead of assumption, and both strong and weak play alike start this way, so don't skip it. When the enemy king looks exposed, a queen or rook check (even a material-sacrificing one) is usually the right first candidate to test over a passive recapture or material grab — but still verify it with `<safety>`/`<simulate>` before committing rather than trusting the hand-built line.

Before analyzing any single capture in depth, first scan the legal-move list once for every move ending in "+"; if even one checking move exists, evaluate it with a tool before spending further budget reasoning about a non-check capture. Do not let the presence of one obvious attacked piece (e.g. a rook that looks won) pull you into analyzing that trade first — a forcing motif is more often the key than a piece trade, and starting from "what's attacked" instead of "what gives check" is a proven failure pattern.


If your own piece (e.g. queen) is hanging or under threat, do not let that narrow your search to defensive/escape moves only — before picking a purely defensive move, first scan the legal-move list for every check against the enemy king and identify which of its escape squares are cut off. An exposed enemy king is the primary organizing feature of the position; only fall back to a purely defensive move after a king-directed forcing candidate has been searched for and found lacking. Also check whether the attacking piece itself is undefended: explicitly list every enemy piece/pawn that could recapture on the attacker's square before assuming it's protected — if none can, capturing it outright is free material and should be enumerated as a top candidate alongside (or instead of) retreating.

When judging whether a candidate move gives check (tracing a queen/rook/bishop's line to the enemy king), do not resolve this by manually walking the diagonal/file/rank in prose ("e1 to h1 diagonal goes through f2, g3...") — this is exactly where hand-derivation produces self-contradiction (concluding a move is check, then not, then reversing again). Instead, pull 2-3 plausible checking/capturing candidates straight from the legal-move list and submit them together to `<safety>` or `<line>`; read the returned legality/check status as ground truth. If a tool flags a candidate illegal or not-check, drop it immediately and re-submit the remaining candidates rather than re-arguing the geometry by hand.

When scanning for candidates, explicitly check whether the opponent's most valuable piece (queen, then rook) is undefended or attackable — a move capturing or attacking an en-prise high-value piece is a top-priority candidate alongside checks; confirm it with `<hanging>`/`<safety>` before committing, since spotting the target correctly is necessary but not sufficient — the capture still needs its own safety/recapture verification. A capture-with-check (a move that is simultaneously a capture of an undefended/under-defended piece AND gives check, e.g. Rxf1+) is the single strongest candidate type — it combines both priority signals, so verify it with a tool first before any quiet move or non-checking capture.

At the FIRST decision point of a position, if two or more plausible checks/captures/threats appear in the legal-move list, submit them ALL together in one `<safety>` call (e.g. `<safety>Re4+, c2, Rxd4</safety>`) before analyzing any of them in prose — do not test one candidate, get a flag, retreat into manual re-derivation of the whole board, then test the next candidate in a later turn. This sequential single-candidate pattern is a proven failure mode: it burns turns and forces repeated error-prone hand recomputation that a single batched call would have avoided.


Immediately before the final `<action>` tag, state a one-line PLAN naming the chosen move and its concrete tactical motif (e.g. "PLAN: Nf7+ forks King and Queen") — this explicit motif statement is a proven marker of correct forcing-move selection; if you cannot name the motif in one line, you have not verified the candidate enough to commit.

Runtime check: on the very first reply of any new position, confirm your output contains a tool tag (`<safety>`, `<hanging>`, or `<threats>`) and not an `<action>` tag — committing to a move before any tool-grounded check is a hard stop, regardless of how clear the position looks.


Before generating candidates in a tactical position, call `<threats>` (or `<hanging>`) to see what of your own is attacked or hanging, and state in one sentence what the opponent's most dangerous reply would be if you passed. Your candidate list must explicitly address every named threat (neutralize, defend, or accept with justification) — never search for an attack while ignoring an existing hanging piece.

Do NOT let `<hanging>`'s flagged pieces be the sole driver of candidate generation — that produces a capture-only candidate list and misses checks. Before triaging captures of merely-hanging material, separately enumerate all legal checking moves and any move that opens a line toward the enemy king (back rank, weak diagonal, king boxed in by its own pawns) and name the motif. A forcing check that restricts the opponent's replies is usually more consequential than a quiet material grab — verify it with `<simulate>` even when a hanging piece is also available.

When in check, filter candidates to only legal check-resolving moves (capture the checker, block, or move the king), preferring a block/capture that also creates a threat, and verify that piece is itself defended. Otherwise, scan the full legal-move list for every check, capture, and near-promotion first (moves ending in "+" or "x"), naming the motif that makes each forcing (e.g. "Ra1+ — rook check"); this cheap filter reliably surfaces the winning candidate, so always do this before considering any quiet move — only consider quiet moves after every forcing move has been evaluated and rejected. Any legal move flagged with "+" or "#" in the move list is a top-priority candidate to verify with a tool immediately, ahead of quieter alternatives — forcing moves are the likeliest source of a clearly-best tactic. Give top priority to any legal move already annotated with "#" (checkmate) in the list, treat it as the standout candidate over other checks/captures. Treat the "#" marker itself as strong evidence and the primary anchor for commitment — confirm the move text you're about to play matches the exact annotated move (guards against misreading the list), then commit with a single <action> tag. Proven pattern: even when the list already flags "#", still run ONE quick independent check — verify each flight square is covered, no interposition/capture of the checking piece exists, and the checking piece is itself defended — before committing; this single pass confirms the annotation without wasting further budget. Only run the full manual escape-square walk from the mate checklist below if the position is otherwise unclear (e.g. the annotation seems inconsistent with the board). Do not spend budget exploring or comparing alternatives, and do not re-open comparison once it's confirmed. Treat `#`/`+` annotations in the legal-move list as computed by the engine's actual rules-checker, not a hint requiring independent geometric proof — if you catch yourself doubting the annotation itself ("maybe I misread the FEN," "maybe it's a typo in the move list") even once, that doubt is the failure pattern to stop, not a reason for more manual re-derivation: make at most one confirming tool call, then commit.  — this is proven effective specifically when the enemy king has few empty flight squares or only one open file/diagonal reaching it: in that exact situation, scan the legal-move list for every check/capture touching a square adjacent to or on-line with the king before picking any candidate to test — pull every move ending in "+" from the legal-move list into the candidate pool before anything else, confirming your first round of candidates is a subset of those checking moves before considering any capture or quiet move. When a king looks exposed, do not conclude a checking sequence is forced mate from visualization alone — confirm it with `<threats>` or `<simulate>` before treating it as decisive. Then batch the 2-4 surviving candidates into one `<safety>` call rather than analyzing them one at a time in prose (the tool accepts multiple candidates in one call — do this within the first turn or two of a new position, not after many turns of narration), and verify the 1-2 survivors' follow-up with `<line>`/`<simulate>`. Read the "opponent legal replies: N" field for each checked candidate — a candidate reducing the opponent to exactly one legal reply is a strong signal and should be prioritized over candidates with many replies; check this from tool output, never estimate reply count from memory. Runtime check: before picking which candidate to verify first, confirm you have explicitly listed every check and every capture from the legal-move list — especially against undefended pieces or the enemy king — by name, and for each candidate's destination/contested square, state the attacker-vs-defender count before favoring it. Runtime check before emitting `<action>`: "does this move appear as the argument of my last tool call, or as the stated conclusion of finished analysis?" This applies even if the move was queried earlier in the turn: a candidate checked with `<safety>` early on and then abandoned for untested mental analysis needs a fresh tool call before it can be played — the most recent tool result, not the earliest one, is what licenses `<action>`.


Once you write "the move is X" or "X is best," stop reasoning immediately and make your very next output the opening bracket of `<action>X</action>` (or a single tool tag) with absolutely nothing after it — no "(final)", no restated plan, no trailing sentence. Before sending, confirm the LAST thing in your reply is the closing tag; a tag buried inside surrounding prose is rejected by the harness as containing no move, and a turn with no tag and no tool call at all is also rejected — either is a wasted turn.


When a forcing move (check) also sets up a follow-up capture on an undefended enemy piece, do not assume an interposing block/capture automatically saves that piece — verify with `<safety>`/`<board>` whether the blocking piece's new square actually defends the attacked square; if it doesn't, keep the follow-up capture in your candidate list as the point of the combination.


When a capture appears to win material "for free," that is precisely when verification matters most, not least: before playing it, check the legal-move list for any available check on the same hanging piece or square (e.g. a queen fork or a queen capture with check) and compare it against the plain capture via `<safety>` — a checking win is often safer since it restricts the opponent's reply, while a plain capture can walk into an unnoticed recapture.

Runtime check: after listing candidates, confirm each one traces to an actual `+`/`x` move in the legal-move list or a threat you can name — not unmoored positional intuition. Runtime check: if you catch yourself naming the same 2-3 candidates (e.g. "Qd4+, Qxc5+, Qe3+") in more than one turn without a new tool result between mentions, that is non-convergence, not fresh analysis — stop re-discussing them and either issue the batched `<safety>` call on that exact shortlist or commit to the one already-priced winner. Do not let repeated re-discussion drift you into a brand-new candidate (e.g. Qf4, Qxc3) that was never in your original checks/captures shortlist.

If your freehand board reading produces something impossible (e.g. you conclude your own king is in check on the opponent's move, or you trace a diagonal/file that doesn't actually connect two squares), that impossibility is proof positive your manual geometry is wrong — do not keep re-deriving it by hand. For every capturing candidate, compute the material delta (value gained minus value lost, e.g. Qxf3 trading queen for knight is 3-9=-6) before treating it as promising; discard captures with a clearly negative delta unless they lead to a forcing checkmate or decisive follow-up you have separately verified with a tool.

When given the legal-move list, first tag every move that is a check or a capture; for each, check whether it ALSO attacks a second undefended enemy piece (a fork). ## Verifying the Move: Tool Ritual


Read the position from the printed board and legal-move list rather than hand-parsing the raw FEN piece-by-piece, and trust the observation's "Material" field as ground truth rather than recomputing it.

Hard rule: a turn that ends in `<action>` with zero tool calls issued that turn is always wrong, even if your manual board-reading feels conclusive — long chains of hand-derived recaptures/defenders are exactly what `<safety>`/`<line>` exist to check instead. Before writing `<action>`, count the tool calls made this turn; if zero, stop and issue `<safety>` or `<line>` on the exact candidate first.
 Writing a tool's tag name inside a reasoning paragraph (e.g. "Let's check `<hanging>`...") is NOT a tool call — it produces no output and verifies nothing. A turn that ends in `<action>` must be backed by at least one real tool invocation issued this turn (or a still-valid one from earlier this position) with actual structured output read and cited; if you catch yourself about to write `<action>` with no real tool result behind the current move, stop and issue the call first. Once a candidate's supporting facts are verified, commit — do not re-run the identical manual check again for reassurance; resolve genuine doubt with exactly one further tool call, not repeated recomputation.
 Cap this at ONE re-derivation: if you notice yourself restating the identical already-concluded fact (e.g. "square X is defended by Y") a second time in the same turn — whether as a "let's double check" pass or a "just to be sure" pass — that is wasted budget, not added safety; cut the repetition, restate the existing conclusion in one line, and move on to the next step. Never bank a multi-move plan from memory or reuse a `<safety>`/`<simulate>` result computed for a different move or an earlier position — re-read the current FEN/board and re-verify against it, and after each move you commit, re-read the new position before choosing the next move.
 When the opponent's reply arrives, re-derive your planned follow-up strictly from THAT turn's newly given legal-move list (do not assume a pre-planned continuation still applies) — if the intended move appears there with "+"/"#", confirm it by checking each of the opponent king's escape squares, blocks, and captures individually before playing it, exactly as in the first-move mate checklist. After every opponent reply, do not just re-confirm your own prior static defender analysis by memory: run a fresh `<safety>`/`<simulate>` call on your intended move in the new position, and explicitly read its "forcing replies" field for opponent checks/captures you hadn't considered — squares, defenders, and pins can shift with the new move.

Whenever a candidate depends on reasoning more than one ply deep about material outcome or an opponent's reply, verify it with `<simulate>`/`<line>` instead of hand-deriving the continuation in prose — trust the tool over self-arithmetic when they disagree, and never skip this to "save budget" on a move that changes material.
 Do not hand-derive whether a move is even legal (e.g. counting squares to confirm a knight move) from the FEN in prose — this is a common source of self-correcting, error-prone arithmetic; cross-check against the legal-move list instead, and if a candidate's legality or resulting material is unclear after one ply, call `<safety>`/`<simulate>` rather than re-deriving square-by-square by hand. Before committing to the first move of any hand-calculated sequence (a capture-then-recapture, a check-then-king-move), call `<simulate>`/`<line>` on that exact sequence first; if the tool's reported reply differs from the one you assumed, redo your material/outcome comparison using the tool's actual reply, not your guess.
 When a line's winning point depends on a specific recapture or follow-up move you have not seen played by a tool (e.g. "...then Nxe3 wins the queen back"), do not assume that move exists — after `<simulate>`/`<line>` returns the resulting position, confirm the relied-upon move is legal from there (checkable against the returned legal-move list or a fresh `<board>` call) and that the printed material/en-prise field matches your prediction before trusting the line; a piece cannot recapture on a square its actual FEN-given location can't reach in one move. Runtime stop-signal: if you repeat a question in prose ("wait, is X possible?") more than twice, or write more than ~3 sentences debating whether a square is attacked/defended, stop and issue the tool call instead. Never reject a forcing candidate based on a single manually-traced branch alone — run `<simulate>`, read all listed replies, and check whether a follow-up survives each before discarding it.


When a `<safety>`/`<hanging>` result lists forcing opponent replies (checks/captures) against your candidate, do not resolve the resulting king safety or material by writing out "If [opponent move], then [my move]?" in prose — call `<line>` (or a follow-up `<safety>`/`<board>` on the resulting position) for a concrete material/en-prise readout before committing. Runtime check: if you write that "if X, then Y?" pattern more than once for the same candidate, that repetition is the trigger to spend a tool call on `<line>` instead of continuing to narrate the king walk.

Before committing to a move that appears to deliver mate (or any "#"/"+" claim), verify it with `<safety>` or `<simulate>` FIRST — do not manually trace king escape squares, diagonals, or rank/file coverage in prose.

 For a mating/forcing candidate specifically, prefer calling `<board>` (or `<simulate>`) on that exact move to generate the resulting position, then read its own printed fields directly ("Gives check: YES - CHECKMATE", "Your side en prise: [...]") — this is faster and more reliable than mentally reconstructing the post-move board from the FEN, and it is the proven pattern that separates a one-call confirmation from a long, self-doubting manual re-derivation of the same position.
 If you catch yourself re-parsing the FEN more than once for the same candidate, or reversing a prior conclusion ("wait, that's different, let me re-check") about piece placement or legality, that is itself the signal to stop and issue the tool call immediately rather than attempting a further self-correction in prose. If the tool confirms mate/no-legal-replies, commit immediately with a single action tag. Only if no tool call is available for the claim, fall back to a single systematic manual pass: parse the FEN/board into a piece list once, then enumerate ALL king-adjacent squares in one pass (occupied-by-own-piece / attacked-by-mover / attacked-by-other-piece / free-and-safe), stating why each is unavailable; confirm no opponent piece can capture or interpose against the checking piece; confirm the checking piece is adequately defended if it can itself be captured. Do this enumeration ONCE — do not re-derive the FEN or re-walk the escape squares a second or third time. Hard cap: if you catch yourself re-checking the same square, block, or capture possibility a SECOND time in the same turn (even without any tool call made yet), that is the trigger to stop immediately — either commit if the first pass already confirmed the tag, or issue one `<board>`/`<safety>` call to settle it. Long repetitive monologues that never call a tool are just as much a failure as skipping verification entirely; a correct one-pass confirmation beats a longer but circular one. Do NOT reject a check/mate candidate on a single unverified defensive reply (e.g. "Qxg3? ## Judging Tool Output


If you catch yourself recomputing the same geometric fact (a square's color, a diagonal's occupants, a king's escape squares) more than once in a turn, stop immediately — call `<board>` or `<safety>` on the candidate instead of re-deriving it a third time. If the legal-move list already annotates a candidate with "#" or "+", do not re-derive the mate/check pattern from scratch in prose; confirm it with one `<safety>`/`<board>` call and commit in the same turn.


Treat typed tool results (en-prise status, attacker/defender counts, legal reply count, and "#"/"+" mate annotations) as ground truth rather than re-deriving piece geometry from scratch; if your own count contradicts an annotation, re-examine your counting before assuming the tool is wrong. If a result seems surprising, spend at most one follow-up tool call to confirm, then move on — do not spiral into repeated manual re-derivation. Re-issue the identical query only if the position has changed since the last call; calling the exact same tool with the exact same move on an unchanged position is diagnostic that you're stuck — spend that budget instead on a genuinely different candidate or a deeper `<simulate>` line.

A `<safety>` flag of "en prise," "LOSING EXCHANGE RISK," or an immediate capturing reply is a fact about the position, not automatically a verdict to discard the move on sight: by default drop the flagged candidate, but if it's your best or only forcing option, gives check, or wins material, spend exactly one follow-up `<simulate>`/`<board>` call on the forcing reply to see the resulting material and position before finalizing the rejection — never reject on the flag alone with zero follow-up, and never chase compensation past that one check.
 A checking move flagged with a losing-exchange risk that also reduces the opponent to exactly one legal reply is a classic puzzle-solution pattern — weight this combination heavily before discarding the move on the material flag alone; confirm via `<simulate>`/`<board>` on the forced-reply position rather than a raw material count. Concretely: after each check/capture's `<safety>` call, read the "attackers N vs defenders 0" (or equivalent "your pieces en prise after the move") field for your own moved piece — an undefended piece there is the trigger to drop the candidate, this is a proven, reliable read. If no compensating tactic is even claimed (no follow-up threat proposed), drop the flagged candidate immediately with zero extra tool calls — do not re-simulate a clear-cut free loss just for reassurance. This applies especially when the flagged move itself gives check or forces a specific reply: never conclude a checking/forcing move is "bad" or "loses material" from the immediate exchange alone — always run `<line>` on the full forced sequence (your move, forced reply, your follow-up) to see the position one full move past the exchange, since a losing trade can still force mate or decisive material on the next move. Runtime check: "did the flagged move force a specific reply (check/threat)? If yes, have I run `<line>` on the full sequence including my follow-up move, not just the immediate recapture, before rejecting it?" For mate/forcing candidates specifically, re-confirm king flight squares and captures/interpositions are fully covered (see the Verifying the Move checklist) before trusting the result — this double-check is what separates real mates from mislabeled ones.


Proven pattern: after every `<safety>`/`<simulate>` call, scan the output for "en prise" or "LOSING EXCHANGE RISK" naming your own piece before deciding on that candidate — treat it as a default veto (per the compensation-check rule above) and move on to the next candidate rather than re-justifying the move in prose. This applies especially to tempting "free material" captures: before playing any capture, check whether the capturing piece itself appears in the "your pieces en prise after the move" list — if it does, the grab loses more than it wins, so drop it immediately rather than playing it anyway.



Before writing `<action>`, re-read the single most recent verdict your own reasoning reached on that exact candidate. If that verdict was negative ("doesn't work," "loses material," "bad") and you have not since overturned it with a tool result, do not play it — get a fresh `<safety>`/`<simulate>` result that overturns the specific refutation, or switch to a genuinely different, separately-verified candidate. "It feels most forcing" is not grounds to override your own just-stated refutation.

If a tool call returns a query/format error (e.g. "'Rxb7+' is ambiguous — did you mean Rbxb7, Rdxb7?" or a malformed-tag warning), immediately reissue the same check using the corrected move string or tag from the error message in that same turn — never let one bad call cause you to drop tool use for the rest of the game and fall back to unaided manual calculation.


Before committing to a move justified by "it wins a piece/pawn because the target square is undefended," run `<threats>` or `<simulate>` on the resulting position to confirm the opponent has no in-between forcing reply (check, capture, or bigger threat — a zwischenzug) that lets it ignore or neutralize the grab. "I found an undefended piece" is not equivalent to "I verified the win" — spotting the target is necessary but not sufficient.


If you find yourself rejecting a check or forcing capture because hand-summed material totals make it look 'merely equal' or 'still losing,' do not trust that tally — especially if you have already recomputed material more than once this turn and gotten different numbers. Call `<simulate>`/`<line>` on the exact forcing move first; a checking move's value often comes from restricting the opponent's reply (e.g. forcing Kh1 instead of a capture), not from the raw material count you computed by hand. If the reply you're evaluating looks like mate or a decisive capture, re-verify it against THIS turn's fresh legal-move list before playing it: confirm the target square/move is actually legal now, and if claiming mate, confirm the opponent has zero legal replies rather than trusting your first-move read of the position — a position can change between your plan and the opponent's actual reply.


Proven pattern: treat every `<safety>`/`<board>`/`<simulate>`/`<line>` result from before the opponent's reply as void once that reply lands — re-run the relevant tool call(s) fresh against the CURRENT FEN before relying on any conclusion from them. ## Budget Discipline



Never play a move that your own most recent reasoning or tool output this turn has just identified as losing material or being refuted — running out of budget is not license to submit it anyway. When budget is nearly exhausted, scan back through this turn's own tool results for any candidate that returned a clean, non-losing verdict (no "LOSING EXCHANGE RISK", no favorable-for-opponent forcing replies) and commit to that one; if none exists, prefer the least-committal safe move (a non-capturing, non-hanging improving move) over a move you've just proven loses material.

Spend budget on tool calls, not manual re-derivation: after the FEN/board is read once, go straight to `<hanging>`, `<threats>`, then `<safety>`/`<simulate>` on concrete candidates rather than hand-parsing squares or recomputing material deltas in prose. Manual arithmetic that spirals across many turns is exactly what starves the budget needed to verify the decisive final move — every turn spent hand-calculating is a turn not spent confirming the line that actually decides the game.


Hard backstop: if a single turn's reasoning exceeds roughly 300 words without issuing any tool call or `<action>` tag, stop mid-thought immediately and emit one now — do not finish the current sentence or paragraph first. A turn that runs long purely on manual board/geometry re-derivation (square colors, diagonal membership, piece attacks) with zero tool calls is the exact failure this guards against; convert the candidate under discussion into a `<safety>`/`<simulate>` call instead of continuing to reason about it in prose.
## Common Pitfalls


- Restating the same candidate-move analysis in prose a second time with no new tool result. Ask "did I already write this exact conclusion in a prior turn?" — if yes, emit a tool call or <action> instead of another paragraph.
- After a tool call discards or confirms a candidate, the very next turn must contain another tool call or an <action> tag — never a turn of pure manual analysis. If any sentence or Q&A pair (e.g. "If X, Y plays Z? No.") appears twice in your own output, that is an infinite loop: stop mid-thought and issue a tool/action tag immediately, do not finish the paragraph first.
- Committing to a move that your own analysis already concluded loses material/"is bad" against its critical reply, or whose every self-calculated line was tagged bad, equal, or drawing. Once your own calculation (with or without a tool) produces a concrete refutation of a candidate, that candidate is dead — do not loop back and re-examine it again hoping for a different conclusion. Either move to a genuinely different candidate and verify it, or re-run `<simulate>`/`<safety>` on the exact refuted line to check if the refutation still holds; never restate a plan that contradicts your own just-derived refutation.
- Naming a needed remedy ("let's use the tools," "let's check `<safety>`," "I'm stuck") and then submitting `<action>` on the very next line without calling one. The named tool must actually be invoked and its output read in that same turn before the action tag — a stated intention to verify is not verification, regardless of how confident the surrounding prose sounds.
- Refuting each candidate one at a time on a single downside ("If Nf3, Nxf3... bad") without ever running <safety>/<simulate> to confirm it. Compare candidates using tool output, not isolated prose objections.
- Concluding in words which move is best but not playing it. The turn immediately after that conclusion must contain exactly one <action> tag — do not let another turn pass on restating the comparison.

- Ending a turn with a malformed tag: a bare tool name with no move argument, a tool name placed inside `<action>` tags (e.g. `<action>safety</action>`), or a spliced hybrid mixing both syntaxes in one tag (e.g. `<action>safety>Kxd5</action>`). Before closing any turn, verify the tag is one of exactly two valid forms: `<action><move></action>` with one legal move, or a properly parameterized tool call naming a specific candidate move (e.g. `<safety>Rb3+</safety>`) — never a fusion of the two.
- Repeating the same unresolved question in prose across multiple paragraphs or turns ("Is there a mate?", "is X defended?") without ever calling a tool to answer it. The first repetition is the trigger: map the question to one tool call (`<threats>`, `<safety>`, or `<simulate>`) and resolve it immediately — don't re-litigate it in the next paragraph.
- Discarding tool-checked candidates for a flag, then committing to a fresh, never-tool-checked move on hand-calculation alone. Every committed move needs its own tool verification, not just the ones you rejected.
- Committing to `<action>` after several turns of unresolved, self-contradictory prose ("I think the best move is X... I think the best move is Y") while tool budget remains unused. If neither a fully-stated forced line nor a fresh `<simulate>`/`<board>` result on the exact final candidate exists, spend remaining budget verifying it before committing.
