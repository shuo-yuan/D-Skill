## When NOT to Analyze: Fast Paths and Stopping Rules


- **First output is a tool tag (hard rule, read this first).** Trigger: you are starting a move (first turn, and again after every opponent reply). Action: read the legal-move list once, write at most the two forcing lists (checks '+'/'#', captures 'x') copied from it, one line each, then immediately emit ONE <safety> batching ALL checks and the 2-3 most relevant captures (or <hanging>/<threats></threats> if there are no checks). Do NOT re-parse the FEN, count material, or trace diagonals or lines by hand before that call. Runtime check: does your reply contain more than ~10 lines of prose before a tag? If so, delete the prose and send the tag. A committed move with zero tool calls is the most common failure.
- **Pre-send checklist (hard, every turn).** Before sending, verify in order: (1) the reply contains exactly ONE tag and it is the last thing; (2) if that tag is <action>, its content is a string copied from the legal-move list (never 'safety', 'simulate', '(final)' or any tool name); (3) if my text says 'I will check/verify/run X' the matching tag is emitted THIS turn, not promised; (4) at least one tool result on the exact move in <action> exists for the current position. If (4) fails, replace <action> with a <safety> on that move. A turn with a tool name inside <action> is a failed turn.
- **Never fabricate tool output.** Trigger: you are about to write "the safety analysis shows", "the tool says" or quote 'opponent legal replies' / 'en prise'. Action: only quote fields that appeared in an actual tool result in this conversation; otherwise emit the tool tag now. Text you write yourself is not a tool result.

- **Tool before arithmetic (hard rule).** Trigger: you are about to write more than 2-3 sentences of hand computation about square control, diagonals, check status, attacker/defender counts, or a capture sequence or material count for a candidate (or a sentence like "is X defended / can the king capture / does this piece attack Y"). Action: stop and emit one <safety> (batch the 2-4 live candidates, e.g. <safety>Qa8+, Qb8+, Qg1</safety>) or <simulate> instead. Do not write "Let's try X" for a move that no tool has seen. If your hand result disagrees with a tool, the tool is right. Must NOT be used to skip the forcing-move lists, and must NOT be skipped because a candidate looks obviously good or bad. Runtime check: has a tool result about this exact candidate appeared this move? If not, call a tool now.
- **Never reject a candidate by hand.** Before writing "this loses the piece", "Kxc5 wins the rook", "this is a blunder" or "this is bad" about a candidate, you need a <safety>/<simulate> field from the current position that says so. An unverified hand refutation is not a reason to drop a check or capture.

The reverse also holds: never abandon a candidate that a tool priced as safe/winning because you imagined 'but Black can just play X'. Run that exact reply through <simulate> first; if you cannot, keep the tool-verified candidate. If your new final candidate has no tool result of its own in this position (e.g. a queen move onto a square an enemy rook attacks), revert to the verified one.
- **Repetition tripwire.** Trigger: you are about to write "let's try X", "wait" or "actually" for a move whose name already appears with a conclusion earlier in your reply. Action: do not repeat it. Emit a tool call on a NEW candidate or the <action>. Must NOT be used to skip the commit gate.
- **Call-count tripwire.** Trigger: you are 3-4 tool calls into a move with a tool-supported candidate and no other forcing candidate is untested. Action: commit the best tool-supported candidate. Do not open a new line of analysis in the last call or two. Must NOT be used if a tool showed the candidate loses material, or while an untested check/capture from your forcing lists remains.
Rules in this section license SKIPPING work: when a single cheap check
settles the position, when further verification cannot change the
decision, and when a line of analysis should be abandoned. Every entry
must name (a) the exact trigger that makes the shortcut safe and
(b) the condition under which the shortcut must NOT be taken. A rule
without both parts does not belong here.

- **Stop the spiral.** Trigger: you have re-derived the FEN/board more than once, re-argued the same line's legality or square control twice, or written "wait"/"final decision" more than once. Action: stop prose reasoning and issue a tool call (<safety>, <simulate>, <hanging>, <threats>) on the specific candidate, or commit the best tool-supported move. Must NOT be used to skip verification of the move you are about to commit (see Verifying the Move).
- **Settled facts stay settled.** Trigger: a tool result already stated a fact ("loses the rook", "opponent legal replies: 1", "en prise: Q@e6"). Action: do not re-derive it by hand in later turns; move to the next unresolved candidate. If the result is truly surprising, spend at most ONE confirming tool call, then move on. Must NOT apply if the position has changed since the tool call.
- **One conclusion, one action tag.** Trigger: you have stated a final decision. Action: emit exactly one <action> tag and nothing after it; never re-open with "wait, what about...". Must NOT be used before the commit gate under Verifying the Move is satisfied.
- **Progress check.** If several turns pass with no new tool call and no new information, either query the next specific candidate or commit the current best-supported move. Zero-tool-call turns are a red flag under a 10-call budget.

**Multi-ply lines go to tools.** Trigger: you are about to write a second consecutive move of a hypothetical line (your move, reply, your move...) or a running material count. Action: replace it with <line>/<simulate> containing the sequence and read the result. Runtime check: count opponent moves you asserted without a tool; more than one means call <line>. If your hand arithmetic for a line gives contradictory material counts even once (e.g. 'up 6' then 'up 14' for the same line), discard that line immediately and run <simulate> on the simplest forcing candidate instead. When the legal-move list has only 2-3 plausible moves (e.g. two pawn pushes), <safety> each of them before any deep hand calculation and use the en-prise / attacker-defender flags to eliminate one.

- **Flagged mate: verify once, then commit.** Trigger: the legal-move list contains a move annotated `#` (search the list for the character first). The annotation is engine-provided ground truth. Action: write one sentence checking the king's escape squares, captures of the checker, and blocks (including pins on the capturing piece). Run one <safety> on that move and read 'opponent legal replies' (0 = mate), then emit a single <action>. That one call plus the `#` flag satisfies the commit gate. Do not survey other candidates or spend more calls. Must NOT be used for a `+` move, which is only a strong candidate and still needs the full verification ritual. Must NOT be used if your manual check or the <safety> output finds an escape, capture or block that contradicts the flag. In that case go back to the candidate list.

If two or more moves carry `#`, compare them by piece value and by which one <safety> confirms with 0 replies, then pick one. Copy the move string verbatim from the legal-move list, including the `#` or `+` suffix, into the single <action>.

## Finding the Move: Motifs and Candidates

**Forcing-move pass first (mandatory).** As soon as you read the legal-move list, write two short lists before any other analysis: (1) every move ending in "+" or "#", (2) every move containing "x". A `#` move is the top candidate: verify it first, and dismiss other checks and captures by name in one line each. Then tag threats, forks, skewers and pins on open lines, and only then quiet moves. Do not do material math on quiet moves until the check and capture lists are written. If either list is non-empty, check at least one member with a tool (<safety>, <simulate> or <line>) before committing to a non-forcing move. Do not fixate on the two moves that visually stand out; the strongest check may be sitting unnoticed in the list. If no move carries an annotation, classify the position instead.

Before it, do a one-line own-piece audit: for each of my pieces, is it attacked by an enemy piece and is it undefended? Call <hanging> if unsure. If one of my pieces is attacked and undefended, every candidate must either save it, defend it, or create a bigger threat, and a candidate that ignores it needs a tool-verified justification (e.g. Qxc6 that leaves a knight en prise is not acceptable without one).

**Classify the position** (tactical melee, quiet, or endgame) from king safety and piece activity. If the enemy king is exposed and a check or capture (including a sacrifice) rips open its shelter, make that the primary candidate rather than a quiet consolidating move. Confirm the move is in the legal-move list and addresses the exposed king or hanging piece you identified.

**Check-chain / mate hunt.** Trace every check at least two plies deep: the forced king replies, then your next check or capture. Use <line> with the full sequence, e.g. <line>Rf8+, Kg8, Qc8+, Kh7, Qh8+, Kg7, Qg8#</line>. A check that ends in forced mate beats any "safe material win". In mateIn2 or short puzzles, or when the king is exposed or on a weak back rank, the solution is usually a check, a capture with check, or a quiet move leaving one legal reply, so spend calls on the mating line before settling for a capture. Do not discard a sacrificial check just because the piece can be taken, if the replies are forced and lead to mate. Runtime check: did I trace every check two plies deep, not just the first one that failed?

When several checks exist, rank them by king restriction before material: run <safety> on each and prefer the check with the fewest 'opponent legal replies' (0-2), especially when the enemy king is on an edge or blocked by its own pieces; explore it one ply deeper with <simulate> before choosing a check that merely wins a pawn or exchange (e.g. Rh1+ trapping a king beats Bxf6+ winning a pawn if the rook checks force mate).

**Legality filter.** Any candidate not in the legal-move list is discarded immediately. If your idea needs an unlisted move, you have mislocated a piece: re-read the board once, then use a tool.

**Odd-looking legal moves.** If a listed move seems geometrically impossible (e.g. a capture on a square you believe is empty), spend one sentence checking whether it captures the enemy piece standing there; if still unsure, call <hanging> or <safety> instead of re-parsing the FEN repeatedly.

**Runtime check.** If you considered more than 2-3 candidates before the first tool call, the scan was not targeted enough; go back to the forcing-move pass.

## Verifying the Move: Tool Ritual


**Tool turn = the tag and nothing else.** When you decide to call a tool, the reply is one correctly spelled tag from the allowed set, with only a one-line reason before it at most. Do not write "(reasoning)", "(final)", "I will run..." or "let's check...", and do not put pseudo-tags such as <tactics> inside prose. If the environment answers "no tool tag and no move", your next reply must be nothing but one minimal tag, e.g. <safety>Qa8+, Qb8+</safety>, or <threats></threats> when unsure. Runtime check: scan your draft for future-tense tool verbs ("I will run", "let's call"); if present, delete the prose and send the tag.

**Early batch (hard).** By the end of your second turn at least one <safety> batch covering your forcing-move lists (checks and captures) must have been issued; a move committed with zero tool calls is a process failure.

**Trust the given board.** Take piece squares from the printed rank-labelled diagram and the Material line; do not decode the FEN character by character more than once. If you use the FEN, cross-check every piece you rely on against the diagram; if they disagree, trust the diagram. If you catch yourself giving two different contents for one square, or a tool output (e.g. <threats> listing a move you think impossible) contradicts your mental board, your mental board is wrong: call <board> once to reconcile, then continue from the tool output. Never dismiss a tool result as a bug.

Parse the board at most once per turn, then immediately name the key features (passed pawns, king exposure, own hanging pieces, forcing moves) and move to candidates. Trust the printed legal-move list and its +/# annotations for legality and check status; never rebuild legality from the FEN. If you have not yet called a tool, do not build square-color or diagonal arguments on a piece location you decoded from the FEN; read it from the rank-labelled diagram once, and let <safety>/<threats> output confirm geometry (check, blocked line) rather than deducing it.
**Turn format (hard rule).** Every turn ends with exactly ONE well-formed tag, and nothing after its closing tag. The tag is either a single tool call (<hanging>, <threats>, <safety>, <simulate>, <board>, <line>) or a single <action>MOVE</action> whose content is exactly one string from the legal-move list, spelled as listed (including +/#). Never put a bare word such as "safety" or trailing text such as "(final)" in or after <action>. Never end a turn with reasoning only; such a turn is rejected and wastes budget. If you write "I will call <safety> next", emit the call in that same turn. Before sending, check that there is exactly one opening tag with its matching closing tag, and that it is the last thing in the reply.

1. **Open with a tool, not a manual re-parse.** On the first turn, call <hanging> or <threats> and anchor on its output. Do not re-derive the FEN by hand more than once.
2. **Ground truth is the tool output and the legal-move list, not your own board reading.** When geometry matters (is it check? is a line blocked? is a piece en prise?), get it from <safety>, <hanging> or <threats>. If your analysis contradicts the legal-move list or a tool result, resolve it with a tool call, not more re-reading of the FEN.
3. **<safety> on the exact candidate.** Read "gives check", "opponent legal replies", "forcing replies" and "en prise" verbatim. Any claim like "this is check" or "X is forced" must come from a tool field; otherwise call <safety> first.
4. **<simulate>/<line> for the follow-up.** Once narrowed to a candidate, call <simulate> with the candidate plus the expected reply or replies (all opponent legal replies when there are few) instead of narrating multi-ply trees by hand. If the tool syntax errors, retry once with corrected syntax; if it still fails, state that the follow-up is UNVERIFIED.
5. **After each result, immediately query the next candidate** rather than arguing it out in prose. The budget is about 10 calls per move; use them.
6. **Mate verification checklist.** Before committing a move that gives check (or is marked `#`), test all three defenses in turn: (a) can the king move to any adjacent square, including squares the checker does not cover and capturing undefended adjacent pieces; (b) can any enemy piece capture the checking piece; (c) can any enemy piece block the check (not applicable to knight checks or adjacent checkers). Only when all three fail, write "checkmate" and commit. If any defense exists, go back to the candidate list. Confirm with the <safety> field "opponent legal replies" where possible.

Do not hand-simulate king-move branches after a check; use <simulate> with the check and the most forcing reply, or <board>, and let the returned position drive the next step. Multi-ply hand lines are hypotheses: confirm at least the first two forced replies with <line>/<simulate> before relying on them.

A move marked `#` in the legal-move list is the default hypothesis: never dismiss it after finding one apparent defence. Before saying a capture/block is available, check that the capturing or blocking piece is not PINNED (e.g. your queen or rook standing on the same file/rank/diagonal between the enemy slider and its own king), since a pinned piece cannot capture the checker. Enumerate king flight squares one by one (occupied by own piece / covered by which enemy piece). If unsure, <safety> on the # move and read 'opponent legal replies' (0 = mate).
7. **Commit gate (mandatory before <action>).** The exact move you commit must have either (a) a <safety>/<simulate> result from the current position, or (b) a written, complete list of every opponent reply and the resulting good position for you. Never commit a move merely because the others were refuted ("by elimination"). Runtime check: if you recompute which pieces defend a square a second time, or your piece locations differ from an earlier turn, stop and call a tool on that exact move.

Final-move contradiction check: immediately before <action>, look for the move string in your own reply. If it appears near "blunder", "loses", "hangs" or "refuted", do not play it until a new <safety>/<simulate> on it shows the refutation does not hold, or switch to the candidate your evidence supports. Also, a mismatch between the committed <action> and the last tool-verified candidate is a red flag.
8. **Own-analysis stop signal.** If your last paragraph admits the move loses material, is unclear, or "might" work, do NOT commit. Run <simulate>/<safety> again or pick a tool-verified alternative. Do not rationalise ("often in puzzles this is the key").
9. **Don't discard a self-found winning idea by hand.** Before dropping a forcing or mating candidate, spend at least one <safety> or <simulate> on it and read the opponent's actual escape squares. Abandon it only if a tool result from the current position contradicts it.

## Comparing Candidates

**Keep a tested-candidates ledger.** Track each candidate as "move: verdict (evidence)" and introduce only new, untested candidates in later turns. Do not re-open a rejected candidate unless a new tool result changes the picture. Cycling the same 3-5 moves is the classic way to burn the budget with no decision.

**Tool-based comparison.** Run <safety> on each live forcing candidate (checks first) and pick the one whose output shows the fewest opponent replies and no en-prise loss for you.

**Batch all checks, then compare fields.** Trigger: the legal-move list has 2+ checks (or a check and a capture). Action: put every one in a SINGLE <safety> call (e.g. <safety>Ra8+, Rf7+</safety>) and compare 'opponent legal replies', 'en prise' and exchange flags across all of them before choosing. Must NOT commit after testing only one check while another sits untested in the list. Runtime check: does your <action> move appear in a tool result next to at least one rival candidate?

**Puzzle prior: forcing first.** The task statement says a short forcing solution exists (mate in 2, or a 2-move win). Trigger: you are framing the position as 'how do I trade safely / simplify' or picking a quiet material trade while a check exists. Action: treat every check as the primary candidate and run <simulate>/<line> on it (forced reply, then your follow-up check, capture or fork) before considering trades. A check that loses a piece on ply 1 can still win on ply 3; do not rate it by one-ply material.

**Hard stop on refutations.** If your own analysis or a tool result surfaces a losing continuation (e.g. "queen lost for bishop", "attackers 1 vs defenders 0 [LOSING EXCHANGE RISK]"), that candidate is dead. Do not play it because it "feels forcing". Move to the next most forcing legal move and test it with a tool. Runtime check before <action>: did I just identify a bad line following from this move? If yes, choose differently unless a further tool call shows the line does not occur.

**Never play a self-refuted move.** Trigger: your own last calculation for a candidate ended in 'doesn't win', 'loses the queen', 'not check' or 'down material', and you are about to play it anyway because it is 'forcing', 'active' or you are tired. Action: do not commit; run <safety>/<simulate> on it once, and if the tool confirms the flaw, pick a different candidate from the untested forcing list. Exhaustion is not evidence.

When two or more candidates both look promising, gather the same
evidence for each (one <safety> block, one batched <simulate> against
its testing replies) and choose by comparison — never commit the first
sufficient-looking move.

**Name the runner-up.** Trigger: you are committing a non-mate capture or tactic. Action: before <action>, name at least one alternative capture or check and state in one sentence why it is inferior. Use tool-reported material or safety data where available, for example a piece won cleanly versus a pawn won with equal trades. Skip this only when a `#` move is flagged (see Flagged mate).

## Judging Tool Output


- **Single-reply checks are not dead.** Trigger: <safety> shows a check with 'opponent legal replies: 1' (even if that reply captures your piece, or a flag says 'attackers 2 vs defenders 2' / 'captures queen'). That flag prices only the immediate exchange. Action: run <line> or <board> on the check plus the forced reply and judge the resulting position (open files, follow-up checks, mate threats, material after recapture). Discard only if the follow-up position is tool-confirmed weak. Must NOT apply when the check has several good replies for the opponent, or when the forced follow-up is already shown as losing.

Likewise a 'LOSING EXCHANGE RISK' or 'captures queen/rook' flag on a check or capture is a price of the first ply only: never discard on it or start free-associating about mates in prose. Immediately run <simulate> with the move plus the recapture (e.g. <simulate>Rxf5+, Kxf5</simulate>) and read the material and board, then test the NEXT candidate with a tool. Only a simulate result showing you down material after the full forcing sequence kills the candidate.
- **Simulate to quiescence.** Trigger: a <simulate>/<line> result shows you down material right after the opponent's single reply to a sacrifice/exchange. Before discarding, look at the resulting board for any of your pieces that can recapture on the square the opponent's piece just landed on, or a further check; if one exists, re-run with that extra ply. Discard only once the material readout after the full forcing sequence is unfavourable. Must NOT be used to keep a candidate alive once the extended line is shown as losing.
- **Check chains: trace to the end.** Do not reject a queen/rook sacrifice-check after a one-ply mental read of 'I lose the piece'; require a <line> through the forced replies (two or more plies) before ranking a quiet material grab above it. If no tool evidence exists for the forcing move's outcome, state that explicitly and do not choose the quiet alternative by elimination.
- Read the audit fields literally: "your pieces en prise after the move", "attackers vs defenders", "[LOSING EXCHANGE RISK]", "gives check", "opponent legal replies". Treat them as ground truth; do not hunt for attackers by re-deriving diagonals from the FEN.
- A non-empty en-prise list for your own pieces is grounds to drop the candidate unless a <line> shows the forced reply sequence wins back more. A clean result (no own pieces en prise, forcing replies leading somewhere) supports committing.
- "opponent legal replies: 1" or "forcing replies: none" after a check is a strong signal of a mating net. Prioritise that candidate.
- **Replying to a check: compare every legal reply.** Do not stop at "does it escape check". For each legal reply (capturing the checker, each king move, blocks), evaluate the material result and whether your own pieces are left en prise. Example: after `Nxe7+` with replies `Bxe7, Kf8, Kh8`, the king moves leave a piece hanging while `Bxe7` recaptures and keeps the material gain.
- A <line> result showing a material swing or mate is more reliable than any mental count; use it to price multi-move ideas.
- A tool result that refutes a candidate is final for that position; do not re-litigate it in later turns.

## Converting the Line (Second Move)


**After every check or capture that drags the opponent's king or a defender, re-ask what is now loose.** Run <hanging> in the resulting position, or use <simulate> on your forcing move and read the opponent's pieces en prise. A piece that was safe before the forced reply, such as a rook the king was guarding, may now be undefended. Check this before building a slow mating net or pawn-grab, especially in rook endgames. Do this again at the second move, using <hanging> or <safety> on each capture in the new legal-move list.
After the opponent's reply, first read the new legal-move list and look for mate or winning captures there (a move flagged with # or a check with few replies) before any hand analysis. Verify the candidate second move with <safety> (check its "gives check" and "opponent legal replies" fields), and check each king escape square individually before committing. Do not relax after a correct first move; the second move is scored too.

## Budget Discipline


**Budget pacing and commit rule.** Plan: call 1 = <threats>/<hanging> (or a <safety> batch on the forcing lists); calls 2-3 = <safety> on remaining checks/captures; by call 5 at the latest run <simulate>/<line> on the top 1-2 candidates (never save the first <simulate> for the last call). If a candidate is verified clean and no other forcing candidate is untested, commit. Once you have written 'the move is X' or 'best is X', your VERY NEXT output is exactly one <action>X</action> — never a further tool call such as <safety>X</safety> marked '(final)'. When only 1-2 calls remain, stop analysing and commit the best tool-supported candidate.

**Do not commit from recollection.** Trigger: you are choosing a move because it 'feels standard', 'I recall this pattern', or you wrote 'I'll stick with X' without finishing its line. Action: price the move against the opponent's single most testing reply with <simulate>, and price at least one alternative (especially the simplest forcing capture, e.g. winning an undefended pawn) the same way, then compare on concrete material/king-safety results. Must NOT be used to keep re-analysing after both are priced.
You have about 10 tool calls per move. Plan roughly: 1 call for <hanging>/<threats> orientation, then 1 call per candidate drawn from the forcing-move lists, keeping 1-2 calls in reserve for a <line> on the finalist. Prefer many short tool calls to one long reasoning block, and keep reasoning between calls to a few sentences. A turn with thousands of words of prose and no tool call risks runaway loops, hallucinated pieces and never committing a move. Always leave enough budget to commit an <action>. If calls are running low and a tool has shown a candidate to be clean, commit it with a one-sentence justification. Any legal move in a well-formed <action> tag beats no move. Once a move is settled, close cleanly: the next output is exactly one <action>MOVE</action> with nothing after it, and no hedging or reopened analysis.

## Common Pitfalls

- Skipping the checks/captures list and calculating only the moves that stand out visually (e.g. missing a rook check on an open file).
- Announcing a tool call in prose without emitting the tag in the same turn.
- Putting a non-move word or trailing text in <action>, emitting multiple <action> tags, or ending the turn with no tag.
- Hand-parsing the FEN repeatedly, with piece inventories that drift between turns, instead of asking a tool.
- Treating a tool's surprising output as a bug and spending the turn re-deriving the board.
- Asserting check or forced-reply status from visualisation instead of a <safety> field.
- Settling for a safe material win without checking whether a check chain mates.
- Playing a move after your own analysis has refuted it (e.g. a capture with a losing recapture), instead of running <simulate> first.
- Re-analysing already rejected candidates instead of testing new ones.

## Won or Favorable Endgames: Bank the Safe Material

- **Trigger:** a rook or pawn endgame where you are equal or ahead, and a capture of a pawn or piece is in the legal-move list. **Action:** run <safety> on the capture. If it shows no attackers and no own pieces en prise, take it rather than looking for a cleverer maneuver, then re-run <hanging> on the new position for the next free target. **Must NOT be used** if a check-chain or mate line is still untested, or if <safety> shows a defender or [LOSING EXCHANGE RISK].
