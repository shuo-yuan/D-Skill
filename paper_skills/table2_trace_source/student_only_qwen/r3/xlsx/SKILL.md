## Core Workflow



1. Inspect all relevant sheets: print sheet names, dimensions, headers, and every cell's coordinate and value for the entire used range (not just a sample).
2. Plan changes based on actual data, not assumptions.
3. Execute changes.
4. Verify output: reload the workbook and print the final answer range to confirm it matches expectations.
**Formula cells**: reload with `data_only=True` and confirm every cell holds a concrete computed value (number, string, datetime) — not `None`, not formula text. Printing formula text is NOT verification; only computed values count.

- After inspection, confirm the output file path and begin implementation.
- Before writing the final output, ensure the target directory exists (e.g., `os.makedirs(os.path.dirname(output_path), exist_ok=True)`). After writing, immediately verify the file was created at the exact output_path and inspect its contents to confirm data is present in the expected cells.
- Before modifying any cells in the answer range, take a snapshot: read and log all current values and types in the exact answer range. After writing and saving, reload the workbook and compare the new answer range to the snapshot to verify only intended changes were made. Limit initial exploration to 3-4 inspection actions (e.g., printing sheet info, headers, unique values, row counts, formulas). Do not exceed three consecutive read-only inspections without starting to write or save. Before declaring TASK_COMPLETE, verify the output file exists at the required path (e.g., `os.path.exists(output_path)`).

- Before TASK_COMPLETE, reload the output workbook with `data_only=True` and assert that every cell in the graded answer range contains a concrete value of the expected type (e.g., `int`, `float`, `str`) — not `None`, formula text, or error values. Print the first 3 and last 3 cells as evidence.

- If after 3 inspection actions you have not started writing, stop and implement the solution immediately.
After the third read‑only action, your next action must be to write a script that modifies and saves the workbook.
- Never end a task with only inspection outputs; always produce and run a write‑and‑save script that modifies the workbook and saves it to the required output path. Confirm the output file exists (e.g., `os.path.exists(output_path)`) before proceeding. Do not issue another read‑only command until the first save is complete. Every task must include an explicit write-and-save step that produces the output file at the required path.

Before execution, parse the task instruction to identify the deliverable type. If the task explicitly asks for a VBA macro or a formula string (e.g., 'How can I create a VBA code...' or 'What formula should be used?'), embed the code/formula accordingly. Otherwise, produce computed values: compute results in Python and write them directly as values, not as formula strings. Only write formulas if the task explicitly asks for formula text.

- **Deliverable type vs. answer range**: When the task asks 'how can I create a macro/formula to do X' but the graded answer range is a data range (multiple rows/columns of values), produce the computed data output, not the macro code or formula text. The grader expects the result of the operation, not the tool used to produce it. Only embed macro code or formula text when the answer range explicitly expects code (e.g., a single cell with a formula, or a VBA module listing).
Before writing any code, explicitly restate the deliverable type (macro, formula, static values, pivot table, chart) and confirm your plan produces that deliverable — not a static equivalent that coincidentally matches the expected output. If a macro is requested, the workbook must contain the macro code; do not silently replace it with a one-shot Python transformation. After producing the output, re-read the instruction's first sentence and verify the deliverable type matches what you actually wrote.
For complex lookups (e.g., INDEX-MATCH, VLOOKUP), implement the logic in Python and write the results directly, unless the task explicitly requires the formula text. Verify with `data_only=True`. Also note the exact graded answer range (e.g., 'Sheet1'!A1:A22) and its dimensions; all verification steps will use this range.


- **Proven successful**: Always start by printing the full content of every relevant sheet (all rows, all columns, including headers, empty separator rows, and any pre-filled output labels) to ground all subsequent decisions in actual data. Skipping this step leads to incorrect assumptions and failures.

This inspect-act-verify pattern (load, print structure, transform, verify) has been proven to catch errors early and produce correct results. Always follow this sequence.


- If the task asks to fix or modify existing VBA code, first inspect the workbook's VBA modules (e.g., `wb.vba_project.VBComponents` names) and print the code. Do not substitute a Python script for the macro unless the task explicitly expects the data result, not the macro itself.
- Always write to the absolute output_path from the task; never use a relative filename. After writing, verify with `os.path.exists(output_path)` and print the result.


- **Macro creation**: When the instruction mentions "macro", "VBA code", "function", or "automate", first inspect the workbook for existing VBA modules (`wb.vba_project.VBComponents`). If none exist but the task requests a macro, embed a VBA procedure in the output workbook. Do not substitute a Python script that fills cells with computed values unless the task explicitly expects the data result, not the macro. After saving, verify the macro module exists.

- If the workbook contains multiple sheets, inspect all sheets (not just those named in the task) to uncover hidden data or dependencies that may affect the output.

- If the output sheet already exists (even if it appears empty), inspect it fully — print all rows, columns, and headers — to determine whether it contains partial data, headers, or formatting that must be preserved or updated. Explicitly decide whether to update, append, or overwrite before writing.
## Inspection



- Before any writing, load the spreadsheet and print sheet names, dimensions, headers, and a comprehensive view of the data layout (e.g., every cell's coordinate, value, and type for the entire used range, or at least the first 20 rows with coordinates). When printing all cells, ensure the output is not truncated; if the range is large, print in chunks (e.g., 50 rows at a time) to confirm every row is captured. This ensures a complete map of data layout, headers, and empty regions, preventing off-by-one errors and misread data. After inspection, explicitly note the sheet names and row counts that are relevant to the task before proceeding.
- Before scanning a column for criteria, inspect the first 2–3 rows (or the declared header row) to confirm where data values actually start. Begin search loops after any header rows. Print the row number and cell value of the candidate and manually confirm it is not a header label.
- Before processing any data, dynamically determine each data block’s row and column extents by scanning until an empty cell or reading headers from the relevant row. Never hardcode ranges based on a visual scan.
- When locating a column by header value, scan the header row (e.g., row 5) with a loop: `for col, cell in enumerate(header_row): if cell.value == 'target_value': col_index = col`. Print the found column index for verification.
 Also print a few values from that column to confirm it contains the expected data (e.g., employee names, not IDs), guarding against header-name collisions. Use case‑insensitive matching (e.g., `cell.value.strip().lower() == target.lower()`) when header casing may vary. If the target is not found, raise a clear error (e.g., `ValueError('Column "target_value" not found')`). This avoids hardcoded column letters and handles shifting positions.
- Before filtering, inspect data types and value distributions of the target column. Print each unique type and a sample of its string representation. Do not assume all values are strings or that string coercion is safe.
- After any column move or restructure, print and inspect the full header row (entire row, not just target). Verify each header label appears exactly once in the expected order, with no duplicates or lost labels. If the operation was done by shifting raw values rather than a built-in column-insert/move method, this check is mandatory before saving.

- When a task involves per-entity computation (e.g., per employee, per department), print the unique values of the grouping column(s) and confirm the required grouping scope. After writing results, verify that no cross-entity contamination occurred by checking that each entity's output only reflects its own data.
- Before building formulas that reference specific cells, print those cells' values and types to confirm they contain the expected data types (e.g., numbers, not strings). If a formula expects numeric inputs, verify the cells are indeed numbers; otherwise, the formula may silently fail.
- When writing a formula that references other cells, first read the actual values of every directly‑referenced precedent cell (using `data_only=True`) and print them. If any precedent cell is `None`, empty, or an error, the formula will likely evaluate to `None`. In such cases, compute the desired result in Python and write it directly instead of relying on the formula.

- When mapping source data to target blocks (e.g., invoice numbers to sections), inspect the target sheet for any existing values that might reveal the intended mapping (e.g., existing identifiers in the target rows). Print a side-by-side comparison of the source sequence and the target block structure to confirm the mapping assumption (e.g., 1:1 correspondence) before writing.

- When writing formulas that reference a data section based on observed rows, programmatically confirm the mapping between summary items and data rows. For each summary item, print the matched rows from the data section and the values to be aggregated. Compare against expected totals to catch misalignment before writing formulas.
- When a file access fails (e.g., `FileNotFoundError`), list the directory contents of the containing folder to verify the exact path before retrying. Never assume the path from instruction text alone; always verify the file exists at the expected location.
- Before writing any code, perform two inspection passes: first a broad structural scan (sheet names, dimensions, headers, sample rows), then a detailed content scan (full row-by-row dump of relevant columns, printing all non-empty cells). This ensures no hidden patterns or edge cases are missed before writing logic.

- When building lookup dictionaries from scanned data, filter out header rows and empty cells explicitly (e.g., `if row[0] is not None`) before populating the dict. Print the resulting keys to confirm the lookup table is correctly parsed.
- When a sheet contains multiple data tables or blocks, print the entire sheet row‑by‑row with explicit column letters (e.g., `for row in ws.iter_rows(min_row=1, max_row=ws.max_row, max_col=ws.max_column): print([cell.coordinate, cell.value for cell in row])`) to identify all data regions, headers, and boundaries before planning any operations.
- During initial inspection, also print the formula text (using `data_only=False`) for any cells that contain formulas, to understand the existing logic and avoid overwriting them.
- When deleting blank rows, first print all values in the target column to identify the first and last data rows. Use those observed boundaries to compute the deletion range programmatically, not from assumptions.


- When performing case-insensitive text searches in cells that may be empty or contain non-string values, guard against `None` by checking `if cell_val is not None` before calling `.lower()` (e.g., `if cell_val is not None and target_phrase in str(cell_val).lower()`).
- Before modifying a target range, print each cell's coordinate, value, and type (using `type(cell.value).__name__`) to understand the current data types and avoid unintended type changes (e.g., writing a string where a datetime is expected).
- Before deleting rows based on a search in one column, print the full answer range (all columns, all rows) to confirm what data exists in other columns that may be affected. After deletion, re-read the answer range explicitly to verify the expected rows contain the correct content.
- When planning cross-sheet operations, explicitly identify which columns serve as lookup keys and which hold the data to be transferred. Print a mapping of source columns to target columns before writing any transformation logic.

- When a sheet contains existing formulas or helper cells that relate to filtering criteria (e.g., cells with comparison operators like `">="&I2`), inspect those formulas to understand the intended boundary semantics (inclusive/exclusive) before writing your own filter logic. Confirm your implementation matches.
- When a reference/expected sheet is provided, inspect its entire used range cell-by-cell, printing all values, to understand the exact output structure, including any non-obvious patterns like value duplication, non-sequential ordering, or irregular column usage. Do not assume a simple left-to-right top-to-bottom fill without verifying the reference layout.
- Before applying string transformations (e.g., regex, `.strip()`, `.lower()`) to cell values, print the `type()` and `repr()` of a sample of target cells to confirm whether they are strings, numbers, or other types. Choose a conversion strategy that matches the expected output type (e.g., convert cleaned strings to `float` if the task expects numbers).
- When a column will be used for conditional logic (e.g., identifying rows with errors or specific markers), print all values in that column across all rows (not just a sample) to catch edge cases like `#N/A`, empty cells, or unexpected data types before writing any formula or filter.
- When a task involves modifying existing formulas, first inspect the formula objects in detail: print the formula text, any associated metadata (e.g., `ref`, `type` for Google Sheets API), and the exact data range boundaries used. Confirm those boundaries match the actual data extent from the sheet, not just the instruction text. Base any replacement formula on this observed pattern.

- When modifying a formula that references a range (e.g., MAX, SUM), first print the formula text, then print the values of the cells at the boundaries of the range (first and last rows) and the sheet's max row to determine the correct extent. Never assume the range ends at the row just before the formula cell; verify the last data row.

- Before writing, check for merged cells in the target range using `ws.merged_cells.ranges`. Print any merged cell ranges found. If a target cell is part of a merged range, either unmerge it first or avoid writing to that cell, as assigning values to individual cells within a merged range can raise `ValueError`.

- After unmerging, print the remaining merged cell ranges to confirm they are cleared.

- During initial inspection, print cell formatting (fill color, font, borders, alignment) for the entire used range to identify any formatting-based groupings, special cells, or visual cues that may inform the data structure, and to capture any formatting that must be preserved or applied to the output.

- When multiple data blocks are separated by blank rows, print the row numbers of all blank rows and confirm they form valid boundaries. Print sample rows from the start, middle, and end of each identified block to verify the range before applying operations.


- When a task involves sorting, grouping, or aggregating data, first extract and deduplicate the source data explicitly (e.g., build a clean list of unique rows using a set of key columns to skip duplicates, headers, and empty rows). Print the cleaned dataset to verify completeness before proceeding.

- When using functions like COUNTIFS, SUMIFS, or VLOOKUP that compare cell values, first print the actual data type (e.g., `type(cell.value).__name__`) and `repr()` of the lookup values and criteria to avoid mismatches (e.g., boolean True vs string 'True').

- Before finalizing any conditional logic or formula, test it against at least two contrasting rows (e.g., an "Ok" row and an "Error" row) and print the expected vs. actual output for each. Confirm the logic handles both cases correctly before writing to the full range.


- When the task specifies target columns by letter (e.g., BN), first map the letter to its integer index using `openpyxl.utils.column_index_from_string('BN')` and verify by reading the header cell at that index (e.g., `ws.cell(row=header_row, column=col_idx).value`) to confirm it's the intended column. Never guess the index from the letter alone. After writing, verify output by reading cells using the exact coordinate string (e.g., `ws['BN2'].value`), not by index, to avoid mismatches.

- When a cell displays an error value (e.g., #REF!, #VALUE!), inspect its formula using `data_only=False` to understand the broken reference before deciding how to fix it. Print both the error value and the formula string to identify the root cause.

- When building a mapping from source columns to target columns (e.g., for pivoting/unpivoting), derive the list of variable columns dynamically by scanning the header row and checking each column name against a lookup table or a list of known constant identifiers (e.g., employee ID, name). Print the identified variable columns for verification before proceeding. Do not hardcode column indices or names.

- When a column contains a marker value that drives processing (e.g., rows where B=1), print every row index where that marker appears and the total count. Confirm the full dataset extent and that boundary rows (first/last occurrences, empty tails) are handled as intended before writing any logic.

- When exact header matching fails, fall back to substring matching (e.g., `target.lower() in cell.value.strip().lower()`) to accommodate plural forms, trailing characters, or abbreviations. Print the matched header text for confirmation.
After any lookup by string matching, immediately compute and print the mapping (key → matched value) and check that every expected match is present and no unexpected matches slipped in. If substring matching is used, verify boundaries by confirming the matched substring is delimited by a consistent separator (e.g., `+`) rather than embedded in other text. Do not break after the first match unless you have confirmed there is exactly one match per key; otherwise, collect all candidates and resolve ambiguity.

- When the task specifies an answer range, before writing, print the first 5 and last 5 rows of that range and also check a few rows beyond the range boundary to confirm the data extent matches the range. If the range starts at row 1, inspect the first few rows to determine if they are headers and, if so, exclude them from transformations that should only apply to data rows.

- When a column is cited in the task instruction (including target and output columns), print at least 5 sample values and their exact string representations (using `repr()`) to confirm delimiter positions, padding, and anomalies before writing any formulas or values.


- When inspecting formulas that perform lookups, identify which columns together form a unique row identifier (composite key). Verify that the formula references all necessary columns to uniquely match a row, not just a single column. Print the composite key columns and a few example key combinations to confirm uniqueness.


- Before writing to a target sheet that already contains data, inspect its existing headers and compare them to the source sheet's headers. If the task says to preserve formatting when copying, do not overwrite the target sheet's header row unless explicitly instructed. Print both headers and confirm they match expectations before writing.

- When updating only a subset of rows in a column (e.g., writing a value only for matching rows), first print the full column's values (or all distinct values) to detect any pre-existing data that may conflict with the intended output. Decide explicitly whether to clear, overwrite, or preserve non‑matching rows before writing.

- When the task specifies a source range (e.g., 'A2:E…'), first print the entire used range of the sheet to identify any additional data blocks outside that range. If any are found, inspect their headers and values to determine whether they are part of the dataset. Document the decision to include or exclude them before proceeding.
- After initial data inspection, compute and print any derived properties needed for the task (e.g., duplicate counts, parsed date values, unique identifiers) to confirm assumptions before writing transformation logic. When dates are involved, print the type and repr of several date cells to detect mixed formats (e.g., string vs datetime) before parsing.
- When diagnosing formula errors, print the full set of formulas in the target region (not just the broken cells) to identify patterns like chained references or missing formulas. This comprehensive scan enables correct diagnosis before writing a fix.

- After initial inspection, compute and print a summary statistic (e.g., sum, count, unique count) for the key columns you plan to use. This sanity check confirms data integrity before you write any logic and has been proven to catch misread data early.

- When the output sheet contains partially filled example cells (e.g., rows 2-3 manually filled), print a side-by-side comparison of each filled cell and its corresponding source cell(s) for at least two complete records. Confirm the mapping logic (e.g., value from column I where column H matches a key) before applying to the full range.

- After writing filtering logic, test it on a sample of rows from the source data: print a few rows that pass the filter and a few that are rejected near the boundary. Confirm the filter's behavior matches the intended inclusion/exclusion before applying it to the full dataset.

- Before clearing or overwriting a target sheet, inspect its current contents by printing the first and last few rows to identify any headers, pre-filled data, or formatting that must be preserved.

- When the output contains multiple independent data blocks (e.g., sorted ranges separated by blank rows), scan the full answer range row-by-row for structural anomalies: duplicated header rows, headers appearing mid-data, or data from one block bleeding into another. Print every row and explicitly flag any repeated header labels or unexpected patterns before declaring TASK_COMPLETE.

- After applying conditional number formatting (e.g., whole numbers → 'General', decimals → '#,##0.##') or font changes, verify the number format and font name on a diverse sample: header row, data rows, and a random far‑away cell. Print `cell.number_format` and `cell.font.name` for each to confirm correct application and no unintended style overrides.

- After clearing and partially rewriting a sheet, reload and print the entire used range of the sheet to confirm that no residual values or formulas remain in columns outside the intended write range, unless the task explicitly requires preserving them.

- **Multi-criteria sort verification**: After sorting with multiple criteria, verify that every ordering rule holds. For each rule (e.g., 'names in J appear before others', 'column H sorted lowest to highest within each group'), check at least two rows in the answer range. If any rule is violated, re‑evaluate the interpretation before finishing.

- After any operation that reduces the number of rows (deletions, filtering), verify that the output range still contains the exact number of rows specified by the graded answer range. If the graded range is larger than the actual data, check whether the task expects empty rows to fill the range or if the data should remain in its original positions. Print the full range, including empty cells, to confirm.

- When deleting rows based on duplicate grouping (e.g., keep one occurrence, delete others), after computing the deletion list, print each candidate row and its group's duplicate count. Confirm that every group contributing a deletion has more than one occurrence; if any candidate belongs to a group with only one occurrence, stop and correct the logic before writing.

- After writing formulas to multiple rows (e.g., using a loop), print the formula text of the first and last cells in the range to confirm that row references adjust correctly (e.g., row 2 formula references B2, row 3 references B3). If any cell contains a hardcoded reference like B2 instead of B{row}, correct it before saving.


- **Reference‑sheet comparison**: If a reference/expected sheet exists, after writing your output, reload the workbook and programmatically compare your written answer range to the reference range cell‑by‑cell. Print any mismatches and assert they match exactly. Never claim a match based on visual inspection or a script’s success message without executing an explicit comparison. If the task provides sheets named 'result …' or explicitly states expected output, treat those as the reference sheets.


- **Target cell address verification**: After writing all output cells, re-read the task instruction to identify every explicitly specified target cell address (e.g., "Place output in H10"). Reload the saved workbook and inspect each of those cells, printing the expected address alongside the actual value. Confirm that no cell is empty or contains an unexpected value unless the instruction allows it.


- If the graded answer range appears empty (all `None`) after writing, immediately verify the column mapping by reading the header cell at the target column index; a column letter-to-index mismatch is likely.

- When the output row count is derived from a count column in the source (e.g., duplicating rows based on a quantity), after determining the source data range, print the total number of source rows and the sum of their count values. After writing the output, verify that the output row count equals that sum. If they differ, re-inspect the source for missed rows or incorrect data boundaries.

- After writing, confirm the output sheet's title and used‑range dimensions match the required graded answer range. Print `ws.title` and `ws.dimensions`, then compare the row and column counts to the expected range (e.g., 'Sheet2'!A1:AG10 should have 10 rows and 33 columns).
- When writing data using column offsets (e.g., pandas `startcol`, `ws.cell(row, col+offset)`), after saving, reload the workbook and verify that the data occupies exactly the expected answer range columns. Print the header row and the last non-empty column; confirm that the column count matches the required range (e.g., G1:I1000 should have exactly 3 columns of data). If data extends beyond the graded range, adjust the offset before final save.

- **Full‑range inspection after writing**: When the graded answer range spans many rows, do not rely on sampling the first few rows. Print every cell in the range end‑to‑end using `ws.iter_rows(min_row=..., max_row=..., min_col=..., max_col=..., values_only=True)` and either print all values or a summary statistic (e.g., count of non‑None cells). This catches gaps, off‑by‑one errors, and silent failures that a partial view would miss.

- When overwriting a target range that already contains values (e.g., clearing and rewriting), first record those values. After computing new values, compare them to the old ones as a sanity check: if they match, your calculations are likely correct; if they differ, re-verify your logic before writing.


- **Decimal-place formatting verification**: After writing cells with custom number formats, reload the workbook and inspect the cell's displayed value (using `cell.number_format` and the actual stored value) to ensure the number of decimal places shown matches the instruction's rule. For rules like 'zero decimal places for whole numbers, 1 decimal place for numbers where only 1 decimal place is needed,' test a sample of cells including edge cases (e.g., -2.5, 5.0) and confirm the formatting logic correctly distinguishes them.
- If any formula cells remain in the graded answer range and the task does not explicitly require formulas, compute their values in Python and overwrite them before final save. Reload and verify that all cells now contain concrete values.


- **Expected‑value comparison**: When the task describes explicit expected values for specific cells (e.g., "the result should be 42"), compute those values programmatically and compare them to the actual output after writing. Print any mismatches to catch errors from merges, overwrites, or partial copies.
- After each modification to the output sheet, reload the workbook and print the full answer range values (or the entire sheet if the answer range is not specified) to visually confirm the transformation before proceeding. Cross-reference at least one computed output row against its source rows by printing both the source values and the computed results in a single verification script to catch off-by-one errors, missing columns, and formatting issues early.

- **Structural change context verification (insert/delete)**: After any row insertion or deletion, reload the workbook and inspect at least 3 rows above and below each modified position, printing full row content (all columns). Confirm that data shifted correctly into new positions and that no data was lost or displaced. Do not check only the inserted/deleted row — verify the surrounding context to catch silent displacement.

Compare the modified row count to an independently computed expected count.

- When printing the answer range for verification, use `iter_rows(min_row=..., max_row=..., min_col=..., max_col=..., values_only=True)` to print all rows' values in a compact table, confirming every cell matches expected output. This pattern was proven effective in closing the loop between writing and declaring success.
## Common Pitfalls



- Writing formulas without verifying their computed values. After writing formulas, always reload the workbook with `data_only=True` and print the computed values of the answer range. If any are `None` or error, compute the values in Python and write them directly; never trust formula text alone. **Anti-pattern**: writing `=SUMIF(...)` into D2, printing `cell.value` (which shows the formula string), and declaring success — the grader will see `None` because openpyxl cannot evaluate formulas without `data_only=True`. Always do the `data_only=True` reload and confirm numeric output.
Hardcoding row/column ranges (e.g., `range(2, 86)`) based on a single observed `max_row` value without dynamically deriving the data boundaries. Always determine `min_data_row` (first row after headers) and `max_data_row` from the spreadsheet’s actual dimensions and content, using `ws.max_row` and scanning for headers. This prevents silent data loss if the dataset size changes.
- Applying string-based filters (e.g., startswith) without first inspecting data types. Non-string values like integers or None can produce unexpected string representations. Always inspect the column’s types and sample conversions before filtering.
- Moving columns by blind value-shifting without verifying the header row afterward can silently corrupt column–data associations.
- Writing raw values where the original cells contained formulas (especially in totals) leads to inconsistent outputs; always check cell type before copying.
- **Row deletion index drift**: When deleting rows programmatically, iterate from the last row upward (`for row_idx in range(ws.max_row, 1, -1)`) to avoid index shifts. After saving, reopen the output file and verify the total row count and a few sample rows to confirm deletions were applied correctly.
- Skipping initial inspection leads to incorrect assumptions about data layout and missing rows/columns.

- **Cumulative formula boundary errors**: When writing cumulative formulas (e.g., running totals, compound growth), ensure the first row's formula correctly incorporates the starting balance (often 0) before applying the current row's operation. Manually compute the expected values for the first 2-3 rows and verify the evaluated formula output matches. A missing initial addition can propagate errors through the entire column.
- Applying stateful rules (like tracking previous values) across the entire sheet without resetting per group (e.g., per employee) leads to incorrect results when multiple entities are present. Always identify natural break points and reset state accordingly.

- **String sorting on mixed-type columns**: Sorting by `str()` yields lexical order that may not match the task's intent (e.g., "CT1", "CT10", "CT2"). Before sorting, inspect the data to decide if a natural sort (extracting numeric subfields) is needed. After sorting, spot-check adjacent rows to confirm the order aligns with the instruction (e.g., "small to large").
- **Rebuilding workbook from scratch**: Creating a new `openpyxl.Workbook()` discards original formatting, named ranges, and other properties. Always load the input workbook and modify it in place, unless the task explicitly requires a fresh file. Before writing, inspect the original workbook's structure (sheet names, formatting, merged cells) to preserve necessary attributes.
- **Writing formulas when the task expects computed values**: If the task instructions describe the output with example values (e.g., "ABC123-02-010"), write computed values, not formula strings. After writing, reload with `data_only=True` and confirm each cell holds the expected value type (string, number) and format. If formulas are required but cannot be evaluated, compute values in Python and write them directly.

- Declaring TASK_COMPLETE after a script prints a success message without verifying the output file's actual contents. Always reload the workbook and inspect the answer range to confirm the transformation was applied correctly.
- **Column deletion index drift**: When deleting columns programmatically, iterate from the last column index backward (`for col_idx in range(ws.max_column, 0, -1)`) to avoid index shifts. After saving, reload and verify the header row to ensure the correct columns remain.

- **Lookup with duplicate keys**: When building a lookup dictionary from a source that may contain duplicate keys (e.g., names appearing multiple times), never default to keeping the first occurrence without evidence. First inspect any pre‑filled example cells in the target range that might reveal the intended matching rule (e.g., Nth occurrence, transposed all‑matches). If no examples exist, explicitly examine all occurrences of each duplicate key and reason about the correct rule implied by the task. After writing, verify that the produced output is consistent with any visible patterns in the original workbook.
- **Using INDIRECT, OFFSET, or other volatile functions that openpyxl cannot evaluate**: Since openpyxl does not calculate formulas, these will produce empty cells when read with `data_only=True`. Instead, use Python to read the referenced data and write the computed values directly. If the task explicitly requires the formula text, compute the value in Python and write it as a cached value alongside the formula.
- **Conflicting instruction ambiguity**: When the task description contains conflicting or layered range specifications (e.g., a primary range and a later "IMPORTANT" clause that narrows it), stop and list both interpretations before coding. Print the exact columns being checked and confirm they match the widest column stated in the instruction. After writing, spot-check rows that could be affected by the column-choice decision (e.g., rows where the extra column has data but the narrowed range would have deleted them).
- When deleting specific rows identified by a condition, collect their indices in a list, sort descending (`sorted(rows_to_delete, reverse=True)`), and delete each in that order. This avoids index drift more safely than deleting while iterating forward.


- **Row deletion verification**: After deleting rows, always re-read the exact graded answer range (e.g., A4:A18) and print their values. Do not rely solely on `max_row` or a single-column check; verify the entire answer range to ensure no data was lost or shifted incorrectly. If the task requires row deletion, ensure that no `None` cells appear in the answer range that would indicate a mistaken clearing operation; only actual row removal should shift data upward.

- After row deletions, also confirm that the resulting sheet's row count (or the number of data rows) matches the expected answer range's row boundary (e.g., if the answer range is A1:F8, ensure the sheet contains data through row 8). If the answer range specifies more rows than present, fill with empty rows or adjust as required.
- **Ignoring existing workbook artifacts (macros, named ranges, specific formats)**: When the task mentions an existing macro, named range, or format (e.g., 'modify an existing macro', 'match format of A2'), inspect that artifact before choosing an implementation. For macros, list VBA modules and print the code; for formats, read the reference cell's `number_format` and use the exact string, not a guessed equivalent. After modification, verify the artifact is still present and the output adheres to the reference's exact properties (e.g., the macro is modified, not replaced by static data; the format string matches the reference cell's `number_format`).
- **Formula syntax errors from string manipulation**: When formulas are constructed via string replacement or concatenation, the resulting formula may be syntactically invalid (e.g., `TRIM()` on a multi-column range). After writing, always reload with `data_only=True` and print computed values; if any are `None`, inspect the formula string for invalid constructs before saving. Never assume a string-edited formula is valid just because it was written successfully.
- **Blindly following suggested formula fixes**: Before implementing any suggested formula fix (especially from user instructions), pause to validate the expression against spreadsheet engine syntax rules. Enumerate alternative approaches (e.g., trim only the lookup column, adjust lookup value) and re-inspect the actual data differences to ground the solution in evidence, not in phrasing.

- **Copying pre-existing formatting or reference sheet answers**: When a task asks to identify a subset of values meeting a condition (e.g., summing to a target), do not rely on pre-existing cell formatting (like highlighting) or a separate reference sheet to determine the answer. Always write algorithmic code to compute the selection, and after writing, confirm that each modified cell was selected by your own logic, not by observation of existing formatting.
- **Writing static numbers when a formula is expected**: If a cell's value should reflect a computation on other cells (e.g., a sum of selected items), write a formula (e.g., =SUM(...)) rather than a hardcoded number. Before writing, inspect the instruction for keywords like 'automatically', 'update', 'dynamic', or 'how can I' that signal the grader expects formulas that recompute when data changes, not static values. If the instruction says 'put the numerical value', clarify whether it expects a static value or a formula. After writing, inspect the cell's content: a formula starts with '=', a static value is a plain number or string. If the task asks for a computed result that should update with data changes, use a formula. After saving, reload the workbook and confirm that at least one cell in the graded range contains a formula (data_type 'f' in openpyxl) unless the task explicitly grades computed values only.
- **Assuming regular spacing from a partial scan**: Do not infer a fixed interval (e.g., every Nth row) from a few data points. Always scan the entire source column and print all non‑empty cells to confirm the full pattern. Also inspect any pre‑existing formulas in the target range for clues about the intended mapping.

- **Formula range adjustment without verifying data extent**: When adjusting a formula's range to exclude a self-referencing cell, first print the values in the entire column to find the actual last data row. Do not assume the range should be `B$7:B322` just because the formula is in B323; verify that B322 is indeed the last data row and that rows 323+ are empty.



- **Multi-criteria sort overriding earlier grouping**: When a task specifies multiple sort criteria with a primary/secondary relationship, never apply a global sort that can override earlier grouping. If the instructions contain conflicting sorting directives, list each explicitly in your plan and decide on a precedence order before writing code. After producing a sorted result, inspect the first few and last few rows of the answer range to confirm all stated ordering rules are satisfied.

- **Writing a static formula string to multiple rows without adjusting row references**: When constructing a formula string and writing it to multiple cells in a loop, ensure that any cell references that should vary by row are parameterized with the current row number (e.g., using f-strings). Before writing, print the formula that will go into the first and last cells of the target range and verify that their row numbers differ appropriately. Writing the same literal string like `=IF(A2=J2,…)` into every cell will cause all rows to reference row 2, producing misaligned results.


- **Shallow verification of fill logic**: After filling blank cells or generating sequences, always spot-check a few generated values against the expected pattern from the task instructions. Do not just confirm that blanks are filled; verify the logic produces the correct labels.


- **Assuming output ends at original max_row**: When a graded answer range specifies an ending row (e.g., A1:B90), always verify that the output file contains data through that exact row, not just up to the original file's last data row. Print the boundary rows to confirm.

- **Macro modification vs. data output**: When the task asks to modify a macro but the graded answer range is a cell range (e.g., A1:E7), the expected output is the resulting data after the macro’s effect, not the macro code. Implement the required transformation (e.g., row deletions) directly in Python and write the resulting values to the output cells. Do not spend effort on editing VBA code unless the answer range explicitly contains macro source text. After writing, verify the answer range holds the correct data values.


- **Conflicting deletion criteria**: When the task description describes one deletion condition (e.g., 'delete rows with "to be processed"') but the existing workbook or code shows a different filter (e.g., VBA code filtering for 'Accepted'), inspect the raw data to determine the correct criterion. Print unique values in the target column and count matches for each candidate condition. Reconcile based on the data and any explicit instruction, not solely on the user's paraphrased intent. If ambiguity remains, clarify before acting.

- **Formula strings producing None in graded range**: When openpyxl cannot evaluate a formula (which is always the case for most formulas), `data_only=True` reads return `None`. If the grader extracts answer-range values and sees `None`, the task fails even if the formula text is correct. Default to computing values in Python and writing numeric/string results directly. Only embed formula text when the task explicitly grades the formula itself.

- **Clearing cells instead of deleting rows**: When the task says 'delete rows' or 'remove rows', you must use `ws.delete_rows()`, not `cell.value = None`. Before writing, re-read the instruction to confirm the required operation. After writing, verify that the row count has decreased and that no `None` cells remain in the answer range from a mistaken clearing operation. A simple value check cannot distinguish between cleared cells and deleted-then-shifted rows.

- **Misinterpreting matching rules**: When the task says 'match and replace based on column B', do not assume a different column is the join key. Before writing any replacement logic, explicitly restate the matching rule — what two cells are compared, and what 'corresponding' means — and verify it against the instruction wording. If ambiguity exists, inspect any provided result example sheets to confirm which columns align between source and target.


- **Unverified scoring/interpolation formula**: When a task requires proportional mapping or scoring, before writing, test the chosen formula against all stated anchor points (min, max, zero) by printing the computed values at those boundaries. Confirm the mapping matches the instruction's description (e.g., linear across full range vs. piecewise).
- **Unverified matching scope**: When the task involves matching parameters to retrieve an ID from a table, do not assume same‑row matching without evidence. Inspect the sample data: for each row, compare its parameters against all rows' comments and print which IDs would match under same‑row vs cross‑row interpretations. Confirm the correct pattern before writing logic.


- **Assuming the graded answer range defines the full processing scope**: When the task instruction specifies an operation across a broader scope (e.g., 'across all columns', 'the entire sheet'), inspect the full used range and apply the operation accordingly, even if the answer range is smaller. Do not limit processing to just the graded cells.
- **Copying data without inspecting target structure**: When moving or copying data, always inspect the target range's existing content (headers, formulas, dependencies) before writing. Do not overwrite target headers with source headers unless the task explicitly asks to replace them. If formulas in the target reference the source data, either adjust them or compute values in Python to avoid broken references.
- **Unverified indexing after code changes**: When you change how cells are indexed (e.g., column offsets, row mapping), always verify the output for at least two non-trivial groups by printing each source row's values alongside the computed results. Confirm the final sums or transformations match manual calculations. Do not rely on a single group check; errors may only affect some groups.
- **Pandas column indexing without verification**: When using pandas, never rely on column integer positions without inspecting column names and values. Use `df.columns` and `df.head()` to identify the correct column by name, not by index. For operations like `drop_duplicates`, use the column name (e.g., `subset='column_name'`), not an integer index, unless the task explicitly references column position.

- **Destructive operations on the graded answer range**: When a task asks to 'delete', 'remove', or 'clear' cells within the graded answer range, first inspect the exact cells and question whether the grader expects the data to be moved rather than permanently erased. If you must clear cells, copy the original values to a safe location or confirm that empty cells are acceptable. After writing, verify the answer range contains inspectable values, not all `None`, unless explicitly required.
- **Applying transformation to full range without testing on sample rows**: Before applying any transformation to the full answer range, test the logic on one or two sample rows (including headers, empty cells, and edge cases). Inspect the results immediately to confirm the transformation handles all row types correctly. Then scale to the full range.
- **Row insertion without context inspection**: When inserting rows based on a marker value, first inspect 2-3 rows above and below each target row to understand what data will be shifted. After inserting, verify that shifted data landed where expected by checking the cells that now occupy the old row numbers, not just the inserted blank rows. Confirm the answer range holds the expected structure — blank rows only where intended and no data displaced into unexpected positions.
- **Hardcoded column extents producing trailing nulls**: When the instruction says to remove blank cells or produce a contiguous output, always verify the entire graded answer range after writing. Print every cell in the answer range explicitly, including those beyond the last written value, to confirm no trailing blanks, old data, or formatting artifacts remain. Derive write extents dynamically from the number of items being placed, never from a fixed constant.
- **Selective verification after bulk write**: Verifying only the first few rows after a bulk operation. Always perform a full‑range verification: either count how many rows were modified and compare to an expected count, or iterate through the entire data range and collect unique outcomes. A head‑only sample cannot catch errors in later rows.
- **Row insertion index drift**: When inserting rows programmatically, iterate from the last row upward (e.g., `for row in range(max_row, start_row-1, -1)`) to avoid shifting rows that haven't been processed yet. After saving, verify the row count and check sample rows.

- **Assuming blank rows are contiguous**: Before bulk deletion of rows that appear blank, programmatically scan the used range to identify all rows where every cell is None or empty. Print the list of row indices that are fully blank, visually confirm they match the intended deletion set, and then delete only those specific rows (iterating from bottom up). Never delete a contiguous block of rows based on a visual scan without verifying that every row in the block is indeed fully blank.
- **Ignoring macro debugging task**: When the instruction asks to 'debug', 'fix', or 'correct' an existing macro, do not bypass the macro and manipulate data directly. First locate and print the existing VBA code (e.g., using `wb.vba_project.VBComponents`). Understand what the macro is supposed to do, fix the code, and then either run the macro or simulate its effect while ensuring the corrected macro is present in the output workbook. After saving, verify that the macro code exists and the answer range reflects the macro's intended result. Do not substitute a Python script for the macro unless the task explicitly expects the data result, not the macro itself.
- **Overwriting cells that already contain correct values without checking**: Before writing to any target cell, inspect its current value and type. If it matches the expected output, skip overwriting unless the task explicitly requires recomputation. Blind overwriting can destroy formulas, formatting, or pre-existing correct data.
- **Copying cell styles unnecessarily**: Do not copy font, alignment, or fill objects unless the task explicitly asks to preserve formatting. Direct assignment like `target_cell.font = source_cell.font` can raise `TypeError`. Instead, copy only `.value` and `.number_format`. If formatting is required, construct new style objects only when the task demands it.

- **Global-sum misinterpretation of row-deletion criteria**: When deleting rows based on a sum-to-zero condition, always inspect all columns (especially ID, account, batch) to identify natural grouping keys. Do not compute an overall sum and delete all rows if it's near zero unless the instruction explicitly says 'all rows together'. Determine the correct grouping (e.g., rows that net to zero per group) and apply deletion per group. After deletion, verify that the remaining rows in the answer range match the intended survivors, not an empty sheet.


- **Using the answer range hint as the data processing boundary**: When the task provides an answer range (e.g., `'Sheet1'!F2:F71`), do not assume that the data ends at that row. The answer range may be a superset of the data. Always scan the relevant data column to find the last populated row and use that as the processing boundary. After writing, verify the last few rows of the answer range to ensure no data beyond the assumed boundary was missed.
- **Clearing non-matching rows unintentionally**: When conditionally writing to a column, never set non-matching cells to empty string or `None` unless the task explicitly requires clearing. This destroys pre-existing data. Instead, only write to matching rows; leave others untouched. Before writing, inspect the target column's existing values to decide what to preserve. After writing, verify that non-matching rows still contain their original values (if preservation was intended) by comparing against the pre-write snapshot.

- **Overwriting pre-existing values in the answer range without checking**: Before writing to any target cell, inspect the entire answer range for pre-existing non‑empty values. If any are present, compare your new computed values to them. If they differ, pause and re‑examine your logic and the task intent before overwriting. After writing, reload and verify that any pre‑existing values that should have been preserved remain unchanged.
- **Expanding task scope beyond explicit instruction**: When the instruction describes a specific subset (e.g., ranking 'dog' values) but the data includes other categories, do not assume the task applies to all categories. Inspect the answer range for pre‑existing labels that may indicate the grader's intent. If the answer range already has some filled cells (e.g., 'cat2'), treat them as constraints: your output must be consistent with them. Do not expand the scope without an explicit verification step. After writing, verify that every value you wrote in the graded range directly corresponds to an explicit requirement from the instructions.
